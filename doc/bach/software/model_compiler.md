# 模型编译器

**文档模式：设计。** 供评审用，不作为实现依据。还没定下来的集中在最后一节。

本文定义一层新的编译器：

* 做什么：把一个模型在一台具体机器上怎么跑写成一段 Python，跑这段 Python 就得到一份 `.bachir`
* 读者：要写这段描述的人，以及要实现这个编译器的人
* 边界：产出的文件格式由《Bach 中间文件格式》定义，本文只讲怎么把它生成出来

***

## 1. 这一层在哪

### 1.1 三份输入

编译器吃三份东西，产出一份 `.bachir`。

* **机器描述**：这台机器长什么样
  * chip 的行列数、每个 chip 的核阵列
  * 片间链路、PCIe 交换拓扑、以太网交换节点
  * 各段的带宽与延迟
  * credit 的额度，以及它在哪些核之间收发
  * 一台机器写一次，换模型不用改
* **模型描述**：这个模型在这台机器上怎么跑
  * 它是一段 Python，本文其余部分讲的都是它
* **实测时间**：每个算子在真实机器上跑出来的时间
  * 编译器不估算计算时间，也不从形状反推，照着填进 `MC` 与 `VC` 行

模拟器不区分文件是编译出来的还是别处来的，两条路产出同一种文件。

### 1.2 产出落到哪些记录

| 记录 | 来自 |
| --- | --- |
| `DIM` `CORE` `PARAM` `MODE` | 机器描述 |
| `EXTNODE` `GATEWAY` `DIRATTR` `CHIPLINK` | 机器描述 |
| `TASK` `TMETA` `CREDIT` `SKIPSRC` | 模型描述，`MC` 与 `VC` 的时间来自实测 |
| `CREDITEDGE` | 机器描述 |
| `EPGROUP` `HOSTBIND` | 模型描述里专家落在哪些核 |
| `TOTALUSERS` `USER` `USERTARGET` `HITMAP` `BITMAP` `OUTFRAG` | 按给定种子算出的这一次 run 的路由决策 |
| `META` | 三份输入的路径与摘要 |

## 2. 描述怎么写

### 2.1 算子

算子是一次计算，对编译器是黑盒。它要能回答两件事：

* 它有哪些**轴**（可以切开的维度），各多长，输出是什么形状
* 每个轴切开之后各份是什么关系
  * **并行轴**：各份互不相干，输出在这个轴上拼起来
  * **归约轴**：各份出的是部分结果，出口要合到一起

算子不回答自己要算多久。

内置算子自带这三件事的答案：

| 算子 | 并行轴 | 归约轴 |
| --- | --- | --- |
| `linear` | `token` `out` | `in` |
| `attention` | `batch` `seq_q` `head` | `seq_kv` |
| `moe` | `token` `expert` | `ffn` |
| `norm` `add` | `token` `hidden` | 无 |

自定义算子自己声明这张表和这两个答案，写法与内置算子一样。

轴只在两处起作用：

* 编译器要补一条没写出来的搬运时，靠它判断多份是拼起来还是加起来
* 人写了合并方式时，靠它检查写得对不对

人已经写明每个核算哪一段的地方，轴不参与。

### 2.2 当前在哪个核上

`with` 划定接下来的算子落在哪个核上：

```python
with cores[2]:
    y = attn(q.head[32:48], k.head[32:48], v.head[32:48])
```

* `with` 可以嵌套，内层盖住外层
* 在 `with` 之外调用算子报错
* 一个核的任务表按代码里出现的先后排，同一个 `with` 块里写在前面的计算排在前面

### 2.3 张量与切片

张量在这段 Python 里只有形状，没有数据。切片按轴名取一段：

```python
q.head[16:32]              # head 轴上的第二个四分之一
x.token[:n]                # 取 n 个 token，n 是变量
```

切片的长度可以是变量。各份不等长的地方靠它写，典型的是 MoE 里每个专家分到多少 token 随路由变化：

```python
n = tokens_of(expert=g)    # 这个专家这次分到的 token 数
with c:
    y = expert_ffn(x.token[:n], ffn=i, of=4)
```

两条规矩：

* 变量在编译时求值。路由决策按给定的种子算出来之后每个变量都有确定的值，写进任务表的是那个值
* 切片本身不产生任务，只记下这一份是谁的哪一段。搬运在数据跨核使用时才出现

### 2.4 搬运的三档

一条数据在一个核上产生、在另一个核上用，就要搬。三种写法，同一份描述里可以混着用。

**一、不写。** 编译器会补上。

**二、写合并方式，拓扑用现成的。**

```python
x = concat(parts, "head")
x = reduce_sum(parts)
x = reduce_sum(parts, topo="ring")
```

**三、每一跳自己写。**

```python
with cores[0]:
    y = attn(...)
    send(y, to=cores[1], tag="a")
with cores[1]:
    y0 = wait(tag="a")
```

`send` 写在代码的哪一行，就排在那个核任务表的哪个位置。要在计算之前先把下一份数据发出去，把 `send` 往上挪一行。

### 2.5 一个完整的例子

```python
CFG = dict(hidden=7168, q_heads=64, head_dim=128, ffn=2048,
           experts=256, topk=8, shared=1, seq=4096, dtype="bf16")


# 一次 attention 在这台机器上怎么跑：4 个核，每核 16 个 head
def attention(q, k, v, cores):
    parts = []
    for i, c in enumerate(cores):
        with c:
            parts.append(attn(q.head[i*16:(i+1)*16],
                              k.head[i*16:(i+1)*16],
                              v.head[i*16:(i+1)*16]))
    return concat(parts, "head")


# 一次 MoE：16 个 chip 各持 16 个专家，chip 内 4 个核再把 ffn 切开
def moe(x, hit, chips):
    parts = []
    for g, ch in enumerate(chips):
        for i, c in enumerate(ch.cores(4)):
            with c:
                parts.append(expert_ffn(x, experts=hit[g], ffn=i, of=4))
    return reduce_sum(parts)


# 一层：结构与原始模型的 forward 一致
def layer(x, cores, chips):
    q, k, v = qkv(norm(x), cores)
    x = x + o_proj(attention(q, k, v, cores), cores)
    x = x + moe(norm(x), route(x), chips)
    return x


# 整个模型：前 46 层在一组核上，后 46 层在另一组
def model(x):
    for i in range(46):
        x = layer(x, group_a.cores, group_a.chips)
    for i in range(46, 92):
        x = layer(x, group_b.cores, group_b.chips)
    return x
```

分两层看：

* `model` 与 `layer`：跟原始模型的 forward 结构一致
* `attention` 与 `moe`：函数体是这个算子在这台机器上实际怎么跑。换一种跑法就重写这个函数，上面两层不动

## 3. 常见并行方式怎么写

这套写法里没有 TP、PP、EP、DP 这些名字，它们是下面这些填法的结果。

| 常见叫法 | 在这里怎么写 |
| --- | --- |
| 张量按列切 | 每个核拿 `out` 轴的一段，出口 `concat` |
| 张量按行切 | 每个核拿 `in` 轴的一段，`in` 是归约轴，出口 `reduce_sum` |
| 按 token 切 | 每个核拿 `token` 轴的一段 |
| 按专家切 | 每个核拿 `expert` 轴的一段 |
| 流水切层 | 不切，`model` 里不同层段的 `with` 指向不同的核组 |
| 按 kv 切 | 每个核拿 `seq_kv` 轴的一段，`seq_kv` 是归约轴，出口按 flash 的方式合 |
| 几种叠加 | 嵌套的 `for`，内外层各切一个轴 |

流水的重叠不在描述里写：

* 一次跑出来的是一个 user 的执行序列
* 多个 user 由调度器按 stream 顺序沿对角线推进，这就是流水
* 在飞的 user 数由 stream 数卡住，这就是流水深度

不规则的落核由 `with` 直接承担，哪一份放哪个核是人写的：

* 不要求均匀
* 不要求一份一核
* 不要求同一个算子的各份挨在一起

## 4. 字节数与时间

* **字节数由编译器算**：形状乘以 dtype 的宽度。`DTE` 与 `SKIP` 行的量就是它
* **计算时间不由编译器算**：它是实际模型跑出来的实测值，编译器既不估算也不从形状反推，照着填进 `MC` 与 `VC` 行
* **权重当作已经在核上**：不占带宽也不占时间，搬运的字节数里只有激活

## 5. 跑这段 Python 就是编译

### 5.1 跑一遍，把发生的事记下来

张量是只有形状的符号，跑的时候记三样：

* `with` 期间的每次算子调用 → 那个核上的一条任务
* 切片 → 取哪一段
* 搬运 → 一条从哪到哪的边

跑完每个核有一串按先后排好的任务。一次跑出来的是一个 user 的执行序列。

### 5.2 补齐没写出来的搬运

扫一遍所有的边：

* 两端在同一个核上：不用管
* 两端不在同一个核上，且这条边被显式的 `send` 与 `wait` 盖住了：跳过
* 两端不在同一个核上，且没被盖住：补一条搬运

三档写法可以混用，靠的就是这一条。多份合成一份的地方按轴的性质补：并行轴补拼接，归约轴补相加。

### 5.3 生成任务表

| 记下来的东西 | 生成 |
| --- | --- |
| 矩阵类算子 | `MC` 行，带查表得到的时间 |
| 向量类算子 | `VC` 行，带查表得到的时间 |
| 一条跨核的边 | 发送侧一条 `DTE` 行，带目标核坐标与字节数 |
| 接收侧的等待 | 一条 `SKIP` 行，配一条 `SKIPSRC` 记它等谁 |
| 一次发送前的验资 | 一条 `CU` 行，配 `CREDIT` 列出这次要一起验的下游 |

`CU` 行要验哪几个下游，从机器描述里 credit 的收发关系取。

### 5.4 编译期报错

五种情况在编译时报出来，不留到仿真里变成死锁：

* `send` 的形状与对应 `wait` 的对不上
* `wait` 等的 tag 没有人发
* 显式写的合并方式与轴的性质不符，比如在并行轴上写了 `reduce_sum`
* 在 `with` 之外调用算子
* 一条边的两端形状对得上，但数据来源不是同一个

编译器的第二个产出，用来看这份描述实际排出了什么：

## 6. 设计原理

* **为什么跑一遍就算编译，而不是写一份配置让编译器去解释**
  * 配置要先声明再匹配，写完得在脑子里模拟一遍才知道切成了什么样
  * 命令式的写法里代码顺序就是执行顺序，读下来就是每个核干什么
  * 搬运的位置也只有命令式能表达：`send` 挪一行，任务表里的位置就跟着挪，声明式没有“位置”这个概念
* **为什么没有 TP、PP、EP、DP**
  * 这四个名字是常见拆法的结果，不是原语
  * 把它们写进格式就等于把常见情况固化，一种没有名字的拆法就写不出来了
* **为什么直接产出 `.bachir`，不经过 Map**
  * Map 是给人读的 JSON，一层 512 核就 338KB，92 层要 30MB
  * Map 里没有依赖关系，`map_phaser` 要从 timeline 反推屏障怎么配对
  * 编译器本来就知道依赖，直接生成比反推短
* **为什么搬运可以不写**
  * 全都要写的话，一层 MoE 光搬运就几十行，模型那两层的结构会被淹掉
  * 全都不写，通信落在哪条链路上看不出来，而这正是要研究的东西
  * 所以是可写可不写：热点手写，其余省着
