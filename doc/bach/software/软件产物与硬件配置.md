# 软件要产出与写入硬件的东西

> **文档模式：** 设计。定义详设基线所需的软件产物与写入方式；当前bundle格式独立列出，尚未修改代码。
> **文档层级：** 详细实现。它把《Bach 要开发哪些软件》里“产物与接口一览”的每一行展开到表与字段一级。
> **目的：** 给要实现这些配置的人，以及排集成顺序的人：硬件上有哪些格子必须由软件填，每个格子谁产出、落到哪个 IP 的哪个存储器、什么时候写、写错了硬件会不会告诉你。
> **范围：** 只收**提前编译好的产物**，写入时机在 boot 期与装模型时。kernel 在运行期自己写的那些寄存器（DTE 的模板寄存器、MU 与 VU 的动态参数、软件包头）不在内。

TS/DTE设计事实以原始 [TS详细设计](</home/colin/develop/perfechpitch/_refs/Task_Scheduler_详细设计文档模板.md>)、[DTE详细设计](</home/colin/develop/perfechpitch/Bach/05_五、详细设计/02_DTE DSA详细设计文档.md>) 为准。系统流程来源：《SCP 的工作流程》的 boot 与装模型两节、《Router 片上交换与归约》《TS 任务调度器》《DTE 数据搬运引擎》《执行单元与存储》，以及 `07-units/` 下各建模单元第 4 章的存储器清单。软件模块怎么划分见《Bach 要开发哪些软件》，编号的分配规则见该文的“path_id 与其他编号”。

## 全部产物一览

Bach 上电后硬件不含任何业务信息：RouterTable 的所有条目是 bypass / no-op，TS 的任务链为空，Matrix Mem 没有权重，三个 RV core 的 ITCM 未初始化。下面每一项都必须由软件填进去。

| 产物 | 谁产出 | 落到哪 | 什么时候写 |
| - | - | - | - |
| RouterTable（weights 专用的 1 条 P2P path） | 编译器 Route Lowering | Router 的 `rtab[k]`，内部多副本由硬件自己复制 | boot 解复位前 |
| RouterTable（换成业务路径） | 同上 | 同上 | 装 weights 完成、切业务模式时 |

| RouterTable（跟 Router 那份同内容） | 同上 | ReduceModule 的 `rdc_rtab` | 上面两次各跟一次，Router 回完成之后 |
| `core_bad_mask` | 编译器 | 经 bundle 由 SCP 写进 Router 的 `core_bad_mask` | boot 解复位前，Router 配置阶段最先写 |
| Credit Bypass Route | 编译器 | Router 的 `credit_bypass` | boot 解复位前 |
| VC 使能 mask 与 VC 分配方案 | Host 软件按模型部署方案 | Router 的 VC 使能寄存器 | boot 解复位前 |
| Core Mem 分区 | 软件 | Core Mem 的 `cmem_part` | boot 期，运行期不变 |
| 宏指令静态模板 | 编译器 | VU 的静态配置模板寄存器 | boot 期 |
| RV firmware（三份） | 固件开发 | 三个 RV core 的 ITCM，reset pc 位置 | boot 解复位前 |
| DTCM 静态参数 | 软件 | 三个 RV core 的 DTCM | boot 解复位前 |
| `task_chain` | 编译器 | TS 的 `task_chain` | 装模型时 |
| `datain_task` | 编译器 | TS 的 `datain_task` | 装模型时 |
| TS 全局配置项 | 软件 | TS 的 `cfg_misc` | 装模型时 |
| TS 的 `ROUTER_TABLE` | 编译器 | TS 的 `ts_route` | 装模型时 |

| 业务模式下进核那一笔的配置（`DTEIN`） | 编译器 | DTE 的进核配置：`route`、回不回 Ack、标志表的基址与一个槽位多大 | 装 weights 完成、切业务模式时 |
| 旧通信资料中的额外发送窗口 | 软件 | 与详设三方向计数的关系待统一 | 未冻结，不自动生成硬件寄存器 |
| TS方向许可初值 | STREAM_NUM配置派生 | 三方向各N份，硬件成功提交时初始化 | 业务配置生效时，不单独配置按PID计数表 |
| DTE RV core kernel | 编译器 CodeGen | DTE RV core 的 ITCM 与 DTCM | 装模型时 |
| MU RV core kernel | 编译器 CodeGen | MU RV core 的 ITCM 与 DTCM | 装模型时 |
| VU RV core kernel | 编译器 CodeGen | VU RV core 的 ITCM 与 DTCM | 装模型时 |
| `task_pc` 表 | 编译器 CodeGen | 随 kernel 镜像 | 装模型时 |
| weights 分片（每 core 27 MiB） | 编译器 CodeGen | Matrix Mem | 装模型时 |

“谁产出”一栏写“编译器”的，是源文档明写了“编译侧算好”的那几项；写“软件”的，源文档只说了由软件配，没有指明是编译期算还是别处给。

“落到哪”一栏用的是建模单元（`07-units/`）里的存储器名，它与原始 MAS 的寄存器名不是一套：TS 那几项在 TS MAS 里有地址映射（例如 `STREAM_NUM` 在 `0x208`，位域 `4:0`），Router 的配置在 DATA_NOC HAS 里走独立的 **R2CU 接口**（Core NOC 到 CTRL_NOC 的代理路径，APB / AXI-lite，32 bit）由 SCP 固件写。TS/DTE冲突以本轮详设基线为准，原文内部位域分歧等待统一。**`cmem_part` 是例外，原始文档里没有这组分区寄存器，这个名字与它的字段都是建模侧自己定的。**

**通路只有一条**：`ctrl_noc`，主是 SCP。唯一的例外是 weights，它每 core 27 MiB，经 PCIe 的 msg 流进来由 DTE 搬进 Matrix Mem。

## 写入顺序

有三处顺序是硬性的，颠倒会留下不一致的中间状态。

**Router 的三份表按先内后外**。Router 内部的多副本由它自己的更新状态机逐份写，全部写完才拉 `commit_done`；SCP拿到完成之后写ReduceModule的外部路由副本；当前代码DTE rtab_copy作为兼容适配另行核对。Router 硬件不代为同步外部副本。

**Router 配置在解复位之前**。上电顺序是：PMU 释放 core 时钟域复位，`stream_credit` 置 0，RouterTable 处于全 bypass / no-op，SCP 配表与 VC 使能，各 core 发初始化脉冲，就绪。配表完成前 Router 不投递任何包，所以初始化中途不会有包乱跑。配表时 SCP 对全 chip 每个 core 先写 `core_bad_mask`，再写 RouterTable 与 Credit Bypass Route；随后的 core 配置阶段只配好 core，等 ready 只等好 core，坏 core 的 ready 恒为真。

**TS业务配置顺序**：先写 `STREAM_NUM` 与 `SELF_START` 并读回核对；B core 与 R core 重写 `DATAIN_TASK_PC`；逐项写任务链，每项先 `TASK_CHAIN_n_PC` 再 `TASK_CHAIN_n_ATTR`（写 ATTR 时硬件置 `TASK_VALID`）；最后 `TS_INIT_FINISH` 写 1。硬件随即查整张配置表并写 `TS_STATE`，有错软件清掉 `TS_INIT_FINISH`、改链重来；成功提交只保存Task0模板，B/R core的首个已接受Trigger才激活N项，后续本地重生。

**每个 core 的初始化次序**：RV firmware 进 ITCM，解复位，TS 初始化（任务链），Router 初始化（路由表），kernel 初始化。前两步在 boot 期做，后三步在装模型时做。boot 完成时路由表里还没有业务路径，TS 也没有任务链。坏 core 只有 Router 初始化这一步。

## Router 的四项

**当前bundle的RouterTable**：64项，按`path_id`索引。Router MAS的硬件窗口为256项×64bit，采用LO／HI原子提交；TS路由属性表仍为64项。以下字段属于模型记录，不能直接作为硬件寄存器打包格式。字段含出方向掩码 `flow_dir`、本跳与下一跳的 VC 号、进不进本 core、要不要查 stream credit table、credit 类型与额度、reduce 的输入掩码与精度、`stall_way`。**同一个** **`path_id`** **在不同 core 上表项不同，因此每 core 一份，不能从拓扑反推。**

**`core_bad_mask`**：每颗 chip 10 bit，第 i 位为 1 表示 core i 是坏 core，全 chip 每个 core 都写。每个 Router 只看本 core 那一位，为 1 就进透传档：数据只按 RouterTable 转发，不投递本 core，不进 ReduceModule，不做溢流转存。

* 编译器只接受一种布局：中间两列 chip 是 `0x084`（core2、core7），第一列与最后一列是 `0x000`。
* 真机上它是上电时从 eFuse 读出并锁存的。模型没有 eFuse，由编译器写进 bundle，写入时机等同上电锁存：业务开始之前写完，之后不再变。
* 坏 core 上除 `core_bad_mask` 外只配 RouterTable 与 Credit Bypass Route，产物表里其余各项都不写。它的 RouterTable 表项一律不进 core（`path_core_bypass = 1`），`op_type` 为 transfer，`stream_table_enable` 与 `stall_way` 为 0。

**Credit Bypass Route**（`RTR_RELEASE_ROUTE`）：每个业务 credit 输入端口一个静态输出方向 `out_mask`。原始Router设计的Stream与Reduce Release均按静态路由转发，类型及来向分别保留，不查Packet RouterTable、不进数据Crossbar仲裁。当前bundle只配置模型已有的Stream通路，尚无下游Reduce Release实现。

**VC 使能 mask**：哪几个 VC 投入使用。VC3 固定给逐级 reduce，VC0 至 VC2 支持除 reduce 外的全部操作类型，由软件分配。

**Router外部副本**：ReduceModule查reduce_in_mask。当前DTE rtab_copy、path_task_map和stream_cache是旧模型适配状态，后续在TS三方向计数及DTE任务身份对齐时复核用途；详设中的最终VCID由TS命令直接传入。

## TS 的任务链与全局配置

**`task_chain`**：64 项，每项两个 32 位寄存器（PC 与 ATTR）。这是一条全序链，位域里没有前驱表也没有后继表，唯一的结构信息是数组下标。软件在编译期把操作之间的依赖关系拓扑排序，拍成这条链，链上的先后就是任务之间的全部依赖信息。

每项两个寄存器：`TASK_CHAIN_n_PC` 放 `TASK_PC`；`TASK_CHAIN_n_ATTR` 放 `TASK_SEND_UNIT`、`TASK_RECV_UNIT`、`WAIT_WAKE`、`TASK_TYPE`、`TASK_P2P_REISSUE_TID`、`TASK_CREDIT_EN`、`TASK_PATH_ID`、`TASK_END`，写 ATTR 时硬件把 `TASK_VALID` 置有效。

同一个PID可配几项搬入，TS用completion|claimed排除已经完成或被候选占用的TID，选择最低匹配项。dot core（每颗 chip 的逻辑 core7，收 chip 内 FC1/FC3 部分和的归约、广播 FC2 输入、收 concat 的那个 core）收 concat 就这样配：一个上游 core 一项，共 7 项。

**`DATAIN_TASK`**：`DATAIN_TASK_PC` 与 `DATAIN_TASK_ATTR` 两个寄存器，只能绑定 DTE；ATTR 里是 `WEIGHTS_MODE`、只读的 `TASK_SEND_UNIT` 与 `TASK_VALID`。`WEIGHTS_MODE` 置位表示处于 weights 加载阶段，此时不启动 `task_chain`。

**全局配置项**：`STREAM_NUM`（1 至 16，写超过 16 的值只写入 16）、`SELF_START`（B core 与 R core 置 1）、`TS_INIT_FINISH`。

**`ROUTER_TABLE`**：64 项，按 `path_id` 索引，每项 `TASK_DIR`（上下、左、右、本 core 四位）与 `TASK_VCID`。VCID随DTE/MU/VU命令下发；低三方向用于TS新方向许可，Local不扣计数。物理位域在原文旧表和后续说明间有分歧，编码等待统一。

**任务身份**：SID/TID/UID/PID/VCID来自Trigger请求的CSR快照；DTE完成用原描述符身份，不依赖额外path_task_map。旧path_flowctl与Router监听接口的对应关系仍待统一。

**方向许可**：三个方向各N份，用户只对尚未使用的方向申请一次，多方向同时满足。方向返回下一拍可用；用户退休不直接加回这些计数。

**逐级 reduce 的拆分**：Rmem 给一个用户 32 KiB，按 FP32 驻留最多 8192 个元素，一笔 reduce 装不下时软件按这个量拆成链上的几项逐级 reduce 任务（TASK_TYPE=4，recv_unit为Core/DSA双ACK，credit_en任意），当前R Core模型同一TS任务内提交多个操作数搬运，仅最后条目回ACK；与DTE详设任务粒度限制仍待统一。双ACK完成可推进普通后继，下一Reduce仍等该SID的RMEM归还。

## DTE 的进核配置与角色

**业务模式下进核那一笔的配置**（bundle 里的 `DTEIN`）：`route` 选落 Core Mem 还是 Matrix Mem，另有回不回 Ack、标志表的基址与一个槽位多大。weights 加载阶段进核那一笔一律落 Matrix Mem、不回 Ack，装 weights 完成、切业务模式时按下表重配。

**角色**是编译器给每个 core 分的用途，分计算 core、B core、R core、不派角色四种，坏 core 一律不派角色。硬件上没有记角色的寄存器，角色由下面几项配置体现，SCP 在 core 配置阶段逐项写：

| 配置 | 所在单元 | 计算 core | B core | R core |
| - | - | - | - | - |
| `SELF_START` | TS | 0 | 1 | 1 |
| `B_CORE_DIRECTION`（旧适配待统一） | 模型 | 0 | 广播的方向 | 0 |
| 任务链与 datain 任务 | TS | 计算 core 的任务链 | 自启动任务链与 datain 任务 | 自启动任务链与 datain 任务 |
| 业务模式下进核那一笔的 `route` | DTE | Router → Core Mem | Router → Matrix Mem | Router → Matrix Mem |
| 业务模式下进核那一笔回不回 Ack | DTE | 回 | 不回 | 不回 |
| 标志表的基址与一个槽位多大 | DTE | 不配 | token 槽位 | 行结果槽位 |

不派角色的好 core 这几项都不配，没有任务链，Router 走正常档，只转发由表项决定。

## MU 与 VU

**MU 的** **`topK_ep_table`**：16 stream × 256 B，运行时由DTE经M Top sel=1的[0]路两笔128B写入并收响应；表项的专家序号是组内序号（local index），由上游在广播前压好，MU 不再有 boot 期的 `local_ep_table`。

**VU 的宏指令模板**：8 组静态配置模板由编译侧算好，boot 期经 ctrl_noc 的 cfg 口写入。

***

## Core Mem 的分区

`cmem_part` 一组配置寄存器（这个名字与下面的字段都是建模侧定的，原始文档没有对应的寄存器组），boot 期经 ctrl_noc 写入，运行期不变：`stream_base` 与 `stream_stride`（16 个 stream 分片）、`scale_base`、`topk_base`、`header_base`、`reissue_base` 与 `reissue_pkts_per_vc`（Router 溢流重发的暂存区，每 VC 至少容得下一个整包）、`p2p_base[3]` 与 `p2p_entries[3]`（每方向一张 P2P 阻塞缓冲）。

分片数由 `STREAM_NUM` 决定，硬件按它把 Core Mem 均等切分，单用户独占空间等于总容量除以 `stream_num`。软件用统一的虚拟偏移地址读写，硬件按 `stream_id` 路由到当前用户的分片。

## 镜像类

**RV firmware**：三份，写到三个 RV core 的 ITCM 的 reset pc 位置，这个位置是固定的。解复位后 RV core 从 `boot_pc` 跑它，配 CSR、初始化 gp / sp，然后执行 WFT 指令进 wait。

**kernel 镜像**：每类 core 一个 RV32 ELF，连同 `task_pc` 表，装模型时写进 ITCM 与 DTCM。`task_chain` 里的 `TASK_PC` 指向的就是这份镜像里的地址。DTE 那一份含 datain、各搬运 task 与 weights loader，MU 与 VU 那两份含各自的计算 task，B core 与 R core 另有自己的几段。同一份镜像服务每颗 chip 的 8 个逻辑槽位，随槽位变的任务每个槽位一个入口，由任务链里的 `TASK_PC` 选。

**weights loader 是 DTE kernel 里的一段**，不是单独的固件。它把权重从 Router 搬进 Matrix Mem：weights 加载模式下 `datain_task` 的 pc 指向它，`trigger_task_chain_en = 0`。一笔权重进来的路径是 Host msg 流经 PCIe 到 Router，Router 通知 TS 触发 datain，TS 派 DTE RV core 跑这一段，它读取包头中的落点、长度和 scale 标记并配置搬运指令，DTE 把数据从 Router 搬进 Matrix Mem，加载中TS忽略正常ACK，软件确认搬运与写响应完成后再清loading并提交业务配置。当前 kernel 计数后提交无业务 ACK 的搬运并 yield；加载控制方须另行确认数据和写响应完成，再切到业务模式。

权重落点由发送方放在包头的模型软件视图中，loader 将其配置为 MM 物理地址、stride=0。一般 Route 的存储端仍按该段 SID×stride 计算，Core 内搬运的源端使用物理地址。

DTE 还要能解析 MSG 并执行，解析程序同样在这份 kernel 里，MU 与 VU 不需要。

**weights分片**：TS加载路径下发独立PC-only请求，不创建Stream。Router资料中的kernel/weight直启与该路径的关系待统一，不能将旧“绕过TS”当作当前加载合同。

## 运行期 DTE 配置与软件检查

kernel写四段SRC/DST/STRIDE/LEN、SM地址/数据和TRANS_MODE，写Trigger提交。模板8套×128B，显式写字段覆盖模板；SID/TID/UID/PID/VCID随请求保存，直到Trigger Fire快照，不能在反压期间重取CSR。

软件每次配置段0长度32，HeaderTable用组/项索引，按SID分组时stride0=32、基址加项号。配对DataIn/DataOut使用同项；中间任务用另一项Hardware Used，共享core_mask/sw_aux按最后写入值读取。包头在CM/MM中占32B，gpu/token诊断身份独立于硬件包头。

段1～3地址和长度8B对齐，内容由软件选择，不固定scale或topK段号。CM scale全局地址用bit20；topK窗口0x20000000、每项256B，按SID stride256；HeaderTable段窗口0x30000000，与软件读写0x3000域不同。每段窗口、SID乘加、边界及包长须在编译／配置检查中验证。

包长为32B头加使能数据段总和，8B对齐最大数据65496、pkt_length65528；8KB Buffer不限制Packet长度。模型产物按用户确认的TRANS_MODE布局生成：mode[2:0]、bit3保留、seg_valid[6:4]、header[7]、SM[8]、ACK[9]。TS RouterTable的方向低3位保存所需业务许可，Local位保留，VCID使用[5:4]；原文其它编码仍待统一。

DTE 复位 STOP；运行前完成必要控制初始化并 resume。RUN／STOP的16项全局队列满时反压全部RV访问。STOP在队Entry不得超过15；填满后RV无法写resume，详设规定复位恢复；ERROR 接受并丢弃 Trigger、清 dirty。SM标志仅在全部数据写响应完成后发，并等SM bresp再通知TS。B/R软件释放槽位须结合数据完成与RMEM空间条件，不能因为Core ACK已发就复用输入。

当前R Core软件将两个操作数搬运放在同一TS任务，仅最后条目开启ack_ts_en；DTE详设“软件限制”尚未允许不同任务粒度，两者需要统一。权重加载采用每加载阶段一次 Trigger，27MiB 分片如何划分加载阶段、如何确认全部搬运完成仍需统一。

## 当前代码的 bundle 记录与装载检查

编译器把一套配置写成 bundle：一份`.bachir`加三份kernel镜像。当前四套 bundle 已按 TS／DTE 建模基线生成；DTEIN和旧方向字段是兼容适配，不定义新增硬件寄存器。`.bachir` 的格式版本是 `BACHIR 10`，与坏 core、角色有关的记录有三种：

| 记录 | 字段 | 说明 |
| - | - | - |
| `CHIP` | `<chip> <core_bad_mask>` | 每颗 chip 一条 |
| `CORE` | `<chip> <core> <角色>` | 角色 0 计算、1 B core、2 R core、3 不派角色；每颗 chip 的 10 个 core 都写，坏 core 写 3。装载时只用来做检查，不写进硬件 |
| `DTEIN` | `<chip> <core> <route> <no_ack> <flag_base> <flag_entry_bytes>` | 业务模式下进核那一笔的配置：`route` 0 落 Core Mem、1 落 Matrix Mem；后两项是标志表的基址与一个槽位多大，计算 core 填 0。计算 core、B core、R core 各一条 |
| `VUSTATIC` | `<chip> <core> <vu_off> <data>` | VU 静态配置组。有 `task_vu_gate` 的 dot core 写组 1/2，有 `task_vu_add` 的 R core 写组 4/5。装载时 `Vu::Preload`，开钟前一次到位 |

装载时、写入之前先查：

* `core_bad_mask` 至多 2 位为 1，每行至多 1 位。
* 坏 core 的角色是不派角色，坏 core 上只出现 `RTAB` 与 `RELROUTE` 两种记录，`RTAB` 满足坏 core 的表项约束。
* 角色与配置对得上：
  * B core、R core 的 `SELF_START` 为 1，计算 core 为 0。
  * 只有 B core 的 `B_CORE_DIRECTION` 非 0。
  * 计算 core 的 `DTEIN` 落 Core Mem，B core、R core 落 Matrix Mem。
  * 不派角色的 core 没有 CFGMISC、TCHAIN、DATAIN、DTEIN、VUSTATIC。

## 硬件不检查，软件自己保证的

这一节列的是配错了硬件不会报错的地方。

| 要保证什么 | 硬件的行为 |
| - | - |
| 三份 RouterTable 内容一致 | Router 只同步自己内部的副本，DTE 与 ReduceModule 那两份不管 |
| Core Mem 各分区互不重叠 | 存储只按物理地址读写，不检查请求落在哪个分区，写 `TS_INIT_FINISH` 那一步也不查这组寄存器 |
| Matrix Mem地址／stride正确 | 一般存储端按该段SID×stride；软件配置stride0才为物理地址，Core内源不叠stride |
| 任务链在编译期拓扑排序成全序链 | 位域里没有依赖信息，硬件只按下标顺序走 |
| 当前模型一个TS任务内的DTE搬运条目数及依赖有界 | 当前R Core各操作数分别占全局Entry，最后条目回ACK；该模型做法与原文任务粒度限制待统一。STOP在队Entry不超过15，避免队满使RV恢复命令无法接收 |
| 有冲突的 VU 宏指令之间置 `MACRO_INST_FENCE` | VU-DSA 不追踪 Core Mem 访存的数据冲突 |
| VU 的 RF 后门通路访问期间目标 RF 不被在飞宏指令读写 | 该通路与宏指令异步 |
| VRF 的读写寄存器完全重叠或完全不重叠 | 不允许部分重叠，硬件不检查 |
| `path_core_mask` 位数不够时换一个新的 `path_id` | 溢出硬件不报 |
| 多个上游按同一个用户顺序申请同一份下游资源 | 各上游各自维护自己那份 credit，没有集中仲裁 |
| B core 的 chain 里不再配 DTE 的 datain 任务 | 会影响那条一直收数据的 `datain_task` |
| B core落点／计数／tail一致 | 接收kernel计算DST并配置DTE，硬件按描述符搬运和SM快照写标志；包头不直接创建搬运描述符 |
| 送进 B core 那一条与 B core 广播出去那一条各用一个 `path_id` | 坐在进口上的那个 core 要把包往 B core 转，在广播树上它又要往下一跳转，同一个 `path_id` 在它的路由表里只配得出一种转法 |
| datain 任务的完成 flag 由软件设置维护 | TS 不更新它 |
| weights 加载阶段发方发几笔、收方数几笔两边说好 | loader 的计数记在 Share Mem 上，是软件自己数的；硬件按接收kernel配置的DST/STRIDE搬进Matrix Mem并返回写响应 |

## 待定

* **超前发送窗口配在哪张表**：使能位与窗口尺寸 `N` 都是软件按 path 配、编译期确定，但原文只写“在一个 Core 配置了流量控制使能”，没指明是 TS 还是 RouterTable。本套文档按配在 TS 的 `path_flowctl` 建模，因为判断要读 `stream_table` 里正在计算的 `user_id`，这个信息只有 TS 有。
* **完成信息由谁发起**：Router 硬件解析包头发起，还是软件调用 RV core 发起；软件要配置哪个 Bach core 返回完成信息，两者都未定。
* **trace 与 PMU 计数走哪条路**：独立 noc 通道还是复用 ctrl_noc，未定。
* **Core Mem 的分区怎么配**：原始文档只定了 `STREAM_NUM`（TS详设0x208），没有定义分区基址那一组寄存器。Cmem MAS 给的是容量（1 MB + 32 KB，8 bank）、四条通路的带宽（DTE 256 B/T、MU 与 VU 各 128+4 B/T、ctrl_noc 4 B/T）、仲裁优先级与各单元读写延迟，Signal List 与寄存器映射两节都是空的。本表里的 `cmem_part` 是建模侧补出来的，字段名与位宽都要等硬件给。

## 取舍

**为什么配置只走 ctrl_noc 一条路**：配置量小、时机集中在 boot 与装模型两段，与业务数据面完全错开，共用一条通路省掉一整套仲裁。weights 之所以是例外，是因为它的量走控制通路会把 launch 时间拖到不可接受。

**为什么 Router 的表不从拓扑反推**：同一个 `path_id` 在不同 core 上的表项不同，而且 chip 所在的列决定它的坏 core 与角色：中间两列 chip 的 core2、core7 是坏 core，第一列组头 chip 有 B core，最后一列 chip 有 R core，逻辑上相邻的两个计算 core 物理上可能隔着坏 core。让编译侧逐 core 算好写进去，硬件就不需要知道自己在阵列里的位置。

**为什么身份字段不由软件写**：这几个值本来就在本核 RV core 的 CSR 里。RV 执行 `dsaw` 的那一拍把 `streamID`、`taskID`、`userID`、`pathID`、`vcid` 抄进这笔配置请求，跟着写穿过下发队列。DTE、MU、VU 收下 trigger 时用请求上的这一份，软件不必再写进 DSA 寄存器。配置通路把 trigger 挡住时，已经发出的那笔仍带着发出时的身份，下一笔 task 换了 CSR 也不会串。
