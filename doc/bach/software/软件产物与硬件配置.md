# 软件要产出与写入硬件的东西

> **文档模式：** 设计。陈述当前的产物划分与写入方式，待定项集中在文末。
> **文档层级：** 详细实现。它把《Bach 要开发哪些软件》里“产物与接口一览”的每一行展开到表与字段一级。
> **目的：** 给要实现这些配置的人，以及排集成顺序的人：硬件上有哪些格子必须由软件填，每个格子谁产出、落到哪个 IP 的哪个存储器、什么时候写、写错了硬件会不会告诉你。
> **范围：** 只收**提前编译好的产物**，写入时机在 boot 期与装模型时。kernel 在运行期自己写的那些寄存器（DTE 的模板寄存器、MU 与 VU 的动态参数、软件包头）不在内。

来源：《SCP 的工作流程》的 boot 与装模型两节、《Router 片上交换与归约》《TS 任务调度器》《DTE 数据搬运引擎》《执行单元与存储》，以及 `07-units/` 下各建模单元第 4 章的存储器清单。软件模块怎么划分见《Bach 要开发哪些软件》，编号的分配规则见该文的“path_id 与其他编号”。

***

## 全部产物一览

Bach 上电后硬件不含任何业务信息：RouterTable 的所有条目是 bypass / no-op，TS 的任务链为空，Matrix Mem 没有权重，三个 RV core 的 ITCM 未初始化。下面每一项都必须由软件填进去。

| 产物 | 谁产出 | 落到哪 | 什么时候写 |
| - | - | - | - |
| RouterTable（weights 专用的 1 条 P2P path） | 编译器 Route Lowering | Router 的 `rtab[k]`，内部多副本由硬件自己复制 | boot 解复位前 |
| RouterTable（换成业务路径） | 同上 | 同上 | 装 weights 完成、切业务模式时 |
| RouterTable（跟 Router 那份同内容） | 同上 | DTE 的 `rtab_copy` | 上面两次各跟一次，Router 回完成之后 |
| RouterTable（跟 Router 那份同内容） | 同上 | ReduceModule 的 `rdc_rtab` | 上面两次各跟一次，Router 回完成之后 |
| Skip Mask | 编译器 | Router 的 `skip_mask` | boot 解复位前 |
| Credit Bypass Route | 编译器 | Router 的 `credit_bypass` | boot 解复位前 |
| VC 使能 mask 与 VC 分配方案 | Host 软件按模型部署方案 | Router 的 VC 使能寄存器 | boot 解复位前 |
| Core Mem 分区 | 软件 | Core Mem 的 `cmem_part` | boot 期，运行期不变 |
| EP Group 内的专家表 | 编译器 | MU 的 `local_ep_table` | boot 期 |
| 宏指令静态模板 | 编译器 | VU 的静态配置模板寄存器 | boot 期 |
| RV firmware（三份） | 固件开发 | 三个 RV core 的 ITCM，reset pc 位置 | boot 解复位前 |
| DTCM 静态参数 | 软件 | 三个 RV core 的 DTCM | boot 解复位前 |
| `task_chain` | 编译器 | TS 的 `task_chain` | 装模型时 |
| `datain_task` | 编译器 | TS 的 `datain_task` | 装模型时 |
| TS 全局配置项 | 软件 | TS 的 `cfg_misc` | 装模型时 |
| 软件侧任务属性 | 编译器 | TS 的 `sw_attr` | 装模型时 |
| `path_id` 到 `task_id` 的映射 | 软件 | TS 的 `path_task_map` | 装模型时 |
| 超前发送窗口 | 软件 | TS 的 `path_flowctl` | 装模型时 |
| `CreditCounter` 初值 | 编译器 | TS 的 `credit_cnt` | 装模型时 |
| DTE RV core kernel | 编译器 CodeGen | DTE RV core 的 ITCM 与 DTCM | 装模型时 |
| MU RV core kernel | 编译器 CodeGen | MU RV core 的 ITCM 与 DTCM | 装模型时 |
| VU RV core kernel | 编译器 CodeGen | VU RV core 的 ITCM 与 DTCM | 装模型时 |
| `task_pc` 表 | 编译器 CodeGen | 随 kernel 镜像 | 装模型时 |
| weights 分片（每 core 27 MiB） | 编译器 CodeGen | Matrix Mem | 装模型时 |

“谁产出”一栏写“编译器”的，是源文档明写了“编译侧算好”的那几项；写“软件”的，源文档只说了由软件配，没有指明是编译期算还是别处给。

“落到哪”一栏用的是建模单元（`07-units/`）里的存储器名，它与原始 MAS 的寄存器名不是一套：TS 那几项在 TS MAS 里有地址映射（例如 `STREAM_NUM` 在 `0x328`，位域 `3:0`），Router 的配置在 DATA_NOC HAS 里走独立的 **R2CU 接口**（Core NOC 到 CTRL_NOC 的代理路径，APB / AXI-lite，32 bit）由 SCP 固件写。两处名字对不上时以原始 MAS 为准。**`cmem_part` 是例外，原始文档里没有这组分区寄存器，这个名字与它的字段都是建模侧自己定的。**

**通路只有一条**：`ctrl_noc`，主是 SCP。唯一的例外是 weights，它每 core 27 MiB，经 PCIe 的 msg 流进来由 DTE 搬进 Matrix Mem。

## 写入顺序

有三处顺序是硬性的，颠倒会留下不一致的中间状态。

**Router 的三份表按先内后外**。Router 内部的多副本由它自己的更新状态机逐份写，全部写完才拉 `commit_done`；SCP 拿到完成之后才能写 DTE 与 ReduceModule 各自的那一份。Router 硬件不代为同步外部副本。

**Router 配置在解复位之前**。上电顺序是：PMU 释放 core 时钟域复位，`stream_credit` 置 0，RouterTable 处于全 bypass / no-op，SCP 配表与 VC 使能，各 core 发初始化脉冲，就绪。配表完成前 Router 不投递任何包，所以初始化中途不会有包乱跑。

**TS 的配置按四步写**：全局项 `CORE_TYPE`、`STREAM_NUM`、`B_CORE_DIRECTION`，再逐项 `task_chain[i]`（硬件自动置 `TASK_VALID`），再 `DATAIN_TASK`，最后 `TS_INIT_FINISH`。写完最后一项硬件随即查五项合规性并写 `TS_STATE`，B core 与 R core 自启动 16 项。

**每个 core 的初始化次序**：RV firmware 进 ITCM，解复位，TS 初始化（任务链），Router 初始化（路由表），kernel 初始化。前两步在 boot 期做，后三步在装模型时做。boot 完成时路由表里还没有业务路径，TS 也没有任务链。

***

## Router 的四项

**RouterTable**：64 项，按 `path_id` 索引。字段含出方向掩码 `flow_dir`、本跳与下一跳的 VC 号、进不进本 core、要不要查 stream credit table、credit 类型与额度、reduce 的输入掩码与精度、`stall_way`。**同一个** **`path_id`** **在不同 core 上表项不同，因此每 core 一份，不能从拓扑反推。**

**Skip Mask**：每 chip 一份，per-core 一位，标记该 core 是否被跳过。位宽按 5 列 chip 的 10 个 core 定，4 列 chip 只用低 8 位。不派角色的 core 也要写这一项。

**Credit Bypass Route**：每个业务 credit 输入端口一个静态输出方向 `out_mask`。Stream 与 Reduce 两类 release 按它转发，不查 RouterTable，也不进 CrossBar 仲裁。

**VC 使能 mask**：哪几个 VC 投入使用。VC3 固定给逐级 reduce，VC0 至 VC2 支持除 reduce 外的全部操作类型，由软件分配。

**两份外部副本的用途**：DTE 的 `rtab_copy` 用来按 `path_id` 查本跳的 VC 号与资源需求；ReduceModule 的 `rdc_rtab` 用来查 `reduce_in_mask`，也就是这条 path 在本级会有哪几个方向送来分量。

***

## TS 的任务链与全局配置

**`task_chain`**：64 项，每项 64 bit。这是一条全序链，位域里没有前驱表也没有后继表，唯一的结构信息是数组下标。软件在编译期把操作之间的依赖关系拓扑排序，拍成这条链，链上的先后就是任务之间的全部依赖信息。

每项要填的位域：`TASK_PC`、`TASK_UNIT`、`TASK_RECV_UNIT`、`SELF_START`、`WAIT_WAKE`、`TASK_Broadcast_REISSUE`、`TASK_P2P_REISSUE`、`TASK_REDUCE`、`TASK_CREDIT_EN`、`TASK_EXE_MASK`、`TASK_PATH_ID`、`TASK_END`，最后写 `TASK_VALID` 由硬件置有效。

**`DATAIN_TASK`**：独立的一项寄存器，只能绑定 DTE，四个字段是 `TASK_PC`、`TASK_UNIT`、`WEIGHTS_MODE`、`TASK_VALID`。`WEIGHTS_MODE` 置位表示处于 weights 加载阶段，此时不启动 `task_chain`。

**全局配置项**：`STREAM_NUM`（1 至 16）、`CORE_TYPE`（B core / R core / 普通 core）、`B_CORE_DIRECTION`（B core 的广播方向，TS 按它查下游 credit）、`TS_INIT_FINISH`。

**`sw_attr`**：64 项，装的是硬件位域里没有的软件侧属性：`exe_dest`、`reduce_num`、`dsa_en`。

**按** **`path_id`** **索引的两张表**：`path_task_map` 给出这条 path 对应哪一笔 `task_id`；`path_flowctl` 给出超前发送窗口的 `flowctl_en` 与 `window_n`。

**`CreditCounter[path_id][stream_id]`** **初值**：广播任务等于目的 core 数量，P2P 任务是 1。这个初值每 core 一份。

**逐级 reduce 的** **`reduce_num`**：配置任务为逐级 reduce 时同时配它，取值受 Rmem 容量约束。Rmem 给一个用户只留 16 KB，而单用户一笔 reduce 是 32 KB，所以软件要把一笔拆成 4 笔 8 KB，`reduce_num` 就是这个拆分数。

***

## MU 与 VU

**MU 的** **`local_ep_table`**：当前 EP Group 内的专家与组内序号，编译侧算好，boot 期经 ctrl_noc 写入。

**VU 的宏指令模板**：8 组静态配置模板由编译侧算好，boot 期经 ctrl_noc 的 cfg 口写入。

***

## Core Mem 的分区

`cmem_part` 一组配置寄存器（这个名字与下面的字段都是建模侧定的，原始文档没有对应的寄存器组），boot 期经 ctrl_noc 写入，运行期不变：`stream_base` 与 `stream_stride`（16 个 stream 分片）、`scale_base`、`topk_base`、`header_base`、`reissue_base` 与 `reissue_pkts_per_vc`（Router 溢流重发的暂存区，每 VC 至少容得下一个整包）、`p2p_base[3]` 与 `p2p_entries[3]`（每方向一张 P2P 阻塞缓冲）。

分片数由 `STREAM_NUM` 决定，硬件按它把 Core Mem 均等切分，单用户独占空间等于总容量除以 `stream_num`。软件用统一的虚拟偏移地址读写，硬件按 `stream_id` 路由到当前用户的分片。

***

## 镜像类

**RV firmware**：三份，写到三个 RV core 的 ITCM 的 reset pc 位置，这个位置是固定的。解复位后 RV core 从 `boot_pc` 跑它，配 CSR、初始化 gp / sp，然后执行 WFT 指令进 wait。

**kernel 镜像**：每类 core 一个 RV32 ELF，连同 `task_pc` 表，装模型时写进 ITCM 与 DTCM。`task_chain` 里的 `TASK_PC` 指向的就是这份镜像里的地址。DTE 那一份含 datain、各搬运 task 与 weights loader，MU 与 VU 那两份含各自的计算 task，B core 与 R core 另有自己的几段。

**weights loader 是 DTE kernel 里的一段**，不是单独的固件。它把权重从 Router 搬进 Matrix Mem：weights 加载模式下 `datain_task` 的 pc 指向它，`trigger_task_chain_en = 0`。一笔权重进来的路径是 Host msg 流经 PCIe 到 Router，Router 通知 TS 触发 datain，TS 派 DTE RV core 跑这一段，它算出 Matrix Mem 的落地址并发搬运指令，DTE 把数据从 Router 搬进 Matrix Mem，**完成后通知 TS 释放，不触发任务链**。它自己计数，数满了用自定义指令中断 SCP，SCP 据此把三处配置切到业务模式。

落地址只能由它算：Matrix Mem 一侧硬件不叠 `stream_id × stride`，而每个 core 的权重分片不同、落在哪几个 core 由 msg 里的标记定。

DTE 还要能解析 MSG 并执行，解析程序同样在这份 kernel 里，MU 与 VU 不需要。

**weights 分片**：`op_type = 0` 的 weights 包进 core 时跳过 TS 直接唤醒 DTE，不占 stream 表项。

## 硬件不检查，软件自己保证的

这一节列的是配错了硬件不会报错的地方。

| 要保证什么 | 硬件的行为 |
| - | - |
| 三份 RouterTable 内容一致 | Router 只同步自己内部的副本，DTE 与 ReduceModule 那两份不管 |
| Core Mem 各分区互不重叠 | 存储只按物理地址读写，不检查请求落在哪个分区，写 `TS_INIT_FINISH` 那一步也不查这组寄存器 |
| Matrix Mem 的地址算准 | 硬件不叠 `stream_id × stride`，配进去多少就是多少 |
| 任务链在编译期拓扑排序成全序链 | 位域里没有依赖信息，硬件只按下标顺序走 |
| TS 下发的任务足够小，到 DTE 之后不用 RV core 再拆 | 一个大任务拆出的小任务数量不确定，可能填满 TaskQueue，把后面那笔释放下游资源的任务堵在外面 |
| 有冲突的 VU 宏指令之间置 `MACRO_INST_FENCE` | VU-DSA 不追踪 Core Mem 访存的数据冲突 |
| VU 的 RF 后门通路访问期间目标 RF 不被在飞宏指令读写 | 该通路与宏指令异步 |
| VRF 的读写寄存器完全重叠或完全不重叠 | 不允许部分重叠，硬件不检查 |
| `path_core_mask` 位数不够时换一个新的 `path_id` | 溢出硬件不报 |
| 多个上游按同一个用户顺序申请同一份下游资源 | 各上游各自维护自己那份 credit，没有集中仲裁 |
| B core 的 chain 里不再配 DTE 的 datain 任务 | 会影响那条一直收数据的 `datain_task` |
| datain 任务的完成 flag 由软件设置维护 | TS 不更新它 |

## 待定

* **超前发送窗口配在哪张表**：使能位与窗口尺寸 `N` 都是软件按 path 配、编译期确定，但原文只写“在一个 Core 配置了流量控制使能”，没指明是 TS 还是 RouterTable。本套文档按配在 TS 的 `path_flowctl` 建模，因为判断要读 `stream_table` 里正在计算的 `user_id`，这个信息只有 TS 有。
* **concat 的 task 配 1 个还是多个**：若配 1 个，需要在任务链里指明 `exe_num`。
* **完成信息由谁发起**：Router 硬件解析包头发起，还是软件调用 RV core 发起；软件要配置哪个 Bach core 返回完成信息，两者都未定。
* **trace 与 PMU 计数走哪条路**：独立 noc 通道还是复用 ctrl_noc，未定。
* **Core Mem 的分区怎么配**：原始文档只定了 `STREAM_NUM`（TS MAS `0x328`），没有定义分区基址那一组寄存器。Cmem MAS 给的是容量（1 MB + 32 KB，8 bank）、四条通路的带宽（DTE 256 B/T、MU 与 VU 各 128+4 B/T、ctrl_noc 4 B/T）、仲裁优先级与各单元读写延迟，Signal List 与寄存器映射两节都是空的。本表里的 `cmem_part` 是建模侧补出来的，字段名与位宽都要等硬件给。

## 取舍

**为什么配置只走 ctrl_noc 一条路**：配置量小、时机集中在 boot 与装模型两段，与业务数据面完全错开，共用一条通路省掉一整套仲裁。weights 之所以是例外，是因为它的量走控制通路会把 launch 时间拖到不可接受。

**为什么 Router 的表不从拓扑反推**：同一个 `path_id` 在不同 core 上的表项不同，而且 chip 有三种形状（中间列 2×4，两侧 2×5），harvest 之后每颗 chip 的可用 core 还不一样。让编译侧逐 core 算好写进去，硬件就不需要知道自己在阵列里的位置。

**为什么身份字段只有 MU 由软件写**：TS 到每个 DSA 都拉一组线，线要多铺两跳，而这几个值本来就在本核 RV core 的 CSR 里。DTE 与 VU 就从那里接一条 `dsa_ids` 直连过去，写 Trigger 那一拍采样，软件一个字都不用写；MU 没有这条线，只能由软件从 CSR 读出来再写进它的动态配置寄存器。
