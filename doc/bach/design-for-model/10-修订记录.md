## TS 按现版 MAS 重写，搬入任务按 PID 找，reduce 拆成链上几项

**改动日期**：2026-09-10

**改前**：TS 的配置按 TS LLD 的旧位域：链上每项带 `self_start`、`TASK_EXE_MASK`、`TASK_DSA_EN` 与 `B_reissue`、`P2P_reissue`、`task_reduce_iss` 三个类型位，全局 `CORE_TYPE` 分普通 core、B core、R core。trigger 带 `compute` 位，TS 按 `TASK_EXE_MASK` 跳过这个用户不做的计算任务，找后继用 `SKIP_MASK`。逐级 reduce 在链上只占一项，TS 逐笔下发 N 笔，命令带第几笔（`reduce_seq`）与共几笔（`reduce_num`），完成拆成 DTE ack 与 Router Done 两半逐笔配对。重发的任务不在主线链上，在 DTE_Arb 里优先级最高。出核的 VC 由 DTE 按 `path_id` 挑。

**改后**：TS 的配置按 TS MAS 寄存器表。链上每项是 `TASK_CHAIN_n_PC` 与 `TASK_CHAIN_n_ATTR` 两个寄存器：`TASK_TYPE` 六档取代三个类型位；`TASK_RECV_UNIT` 取 00（只收 RV core 的完成）或 01（RV core 与 DSA 两路都到才算完成）；`TASK_P2P_REISSUE_TID` 指向配对的搬出。全局 `SELF_START` 取代 `CORE_TYPE`，另有按 PID 索引的 64 项 `ROUTER_TABLE`，VCID 从这里取、随 DTE 任务下发。trigger 只带 `user_id`、`path_id`、`reissue`。TS 在 `WAIT_WAKE = 1` 的项里按 PID 找这个用户还没做完的最低一项，按它的类型与 `reissue` 当场把要跳过的项并进完成位图；找后继只看这一张位图，第 0 项到 End 的完成位全齐才退休。一笔 reduce 装不下 Rmem 时在链上拆成几项 `TASK_TYPE = 4`，一项一包，完成只认 Router 的 Reduce Done（按 `user_id` 找 stream），本级 Rmem 的 credit 由 TS 按用户记一位 `rmem_busy`。重发的搬出在主线链上，与其他任务一样按年龄仲裁。自启动模式写完配置就建满 `STREAM_NUM` 个表项。RV core 的 PID CSR 可读写，PID 更新任务把新 PID 写进去，随完成带回 TS。

**依据**：TS MAS《06_Task Scheduler（编写ing）》的寄存器表、功能清单、Programming Sequence 与配置检查；TS LLD 的 Task LUT、User Match、Task Generator、完成合流与退休几节。两份不一致的地方按哪一份、模型另作的取舍，记在第 8 章的口径冲突与 TS 待定项里。

**对软件的影响**：

* 产物格式升到 `BACHIR 8`：`TCHAIN` 每项的字段改为 `<pc> <unit> <recv> <wait_wake> <task_type> <p2p_reissue_tid> <credit_en> <path_id> <end>`；`CFGMISC` 的第二个字段是全局 `SELF_START`；新增 `TSRTAB` 记录，每个 PID 一条，带 `TASK_DIR` 与 `TASK_VCID`
* 链上的搬入任务标 `WAIT_WAKE = 1`，`TASK_PATH_ID` 配成数据进来那条 path
* 一笔 reduce 在链上拆成几项逐级 reduce 任务，各有各的 PC；kernel 不再读第几笔、共几笔
* PID 更新任务的 kernel 写 PID CSR（模型里在 `0x18`）带回新 PID
* 包头的软件 payload 里不再有 `compute` 位

## Rmem 分区用时才分配，结果按 flit 流出

**改动日期**：2026-09-10

**改前**：ReduceModule 的 16 个用户上下文在用户建 stream credit 表项时预先占用，与 stream 表一一对应；Retire 后本地上下文与下游映射一起等 release 回来才删。结果要等全部方向的整包到齐才进输出队列（深 8），入队后就放开上下文。Xbar 的一个出口在包中间断拍时，别的入口能在同一个 VC 上插进来。模型里 DTE 出核把包的首拍标志打在末拍上，ReduceModule 又在带首拍标志的那一拍读整包累加，两处错位碰巧得到对的结果。

**改后**：分区在用户第一笔 Reduce 任务真正进来时分配，后面的任务接着用；16 个分区都占着时对新用户的输入反压。User Retire 时当场放本地分区，这个用户还有在做的任务就等结果交付完再放；下游 Reduce 资源映射与本地分区分开记，等在途任务的 release 回来才清。累加按 flit 做，每个 flit 只动它带来的那一段元素。某个结果 flit 的操作数都加完就发，不等整包；一个包发出首 flit 后锁定到尾 flit，后面的结果没好就占着输出等；上下文保护延到结果全部发出为止；输出队列深度这一参数去掉。Xbar 上同一出口同一 VC 被一个包从首 flit 占到尾 flit。DTE 出核的首拍标志改标在首拍上。Task Done 按任务报一次：模型里一笔任务就是一个 `reduce_seq` 的包，这一条本来就一致。

**依据**：Router MAS F-029、F-030、F-034、F-037，ReduceMemory 一节的“用户分配、任务执行与容量保护”“整包输入输出与结果流水”“Task Done、User Retire 与下游映射清理”。

**对软件的影响**：无。

## 本级 Rmem credit 由 TS 按用户记，reduce 的 N 笔逐笔下发

**改动日期**：2026-09-10

**改前**：reduce 任务生成后直接置 READY，一次下发给 DTE RV core，kernel 在这一笔里连发 N 包。TS 不记本级 Rmem 的 credit，本级那一段只靠 ReduceModule 的输入反压兜着。`reduce_seq` 由 DTE 在收下任务时按 stream 自己数。派生文档写 TS 经 `router2ts_credit_ch` 向 Rmem 申请本级 credit，N 笔之间不要求前一笔完成；Rmem 单用户容量仍有几处写 16 KB。

**改后**：本级 Rmem 的 credit 由 TS 为每个用户记一份，不向 Router 申请。reduce 任务生成后置 WAIT，这个用户的 credit 在、还有没发的笔就置 READY。DTE 发射通路一次只下发一笔，命令里带这是第几笔（`reduce_seq`）与共几笔（`reduce_num`），RV core 收下时占掉 credit、已发笔数加一。Router 的 Reduce Done 还 credit，还有没发的笔就把这一步退回 WAIT。kernel 从两个只读自定义 CSR 读出这两项，只发第 `reduce_seq` 包；DTE 从 `dsa_ids` 采到 `reduce_seq` 打进包头。逐级 reduce 那一步置 `TASK_CREDIT_EN`，TS 向 Router 要 credit 的那一路跳过 reduce 任务。Rmem 单用户容量统一为 32 KiB。

**依据**：TS MAS 逐级 reduce 那一段与配置示例表，逐级 reduce 一行 `credit_en = 1`、`reduce_iss = 1`；Router MAS 引的 HRD-TS-018：“维护Rmem的credit资源，每个用户只有1个credit资源。TS发射reduce 任务后，credit清零，等到Tmem完成reduce，通知TS，对credit恢复。”以及 HRD-TS-019、F-030、F-034、F-044。

**对软件的影响**：逐级 reduce 那一步置 `TASK_CREDIT_EN`。kernel 读 `reduce_num` 判断这一次是不是逐笔下发，是就只发第 `reduce_seq` 包。

## Reduce credit 按用户按任务准入，本级由 TS 申请

**改动日期**：2026-09-10

**改前**：Reduce credit 按 flit 记，分两段。DTE 持本级 ReduceModule 的计数，每用户一个 entry，发 Reduce 包前要求够整包；ReduceModule 按 UserID 加方向逐 flit 扣下游 credit，下游每发出一个 flit 还一个 release。用户退休后，等 credit 恢复到分配数量才删映射。

**改后**：下游 Reduce credit 以 UserID、目标方向、Reduce 任务为粒度。表项 `reduceNeedMask` 置位时，一笔任务头一次向某个方向提交前取得那个方向这个用户的准入，这笔任务后面的 Packet 与 flit 复用这次准入；下游做完这笔任务、结果全部交付后发一次携带 UserID 的 release，经 `RTR_RELEASE_ROUTE` 静态路由回到上游。本级那一段由 TS 在下发 reduce 任务前经 `router2ts_credit_ch` 向 Rmem 申请，DTE 只查 VC credit。逐 flit 那一层归 VC credit 管。用户退休后，等相邻下游各方向在途任务的 release 都回来才删映射。

**依据**：Router MAS F-018～F-020、F-032、F-033 与“Reduce Credit 与传输 Credit”一节；TS MAS 逐级 reduce 那一段：“TS 发现是 reduce task，顺序连续下发 N 笔 credit 请求，一旦 credit 请求满足，可以直接顺序下发，直到收全 N 笔 Rmem（reduce）finish”。DATA_NOC HAS 写的“reduce 与 reduce 之间按照 flit+user 的粒度”与之冲突，第 8 章已定按 MAS。

**对软件的影响**：链尾那一跳的下游不做归约，表项 `reduceNeedMask` 填 0。每一跳朝下游的那个口要在 `RTR_RELEASE_ROUTE` 里配交给本级的位，纯透传的口配原路转回的方向。编译侧产物的版本升到 `BACHIR 7`：RTAB 末尾加 `rdc_need` 一列，新增 `RELROUTE` 记录。

## ReduceModule 上下文每用户 32 KiB，按 FP32 驻留算

**改动日期**：2026-09-10

**改前**：16 用户 × 16 KiB = 256 KB，每用户固定 16 KiB，存 FP32 中间累加结果。

**改后**：16 用户 × 32 KiB = 512 KiB。容量按 FP32 驻留数据量算，一个分区最多 8192 个 FP32，相当于 16 KiB 的 BF16 输入。分区在用户首笔 Reduce 任务进入时分配，后续任务复用，收到 Retire 回收。

**依据**：Router MAS F-044 与 ReduceMemory 一节：“容量统一按 FP32 驻留数据量计算。一个 32 KiB 分区最多保存 8192 个 FP32 元素，对应 16 KiB 的 BF16 输入数据”。《TS_通信机制》写的每用户 16 KiB 与按 BF16 输入量折算的数一致。

**对软件的影响**：一笔 reduce 按 FP32 驻留量不超过 32 KiB 来拆，笔数配成 `reduce_num`。kernel 里 FC2 的结果按 8 KB 一笔拆成 3 笔，`reduce_num = 3`。

## 用户号由两个改为一个

**改动日期**：2026-09-09

**改前**：用户号分成两个。`user_id` 16 bit，是 Router 与 credit 记账认的全局编号，建表时从 Router 请求里取；`local_user_id` 12 bit，是 core 内部软件自己编的号，只用于 R core 的用户映射表与 Matrix Mem 地址计算。两者互不相干，不存在换算关系，硬件不做任何转换。自启动的 B core 与 R core 上，软件认出用户后写回的那个值补进 `local_user_id`。

**改后**：只有 `user_id` 一个。RV core 的自定义 CSR 三个，`stream_id` 与 `task_id` 只读，`user_id` 可读写；它有两条写入路径，写的是同一个字段：普通计算 core 上 TS 下发 task 时硬件写入，B core 与 R core 上 TS 下发时还没有用户身份，软件在 `flag_check` 认出之后自己写，随 `task_done` 经 `rv_done` 回 TS 更新表项。软件读它算 R core 的用户映射表与 Matrix Mem 地址，Router 与 credit 记账认的也是它。

**依据**：RV Core MAS 的“自定义 CSR 寄存器”一节只列三个寄存器，`user_id` 那一条的原文是“用户在 HBU 流控范围内的 local user_id，有效位宽暂定为 12bit，可读写，传统业务流下由 TS 的 task 开始执行时从 task_queue 硬件写入 CSR（可以不写入），R-core 执行 flag_check 对应的 task 时，由软件 check 到 flag 对应的用户 user_id 后通过 CSR 写指令写入”，即同一个 CSR 的两条写入路径。同文档“task 完成通道”一节把回给 TS 的那一项叫 `local_user_id`，是同一个东西的另一个叫法。Task Scheduler MAS 的 stream_table 表项内容清单里也只有一个 `user_id`，自启动那一路写的是“等该自启动任务 (rv core) 返回 user_id 更新 stream_table”。

**为什么会发现**：B core 的搬出任务开 `TASK_CREDIT_EN` 之后，连着送进来的三笔 token 只发得出一笔。TS 向 Router 申请资源时带的是表项的 `user_id`，自启动这一路它一直是 0，Router 按“同一笔连着两拍出现在端口上”去重时就把三笔当成了一笔。

**对软件的影响**：kernel 的 `set_local_user_id()` 改名 `set_user_id()`，写的 MMIO 口从 `TC_LOCAL_USER_ID` 改成 `TC_USER_ID`；`local_user_id()` 并进 `user_id()`。R core 的 `task_rc_find` 与 B core 的 `task_bc_wait` 认出用户后调的是新名字，`task_dte_rc_send` 算落点读的也是 `user_id()`。

## DTE 中间 Buffer 的 8 KB 是每条通道一份

**改动日期**：2026-09-09

**改前**：inbound buffer 与 outbound buffer 合计约 8 KB，各 4 KB，按 256 B 一项算各 16 项。

**改后**：每条通道一份 8 KB，按 256 B 一项算 32 项。DTE 有五条物理数据通道（一条进核、四条出核），各一份。

**依据**：DTE MAS 的“主要参数介绍”表把 `Channel Buffer 8KB` 与 `物理数据 Channel 5`、`TaskQueue 16` 并列，一行一项，说的是每条通道的量；性能一节写“Ch 内 buffer：容量 8KB，最大可掩盖 32T latency”，32 拍乘 256 B 正好 8 KB。模型的一个 Lane 就是 MAS 的一条 Channel，里面含读写两侧，与“物理 Lane 10，每一个 Channel 存在两个 Lane”对得上。

## CFG_DATA_LEN 按 8 B 一格

**改动日期**：2026-09-09

**改前**：文档没写这个寄存器的粒度，模型与 kernel 都按字节数配，两边自洽。

**改后**：`CFG_DATA_LEN` 是 16 bit，写进去的数以 8 B 为一格，硬件乘回字节，所以一段最长 64 KB 差 8 B，不足一格的尾巴配不出来。

**依据**：DTE MAS 的寄存器表里 `CFG_DATA_LEN0` 到 `CFG_DATA_LEN3` 四条的描述都是“段 N 有效传输长度，16 bit，粒度 8B”。

**对软件的影响**：kernel 的 `dte_move()` 写这个寄存器时除 `DTE_DATA_LEN_GRAIN`（8），传进去的字节数必须是 8 的倍数。现有的几处搬运长度都满足：token 512 B、FC1 与激活各 128 B、出核 reduce 包 24592 B、R core 一个槽 49664 B。

| - | - | - |

| `src/bach/ip/chip/core/dte/regfile.h` | 写寄存器与生成描述符两处 | 写入时检查 16 bit 宽度，取出时乘 8 换回字节 |

## 装 weights 的包照常通知 TS，落点取自包头

**改动日期**：2026-09-09

**改前**：`op_type = 0` 记成“kernel / weight 搬运包进 core 时跳过 TS、直接唤醒 DTE”；进核那一笔的 `route` 按 core 的角色定死；weights 加载的数据路径写成“TS 派 DTE RV core 跑 weights loader → 算出 Matrix Mem 地址 → DTE 指令搬 Router → Matrix Mem”。

**改后**：跳过 TS 直接唤醒 DTE 的只有走 msg 流搬 kernel 那一档。装 weights 的包照常通知 TS，由 TS 派 datain 任务；数据由 DTE 按包头里的落点搬进 Matrix Mem，loader 数搬进来几笔，数够了中断 SCP。进核那一笔的 `route` 由 SCP 配：业务模式下按 core 的角色定，weights 加载阶段计算 core 上也落 Matrix Mem。

**依据**：《通信机制（分析过程）》与《MU-DTE 需求整理和遗留问题分析》两处写的都是“kernel 搬移 msg 进入 core 时，会跳过 TS，直接唤醒 DTE”，说的是 kernel 不是 weights，而走 msg 流搬 kernel 本身仍是待定需求；《系统软件需求分析》的 weights 加载步骤第一条就是“router 通知 ts，trigger datain 任务执行”。落点取自包头这一条与 R core 进核那一笔同源，依据是 DTE MAS 的 Header Parser 解析入站包头即生成 Descriptor、搬运随即开始。
