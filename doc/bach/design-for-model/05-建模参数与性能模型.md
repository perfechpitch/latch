#### ReduceModule 上下文与 Core Mem 是两块存储

两者都按 16 个用户切分，数字又都出现 16 KB，容易当成一块。

| | ReduceModule 上下文（Rmem） | Core Mem |
| - | - | - |
| 在哪 | Router 的 ReduceModule 里 | core 里 |
| 总容量 | 16 用户 × 16 KiB = 256 KB | 1 MB + 32 KB |
| 每用户 | 固定 16 KiB | 按 `stream_num` 均等切分，16 个用户时每人 64 KB |
| 存什么 | 归约的 FP32 中间累加结果 | 业务 token、MU 与 VU 的计算结果 |
| 占多久 | 一个包累加完就走 | 这个用户在本 core 上跑完整条任务链 |
| 谁管额度 | Reduce credit，DTE 与 ReduceModule 各维护一部分 | stream credit，Router 的 User Resource Allocation Table |
| 何时回收 | 收到 Retire 且相邻下游各方向的 credit 全部恢复 | 用户任务链结束发 release，或收到 Retire |

单用户 16 KiB 装不下一笔 32 KB 的 reduce，所以软件要把一笔 reduce task 拆成 4 笔 8 KB，这就是 `reduce_num = 4` 的由来；Core Mem 这一侧没有对应的约束。

> **带宽的两种算法应当互相验证**：
>
> 1. 每部分按最恶劣情况分别计算
> 2. 用容量需求 × 2RW × TPS 直接折算
>

>
> * MSG 包头被重复计算
> * 某些数据同时被 MU 读和被 DTE 广播（1W2R）
>

* 要读写 5 次：DTE 1 写 + VU 2 读 + VU 1 写 + DTE 1 读 = 3R2W
* 以 6144 BF16 为例，总带宽 = 6Ki × 2B × 5 × 5 MiTPS = **300 GiB/s**

### 包效率与总线对齐效率

R2R 与 C2C 上传输的包不是纯业务数据，包头等非业务数据按 32 B 算。包越短，非业务数据占比越高。传输的数据量范围是 32 B 到 12 KB（chip 内切 N、chip 间切 N）或 51.2 B 到 12 KB（chip 内切 K、chip 间切 N）。

| 切分 | 包效率下界 | 激活 N 个专家时的包效率 | N 服从 U(1,9) 时的平均包效率 |
| - | - | - | - |
| chip 内切 N、chip 间切 N | ≥ 50%（只激活一个专家） | N × 32 / (32 + N × 32) | 78.57% |
| chip 内切 K、chip 间切 N | ≥ 62% | N × 52 / (32 + N × 52) | 85.13% |

包效率之外还有一层总线对齐效率。**假设只能在 256 B 总线上对齐传输**时，效率随激活专家数剧烈波动：

| 激活专家数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
| - | - | - | - | - | - | - | - | - | - |
| chip 内外都切 N | 25% | 37.5% | 50% | 62.5% | 75% | 87.5% | 100% | 56.25% | 62.5% |
| chip 内切 K、chip 间切 N | 32.81% | 53.12% | 73.44% | 93.75% | 57.03% | 67.19% | 77.34% | 87.5% | 97.66% |

由此得出两条结论：

* **需要支持非总线宽度对齐的传输**。大部分包都小于总线带宽，256 B 完全对齐会有大量空泡
* 32 B 对齐是面积与效率的折中方案，**初步结论是不实现**，改为在算子切分时尽量不切出这么小的包

建模时这两层效率都要体现：链路上跑的字节数是业务数据加 32 B 包头，再按对齐规则向上取整。

## 延迟与吞吐模型

性能需求规格说明书给出的解析模型，作为 latch 性能模型的**参照基线**，建模跑出来的数应当能对上这些公式。

### 单核流水延时

```
单核流水延时 = 4 × 控制延时
             + (输入数据量 + 输出数据量) / DMA带宽
             + 大模型单核数据量 / Matrix计算带宽
             + 向量数据量 / Vector计算带宽
```

core 内基础流程是四个阶段：`数据 Load → Matrix 计算 → Vector 计算 → 数据 Store`。每个阶段的开销分两部分：

* 固定的调度启动开销
* 随数据量线性增长的执行开销

> **算子拆得越细，瓶颈会从数据量转向控制延时。**
>
> * 拆分足够细、计算时间小于调度开销时，流水线的瓶颈就变成控制延时
> * 《系统与部署》“切分限制”里“MU 计算时间最好不低于 100 cycle”那条约束就是这么来的

### 多用户吞吐

```
多用户吞吐 = 10^9 / (MU控制延时 + 大模型单核数据量 / Matrix计算带宽)
          = 10^9 / (MU控制延时 + 大模型总数据量 / (Matrix计算带宽 × 部署的总core数))
```

取决于执行流水中最长的阶段，通常是 Matrix 计算阶段。

### 跨 chip 关键路径

拆分粒度往两头拉，两项延时反向变化：

* 拆得越细，单 core 数据量越少，core 内延时越短
* 但部署的 core 数上升，chip 规模变大，跨 chip 传输延时随之变大

Reduce 的关键路径随部署规模增长：

| 部署规模 | 关键路径 |
| - | - |
| 一行的前 4 个 chip | 单 chip 传输延时 × 8 + Reduce 延时 × 4 |
| 一整行 chip | 单 chip 传输延时 × 8 + Reduce 延时 × 8 |
| 两整行 chip | 单 chip 传输延时 × 9 + Reduce 延时 × 9 |
| 四整行 chip | 单 chip 传输延时 × 11 + Reduce 延时 × 11 |

归纳成公式：

```
部署 chip 数 ≤ 行 chip 数：
  Node关键路径 = 行Chip数 × 跨chip传输延时 + 部署chip数 × 单chip Reduce延时

部署 chip 数 > 行 chip 数：
  Node关键路径 = (行chip数 + 部署chip数/行chip数 − 1) × (跨chip传输延时 + 单chip Reduce延时)
```

### 单用户总延时

```
单用户总延时 = 单core内流水延时 + Node关键路径传输延时

= ( 4×调度开销
  + (输入数据量+输出数据量)/DMA带宽
  + 一层大模型总数据量 / (Matrix计算带宽 × 部署core数)
  + 一层大模型向量数据量 / (Vector计算带宽 × 部署core数) )
+ ( (行chip数 + 部署chip数/行chip数 − 1) × (跨chip传输延时 + 单chip Reduce延时) )
```

> **这是一条有极小值的曲线**：
>
> * 切分规模越大，单 core 流水延时越小、Node 关键路径越大，反之亦然
> * 求这条曲线的极小值点，即最优切分策略，是建模要回答的核心问题之一

### TP 与 PPTP 的展开式

#### TP 切分

```
T_chip(broadcast/reduce) = d_embedding / B_R2R + T_R2R × 5跳

T_MU = 2 × T_core_delay + (d_embedding × d_intermediate × 3)
                        / (B_MU × TP_chipNumber × N_coreNumPerChip)

T_VU = T_core_delay + (d_intermediate × 2 Byte/element)
                    / (B_VU × TP_chipNumber × N_coreNumPerChip)

T_broadcast = T_reduce
            = TP_chipNumber × (T_C2C + T_R2R × 5跳) + d_embedding/B_R2R + T_C2C

T_delay = T_broadcast + T_MU + T_VU + T_reduce
```

#### PPTP 切分

```
T_chip(broadcast1) = d_embedding    / B_R2R + T_R2R × 5跳
T_chip(broadcast2) = d_intermediate / B_R2R + T_R2R × 5跳

T_MU1 (FC1/3) = T_core_delay + (d_embedding × d_intermediate × 2) / (B_MU × N_coreNum1)
T_MU2 (FC2)   = T_core_delay + (d_embedding × d_intermediate)     / (B_MU × N_coreNum2)
T_VU          = T_core_delay + (d_intermediate × 2B) / (B_VU × N_coreNum1)

T_broadcast^N = T_concat^N = TP_chip^N × (T_C2C + T_R2R × 5跳) + d_N/B_R2R + T_C2C

T_delay = T_broadcast1 + T_broadcast2 + T_MU1 + T_MU2 + T_VU + T_concat
```

#### 公式跑出来的数

### 试算口径

1. TPOT 按（GPU 注入到 LPU 时间 + LPU 计算时间 + LPU 输出 GPU 时间）× 层数估算
2. 理论吞吐上限 = 一个 Node 能提供的计算量 / 一个用户一层的计算量
3. 并行组内吞吐按矩阵计算算力折算：一个用户占用 T_MU 时间，换算 1s 能处理多少用户
   * **单用户 T_MU 里有调度开销，多用户时调度开销会被并行掩盖一部分**
4. 注入带宽按 `1 × d_embedding @FP8`，输出带宽按 `1 × d_embedding @FP16`
5. C2C 节点最大带宽按广播 reduce 并行的需求：`group内吞吐 × (d_embedding@FP8 + d_embedding@FP16)`
6. Node 吞吐按并行组数量比例放大
