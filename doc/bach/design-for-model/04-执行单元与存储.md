## DTE DSA（数据搬运引擎）

DTE 只做搬运，不做计算。职责是接纳任务、生成访问命令、处理背压、追踪在途事务、向 TS 报告最终完成。

### 支持的搬运方向

| Route | 使用的 Lane Pair | 说明 |
| - | - | - |
| Router → MM | RD_CH0 + WR_CH0（inbound） | Header Parser 解析后 Commit 成对建立 |
| Router → CM | RD_CH0 + WR_CH0（inbound） | 同上 |
| MM → Router | RD_CH1 + WR_CH1（outbound） | 出口是 Router TX |
| CM → Router | RD_CH1 + WR_CH1（outbound） | 出口是 Router TX |
| MM → CM | RD_CH1 + WR_CH1（outbound） | 出口切到 `DMA WR1`，硬件 route mask 只允许 CoreMem |
| ~~CM → MM~~ | — | **本版本不支持**，XBar 不提供 CH1 write ctrl → Matrix Memory 的连接；倾向保持不支持 |

数据布局：**仅支持连续一维搬运**，当前不支持 stride。

### 四 Lane 模型

核心抽象：**两个物理 Channel、四条独立 Lane，一个高层任务由一对 RD/WR 子上下文组成**。RD_CH0、WR_CH0、RD_CH1、WR_CH1 各自拥有 TaskQueue 和 Active Context。

* **配对接纳**：一个高层任务必须**同时**获得目标 RD/WR TaskQueue 项与 Completion RS 项，任一侧无空间则 Commit 整体保持，**不产生半任务**
* **独立激活**：任一 Lane 的 Active Context 释放后即可从本 Lane TaskQueue 激活下一任务，不等配对 Lane
* **Read-ahead**：RD Lane 可领先 WR Lane，领先量由中间 Buffer 的可用 Credit、outstanding 限额、可保留的任务边界数共同约束
* **按任务 Join**：Completion RS 仅在同一任务的 RD 与 WR 条件都满足时产生 `task_done`；**同拍多个 Join 命中时全部写入 Done Pending，不允许覆盖或丢失**

#### 完成状态的六个层级

| 状态 | 粒度 | 定义 |
| - | - | - |
| `queued` | Lane 子上下文 | 已进 TaskQueue，尚未装载为 Active Context |
| `active` | Lane 子上下文 | 由对应 AGCU/Ctrl 执行，四条 Lane 状态彼此独立 |
| `issue_done` | Lane 子上下文 | 该 Lane 最后一个请求已 Fire，**允许该 Lane 提前激活下一任务** |
| `drained` | Lane / 任务边界 | 相关响应、Buffer 数据和外部副作用均已收敛 |
| `join_done` | 高层任务 | 同一 task_id 的 RD 与 WR 子上下文均满足完成条件 |
| `task_done` | 高层任务 | 完成结果进 Done Pending 并与 TS 成功握手，**Exactly-once** |

### 参数

| 项目 | 数量/容量 | 说明 |
| - | - | - |
| 物理数据 Channel | 2 | inbound_ch / ch0 与 outbound_ch / ch1 |
| TaskQueue | 16 | 深度待评估 |
| 中间 Buffer | 约 8 KB | inbound + outbound；约 256B × (20～30)T，最大可掩盖 32T latency |
| 与 Cmem 接口宽度 | 256B + 8B | Data + scale，双向 |
| 与 router 接口宽度 | 256B | Data（看不到 scale），双向 |
| Hmem | 16 KB + 32 B | 软件包头 `sw_harder_table` + 硬件包头 `core_mask_table` |
| LUT | 192 B | `path_id_table` + `task_len_table` |

### Task Descriptor（软件接口）

软件通过 `dsawi` / `dsaw` 指令写四个寄存器，**必须最后写 Doorbell**：

```asm
# 先配 ADDR 和 TD 寄存器（两个都必须配）
dsawi.d TASK_CFG_ADDR(addr0) TASK_CFG_TD(addr1) data0 data1
# 再写 Doorbell，PACK 寄存器随之自动写入
dsawi.s TASK_CFG_TRG data0
```

#### TASK_CFG_TD 位域

| 位域 | 名称 | 含义 |
| - | - | - |
| 31:30 | `src_sel` | 00=Router，01=MM，10=CM，11=Reserve |
| 29:28 | `dst_sel` | 同上 |
| 27:26 | `queue_sel` | b0=ch0，b1=ch1 |
| 25:19 | `cnt` | 搬运总拍数，**单任务最大 256B×128 = 32KB** |
| 18:11 | `mask` | 256B 一拍，按 32B 粒度 mask，位为 0 表示该 32B 无效 |
| 10:5 | `path_id` | 当前任务打包需要的 PathID |
| 4:1 | `task_pack_id` | 一个任务可由多个任务包组成，从 0 计数，**包之间不保证顺序执行** |
| 0 | `last` | 是否当前 TaskID 的最后一个任务包 |

#### TASK_CFG_PACK 位域

`UserID[31:16]`、`stream_id[15:12]`（等同 SlotID）、`task_id[11:6]`（最大 64）、`no_ack[1]`（标记是否需要返回 Ack）、`last[0]`（当前 Task 的最后一个宏指令）。

### Router 入站的帧格式约定

* **一帧一任务**：同一 AXI-Stream Frame 只属于一个 Router→MM 或 Router→CM 任务，不允许任务间交织
* **首拍固定为 Header**：DTE 通过“上一帧 TLAST 已接受”判断下一拍是新 Header，不依赖 Start-of-Frame 信号；建议 Header 限定在一个 256B beat 内
* Header Commit 成功后才允许 Payload Fire，TLAST 标识最后一个 Payload beat；`byte_count` 为 0 时可由 Header beat 同时携带 TLAST
* TKEEP 按字节粒度生效；每个 Payload Fire 累计 TKEEP 有效字节，TLAST 时与 `byte_count` 比较
* **非法 Header 进入 Drop Frame 流程**：不生成 Descriptor、不发存储器请求，只消费到 TLAST 以恢复帧边界

Header 逻辑字段：`version / header_len`、`packet_type / route`、`dst_addr`、`byte_count`、`task_id / stream_id`、`attributes / reserved`。

### 双 Bank 配置与优先级

Commit 提供两个配置 Bank：**Bank0 > Bank1**。都空闲时，Router 配置优先进 Bank0、RVCore 配置优先进 Bank1；只剩一个 Bank 且两者竞争时**优先配置 Router 信息**。

### 并发约束

| 场景 | 允许 | 约束 |
| - | - | - |
| RD_CH0 领先 WR_CH0 | 是 | 受 inbound buffer Credit、任务边界容量、Router AXI-Stream 背压约束 |
| RD_CH1 领先 WR_CH1 | 是 | 受 outbound buffer Credit、读 outstanding、出口背压约束 |
| CH0 与 CH1 同时执行 | 是 | 目的资源无冲突时独立推进；共享 DMA_XBAR 端口时按其仲裁规则 |
| Router→MM 与 MM→CM | 是 | 分别用 CH0 与 CH1，端口映射无冲突时可并行 |
| Router→CM 与 MM→CM | 受限 | **竞争 CoreMem 写路径**，由 CM 写仲裁器选择，未获选 Lane 保持 valid 和上下文 |
| 同一 Lane 内任务乱序 | 否 | TaskQueue 按序激活；Read-ahead 允许 RD/WR 任务序号错位，但不改变各 Lane 内顺序 |
| 多个任务同拍 Join 完成 | 是 | Completion RS 捕获所有命中，Done Pending 负责序列化 |

### 包头与 topK 信息的处理

* **包头存储**：独立于数据存储，硬件包头 / 软件包头分别独立存储；可写入 DTE 内的 Header mem，也可写入 Cmem 中的独立空间（软件配置）
* **包头操作**：进 core 任务支持包头保存与丢弃；出 core 任务支持硬件包头的修改或生成（软件包头由软件改）；支持纯包头任务（无数据，len=0），进出 core 都可
* **topK 信息**：独立于数据保存，可写入 MU DSA 内部的 `topK_ep_table`，也可写入 Cmem 独立空间。**广播 token 进 core 必然携带 topK 信息，需要保存；计算后 result 数据出 core 不需要携带**
* **Setting shareMem**：任务数据传输完成后，支持按配置地址和数据写 shareMem，然后通知 TS

### 性能剖析口径

```
setup_cycles  = first_issue_fire - task_accept_fire
issue_cycles  = issue_done       - first_issue_fire
drain_cycles  = task_done        - issue_done
report_cycles = done_fire        - task_done
total_latency = setup + issue + drain + report
active_cycles = cycles(any_data_fire)
stall_cycles  = cycles(valid && !ready)
```

> **3 Lane 方案仍在评估**：把 Matrix Mem、CoreMem、Router 各看作一个读写 Resource，
> 理想情况应当是 3 Lane，定性上会带来性能提升；代价是 XBar 面积近似 *N_in × N_out × W*，偏大。
> 收益要靠建模与仿真定量给出，原文档标注“正在推进”。

### 通路方案

DTE 用**单向 2 通道**：router→mem 一条输入通道，mem→router 一条输出通道。Mmem→Cmem 归入 mem→router 通道，只需在 dst 端增加 xbar{router, Cmem}。此项暂定。

两条通道可能同时写 Cmem，需要仲裁，仲裁策略未定（轮询，或固定优先 router→Cmem）。

> **取舍的依据**：带宽需求 190～320 GB/s，而 Matrix Memory 硬件带宽 8192 GB/s、Core Memory 512 GB/s、Router 双向各 256 GB/s，带宽不是约束；物理布局上 DTE 位于 router 与 Cmem 之间、Mmem 在 Cmem 上方，因此按物理相邻关系合并通路的代价最小。

## MU DSA（矩阵单元）

针对 MoE 算子深度定制的 GEMV 加速核心，服务 Batch=1（Token=1）的极低延时推理。

### 算力与精度

| 计算类型 | token(A) 精度 | weight(B) 精度 | 算力 | 备注 |
| - | - | - | - | - |
| 同精度 | BF16 | BF16 | 4K MACs | |
| 同精度 | MXFP8 | MXFP8 | 8K MACs | scale block 32，E8M0 |
| 混合精度 | MXFP8 | MXFP4 | 16K MACs | 算力翻倍；scale block 16，FP8 |
| 混合精度 | MXFP8 | NVFP4 | 16K MACs | 同上 |
| 混合精度 | BF16 | MXFP4 | 8K MACs | 相比 FP8×FP4 算力减半：BF16 保持 256B 带宽（128 元素），FP4 减到 128 元素 |
| 混合精度 | BF16 | NVFP4 | 8K MACs | 同上 |

数据类型：token(A) / weight(B) 输入 BF16 或 MXFP8；`W_ep`（专家间权重）输入 FP32；输出 FP32 或 BF16。

### 支持的矩阵运算形式

1. `C = A × B`
2. `C = C + (A × B) × W_ep`。**矩阵乘 + 专家间 reduce，不支持初始 C 加载**

> 第二种形式把 EP reduce 从 VU 挪进 MU，**显著减少 Core Mem 的容量和带宽需求**。
> 建模时 MoE 多专家场景默认走这条路径。

### 计算原语

| # | 精度 | 原语 | 备注 |
| - | - | - | - |
| 1 | MXFP8 × MXFP8 | 1×K128×N64 | |
| 2 | MXFP8 × MXFP8 | 1×K64×N128 | |
| 3 | BF16 × BF16 | 1×K64×N64 | |
| 4 | BF16 × BF16 | 1×K32×N128 | |
| 5 | W4A8 | 1×K256×N64 | A 带宽 256B |
| 6 | W4A8 | 1×K128×N128 | |
| 7 | W4A16 | 1×K128×N64 | A 带宽 256B |
| 8 | W4A16 | 1×K64×N128 | |

物理阵列规格二选一：`1×K256×N32`（输出带宽 128B）或 `1×K128×N64`（输出带宽 256B）。
共 **32 个物理 Lane**，左右镜像各 16 lane，单 Lane 内 10 级混合高频流水。
另一处写的是“执行拍数 / 流水延时 9T”，差别在那处的计算流水不含脉动输出。

### vlane 机制

把 MAC 按 vlane 分组，在 CSA 加法树的第 128 输入层级节点插旁路 MUX，配上对应 vlane 分组的 MUX 逻辑
和 `Ksplit_acc` 寄存器，做到**单 lane 同时输出多个结果**。vlane 有 1 和 2 两种模式，影响两处：

* Load token：从 buffer 只读取 `256B / vlane_num` 字节，再 copy 扩展到 256B 输出
* Store concat：两种 vlane 的拼装方式不同
  * `vlane=1` 步进横切拼装：所有 lane buffer 并行 128B 截面，连续取 8 次攒满 1024B（8T）
  * `vlane=2` 纵向整块拼装：每 lane 一次取 8B、共 256B 截面，连续取 4 次攒满 1024B（4T）

### 数据通路与队列参数

| 模块 | 参数 | 值 | 备注 |
| - | - | - | - |
| `issue_q` | 队列深度 | 16 | 与启动延时有关 |
| Token ldq | 队列深度 | 16 | 取决于读延时 |
| Token ldq | Core Mem 读带宽 | 256 B（接口 512B / 1KB） | 与 MAC 阵列接口 256B |
| Token ldq | Core Mem 读延迟 | 16 | 待定 |
| Weight ldq | 队列深度 | 4 | |
| Weight ldq | Matrix Mem 读带宽 | 8 KB | 32 bank × 256B/T 一对一垂直贴合，**无 crossbar** |
| Weight ldq | Matrix Mem 读延迟 | 4T | 读 sram 2T + 打拍 2T |
| `stq` | 队列深度 | 16 | |
| `stq` | Core Mem 写带宽 | 256 B（接口 1KB） | 不足 1KB 按实际传输并标记 mask |
| `stq` | Core Mem 写延迟 | 16 | 待定 |
| Rd outstanding buffer | 容量 | 16 × 256B = 4 KB | 掩盖 latency |
| Wr concat buffer | 容量 | 1～2 KB | 各 lane buffer 深度不同，取决于物理距离：最远 16 拍、最近 1 拍，**越近 buffer 越大**，最大深度 16 |

### 执行流水

`regfile → issue_q → agu → acu → ldq → matrix exe → stq`。任务拆分顺序：**先循环 tile_K，再循环 tile_N**。

* `gen_ep_info`：按任务信息索引 topK 激活专家信息，用 topK 里的 global index 索引 `local_ep_table` 转成 local index，方便算 weight 访存地址
* `acu`：检查地址越界与对齐，异常时向阵列发排空指令（Drain），**允许已进入脉动通路的合法数据正常算完并写回，仅丢弃越界任务数据**，防止状态机死锁
* Weight 各 lane 访存地址相同，只需发一个地址然后逐级脉动到各 lane，MAC 入口用乒乓 2 级缓存掩盖 Mmem 读出延迟

### 性能目标与异常

* MXFP8 下 Primitive K256×N32 和 K128×N64 **阵列利用率 100%**；BF16 / MXFP4 同样 100%
* **任务切换无 bubble**；支持 task 间在执行通路上不同操作类型的重叠：`task0 load → {task0 计算 ‖ task1 load} → {task0 写回 ‖ task1 计算} → …`
* Primitive 1×64×128 且 K=64 时会有 **50% 性能损失**
* Tile K×N 过小会有性能损失，由 RVcore 配置延时和 MU 内启动延时决定

异常处理机制统一为 **Drain & Trap**，四步：

1. 阻塞任务下发
2. 清理已发出的访存请求（已请求的回复照常处理，不再发起新的）
3. 排空计算流水线
4. 恢复默认状态

走这条路的异常有三类：Load/Store misalign、Load/Store access fault、Load/Store bus·ecc error。
计算异常 `MATH_NAN_INF` 不走这条路，它不阻塞流水，由硬件自动 Clamp。

### 功耗特性（对建模有影响的部分）

* **<mde-comment id="s5mfx9">Matrix 与 Vector 错峰启动</mde-comment>**，防止二者功耗陡升叠加
* **DIDT 分级启动**，分级模式可配置，最小分级为单 lane 启动
* 单 lane MAC 阵列 bitmask 计算，零输入旁路 + 特殊值（NaN/Inf）穿透

## VU DSA（向量单元）

服务 LayerNorm、RMSNorm、Softmax、SwiGLU、MoE-Router、Sigmoid、ReLU 等算子。VU-Core 与 VU-DSA 之间的交互抽象是**宏指令**，这是 VU 与 MU/DTE 最不一样的地方。

### 关键规格

| 项 | 规格 |
| - | - |
| 向量位宽 VW | **1024 bit/cycle**，等效每周期 32 个 FP32 或 64 个 BF16 |
| 向量长度 VL | 1 ～ **16384 element**，单条宏指令内完成 |
| CM 访存带宽 | 每周期 1 次 Load + 1 次 Store，各 128 B（MXFP8 时 132 B） |
| CM 侧数据格式 | FP8_e4m3 / MXFP8 / BF16 / FP32 |
| 内部计算精度 | FP32 或 BF16，**单条宏指令内不支持混合精度** |
| 片内寄存器 | VRF 64 KB（128B/entry × 512 entry）、MRF 4 KB、SRF 256 B（4B/entry × 64 entry） |
| 执行单元 | VEXE（VALU0 / VALU1 / VALU2 / VSFU）、MEXE、SEXE |
| 宏指令配置 | 8 组静态配置模板 + 11 个动态参数寄存器 |
| 宏指令重叠 | **最多两条相邻宏指令重叠执行** |

VL 取上限 16384 时，单个 FP32 Token 恰好占满全部 VRF；VL 更小时按实际长度占用，剩余容量可同时驻留多个 Token 或宏指令之间传递的中间结果。

### 宏指令模型

**一条宏指令 = 1 组静态配置（计算图通路的“模板”）+ 1 组动态参数（本次任务的地址与索引）**。

VU-Core 写完动态参数后写 `macro_inst_trigger`，硬件锁存当前动态参数、与对应静态配置打包压入内部执行队列。
从 CM 读入、多级流水计算、写回 CM 的全过程都由硬件自己走完，**VU-Core 不感知周期级的控制细节**。

静态配置的改写规则：

* 硬件提供 8 组。软件需要的组数不超过 8 时，运行中无需改写。
* 超过 8 组时软件可随时改写。**若目标组正被未完成的宏指令引用，硬件把这次配置写阻塞在配置通路上**，
  等引用它的宏指令退休后写入生效、解除阻塞。
* in-flight 的宏指令始终按改写前的配置执行完毕。

### 依赖管理

* **Scoreboard**：对 VRF / MRF / SRF 实时读写状态追踪，检测 RAW / WAR / WAW
* **重叠执行**：前后宏指令无数据依赖、无执行资源冲突时，后续宏指令无需等前一条完全结束即可重叠发射微操作，最多两条相邻宏指令重叠
* **CM 访存依赖不追踪**：VU-DSA **不追踪 CM 访存的数据冲突**。存在冲突的宏指令之间须由软件置 `macro_inst_trigger.MACRO_INST_FENCE=1`，该宏指令等此前全部宏指令完成后才开始派发

### 单条宏指令的容量上限

下面这套约束决定一个算子要拆成几条宏指令：

| 资源 | 上限 | 细则 |
| - | - | - |
| CM 端口 | **1 次 Load + 1 次 Store** | 仅支持单一基地址上的连续地址访问；scale 区不参与软件编址，MXFP8 时 scale 地址由硬件按一一映射推断 |
| VRF 端口 | **2R + 2W** | 读写 Vector 索引连续；执行单元之间允许 bypass 与广播且不消耗 RF 端口；**允许读写寄存器完全重叠或完全不重叠，不允许部分重叠**（硬件不检查，软件保证） |
| MRF 端口 | **2R + 1W** | Mask 不能广播，一条宏指令内最多两处使用 Mask |
| SRF 端口 | 8 逻辑读 / 6 逻辑写 | 虚拟端口时分复用，每个逻辑口固定归属一个消费者/生产者，**不存在端口争用** |
| 执行单元 | 每个单元 **1 次** | **SEXE 例外**：物理上只有一组，SEXE0/1/2 是同一物理单元在一条宏指令内的 3 次串行迭代 |

> **配平计算依赖树是软件的责任**。硬件在执行单元之间只提供 bypass 与广播，
> **不提供软件可见的缓冲队列**。一条宏指令内的多条并行通路若经过的执行分组级数不同，
> 合并点的两个源操作数会不同拍到达。软件有两种配平手段：
>
> * 级数差一级：用 VALU2 的向量直通指令 `vmv.v.v` 当延迟对齐缓冲，代价是这条宏指令不能再用
>   VALU2 参与计算。
> * 级数差超出可配平范围：拆成多条宏指令，由 Scoreboard 经 RF 传中间结果。

### 执行单元能力

| 单元 | 能力 |
| - | - |
| **LU**（6 条指令） | 从 CM 读向量 / Mask / 标量；格式转换 FP8_e4m3 / MXFP8 / BF16 / FP32 → BF16 / FP32（扩宽，无精度损失，不用舍入模式） |
| **SU**（6 条） | 向 CM 写回；格式转换 BF16 / FP32 → FP8_e4m3 / MXFP8 / BF16 / FP32（窄化按 `TYPE_VL.ROUND_MODE` 舍入） |
| **VALU0**（29 条独有） | 加减乘、最值、MACC、**除法（非全吞吐）**、符号注入、比较生成 Mask、`vfclass`、`vfmerge`、标量广播 / 搬入 |
| **VALU1**（6 条独有） | 加减乘、最值、**跨元素归约（求和 / 最大 / 最小）**、**Top-16 排序**（同时输出 16 个 INT16 索引）、标量广播 / 搬出 |
| **VALU2**（1 条独有） | 加减乘、最值、标量广播、`vmv.v.v` 向量直通缓冲 |
| **VSFU**（12 条） | sin / cos / tanh / exp / exp2 / ln / log2 / rcp / rsqrt / sqrt / sigmoid、自定义拟合函数 |
| **MEXE**（15 条） | Mask 逻辑运算（and/nand/andn/xor/or/nor/orn/xnor）、`vcpop.m`、`vfirst.m`、`vmsbf/vmsif/vmsof.m`、`vmiuset.mv` / `vmiset.mv`（按 16 个 INT16 索引清 / 置 Mask 位，配合 Top-K 做迭代查找） |
| **SEXE**（7 条） | fadd/fsub/fmul/fdiv/fsqrt/frsqrt/frcp（.s） |

上表的条数按下面两张表数出。逐条指令的编码、汇编格式、行为公式与约束也在这两张表里：
[`_T5HNsl/Gu9Zka.csv`](../../../../perfechpitch/_sheets/_T5HNsl/Gu9Zka.csv)（95 条）、
[`JpZMgP.csv`](../../../../perfechpitch/_sheets/_T5HNsl/JpZMgP.csv)（99 条）。

SEXE 有两条约束：

* **迭代之间天然链式依赖**：SEXE1 的操作数可来自 SEXE0，SEXE2 可来自 SEXE1，
  因此第 2、3 次迭代只需 1 个额外的 SRF 读端口。
* **操作数来源只有三处**：SRF 读端口、VALU1 的归约输出、前一次 SEXE 迭代的结果。
  **不支持立即数**，也不能取 MEXE 为源，因为 MEXE 的标量输出是整数而 SEXE 只有浮点通路。

### 典型算子的宏指令拆分

拆分边界几乎总是由这一条决定：**标量结果必须先落 SRF，才能参与下一条宏指令的向量运算**。
根源是 SEXE 位于 VEXE 下游，没有回喂向量单元的通路。

| 算子 | 宏指令数 | 拆分 |
| - | - | - |
| Vector ADD / MULT | 2 | M0：LU 读 x1 写 VRF（不做算术）；M1：LU 读 x2，与 VRF 中 x1 逐元素相乘经 SU 写回 CM。**拆两条的原因是 CM 只有一次 Load** |
| Weighted SUM | 1 + N | 权重是标量走 SRF，不占 VRF；乘与加合成一条 MACC，每项只需 1 次 Load + 1 个 VALU，项数再多也不增加单条宏指令的资源占用 |
| RMS Norm（方案 3，最优） | 2 | M0：LU 读 x 分三路（与 VRF 中 Wi 相乘写 VRF、求平方、VALU1 归约成平方和）；标量链 SEXE 三次迭代（除元素数 → 加 ε → 平方根倒数）写 SRF。M1：VRF 乘积 × SRF 标量，SU 写出。**M0 恰好把 VALU0/1/2 各用一次** |
| Softmax | 3 | M0：读 x，一路写 VRF，一路 VALU1 归约出最大值写 SRF；M1：x − max，VSFU 求指数写回 VRF，同一份结果 VALU1 归约成和交 SEXE 求倒数写 SRF（**本条不访问 CM**）；M2：指数 × 倒数，SU 写回 CM。**归一化用“求倒数 + 向量乘标量”而不是向量除法**，避免全吞吐向量流水去等约 20～30 cycle 的除法 |
| Top-K Sort | 1 | LU 读 x，VALU1 排序指令一次输出 16 个最大值 + 16 个 INT16 索引；值与索引都可经 SU 写回 CM 或写 VRF。**K 固定为 16**，索引 VU-DSA 只原样透传不做算术 |

### 状态与同步

* 只读 `status` 寄存器实时回传 `BUSY`、`ISQ_FULL`、`ISQ_EMPTY`、`ERROR_FLAG`；判断全部宏指令是否完成用 `macro_inst_left` 或 `BUSY`
* 可向 TS 发送 **Event 硬件同步信号**，用于更细粒度的任务调度与软硬件解耦
* 三条配置通路（VU-Core / Ctrl-NOC / Debug Module）**共享同一份寄存器视图、权限一致**，流控彼此独立，VU-Core 的配置写因静态配置组被引用而阻塞时，Debug Module 与 Ctrl-NOC 仍能读出现场
* 经 `reg_file_addr` / `reg_file_data` 可读写 VRF / MRF / SRF，该通路与宏指令**异步**，须由软件保证访问期间目标 RF 不被 in-flight 宏指令读写

### CM 接口时序

读写各一条独立通路，一次请求固定 1024 bit，**不支持 burst**。

* **地址**：32 bit，按 128 B 对齐。软件给出的 `LD_addr` / `ST_addr` 里，向量与掩码按 32 B 对齐、
  标量按 4 B 对齐；跨 128 B 边界的拆分与重组由 LU / SU 完成。
* **数据信号**：1056 bit = 128B data + 4B scale，scale 段仅 MXFP8 有效。

## 存储子系统

### Core Mem（Cmem）

| 参数 | 值 |
| - | - |
| 容量 | (128KB + 4KB) × 8 bank = **1 MB + 32 KB** |
| bank 组织 | 8 个 bank，每 bank 深度 1024、位宽 128B + 4B |
| 最大访存带宽 | (128+4)B × 8 bank = **(1KB + 32B)/T** |
| 访问延迟 | 指令进 CM 到读出或返回 bvalid，**15T 以内** |
| 地址粒度 | 128B + 4B，支持按 Byte mask 读写 |
| SRAM 单元 | 1024×143bit（63×211 μm），每 bank 由 8 个 SRAM 组成，143 bit = 128 data + 4 scale + 10 ecc + 1 mask 标志 |
| 时钟域 | 1 GHz |

#### 各 master 的接口与延迟

| 通路 | 读写 | 带宽 | 写延迟 | 读延迟 |
| - | - | - | - | - |
| DTE(DMA) ↔ Cmem | 读 & 写 | 256B + 8B /T | 13T | 13T |
| MU ↔ Cmem | 读 & 写 | 128B + 4B /T | 11T | 11T |
| VU ↔ Cmem | 读 & 写 | 128B + 4B /T | 14T | 14T |

#### 仲裁规则

* 每组读写端口有 bank 冲突时 arb 二选一，无冲突可同时访问。
* DTE 端口部分 bank 冲突时**只反压冲突的那个 bank**。
* **同组内相同优先级**：DTE 端口先做读写各自的 bank 冲突判断，再做 wr 与 rd 之间的冲突判断。
* **非同组的优先级：MU > VU = DTE**。
* 不增加 bank 冲突计数器。

#### scale 与 ECC 的处理

* scale : data 比例最大 1:32。正常读写 SRAM 均为 132B，读出时多余的 scale(4B) 不向上传输，写入按 132B 写、多余部分补 0；scale 读写时直接按 (4B scale, 128B data) 拼接
* **正常写入数据会覆盖 scale 数据，导致对应地址的 scale 失效**
* byte_mask 非全 1 时 SRAM 内部留存记录，读取时不做 ECC 检测；全 1 时做 ECC 检测
* scale 的 4B 全 0 时默认非 scale 写，此时将最高位写入 32bit 0 数据，避免出现“其余 Byte 无 Byte mask 写入”而无法检测 ECC 的情况
* ECC 编解码在 SRAM 接口处处理（而非随数据到各访问源端口），能**减少 8% 数据传输功耗**，代价是面积增加
* ECC 1bit 错用计数器计数（每读端口 1 个、DTE/MU/VU 读写各 1 个），可经 NOC 读取；2bit 错报错

新需求：新增 DTE RV core 读写 CM 功能，有三种带宽 128B、16B、2B。

### Matrix Mem（Mmem）

| 参数 | 值 |
| - | - |
| 容量 | **32 + 4 MB**。scale 模式下划出 4MB 存 scale（scale:data = 1:8），32MB 存正常数据；非 scale 模式下 36MB 全存数据 |
| bank 组织 | 按 **64 个 lane** 分成 64 bank，每 bank 0.5625 MB；每 bank 与 MU 的 lane 匹配，顶层拉齐不同 lane 的延迟 |
| 最大访存带宽 | **8 + 1 KB/T**（scale 模式；非 scale 模式最大 8KB/T） |
| 访问延迟 | master 请求进 MM 到读出或 bvalid，**50T 以内** |
| 地址粒度 | 128B，**不支持按 Byte mask 读写** |
| SRAM 单元 | 2048×128bit，ECC 按 128bit 一组 |
| 时钟域 | 1 GHz |

| 通路 | 读写 | 带宽 | lane 内延迟 |
| - | - | - | - |
| DTE(DMA) ↔ Mmem | 读 & 写 | 256 B/T | 写 9T，读 8T |
| Mmem → MU | **只读** | 8 + 1 KB/T | 8T |
| Ctrl NOC ↔ Mmem | 读 & 写 | 16 B/T | 地址对齐 128B，数据粒度 16B，burst len 最大 8 |

> **Mmem 的并发约束**：DTE、ctrl noc、MU 三者**不能出现两个 master 同时访问相同 bank**；同时访问时只执行 MU 指令，并通过计数器记录报错。这是建模仲裁逻辑时必须体现的硬约束。

ECC：SRAM 内部支持单 bit 自纠错，读出时检测到单 bit 错，纠错后**在 SRAM 空闲时写回对应地址**覆盖原有错误数据。

Mmem 按 core 角色扮演三种角色：

1. **普通计算 core**：权重加载阶段接收 DTE 从 router 搬来的 weight，供 MU 做 MoE 计算。
2. **reduction core**：存 reduction 数据，不存权重。
3. **broadcast core**：存 token 数据，防止专家不均衡影响其他 EP group 的 token 广播。

### Share Mem

32 KB，只被 DTE / MU / VU 三个 RV core 的访存指令读写，访问延迟 5～10 拍，
远短于 Core Mem 的 15～25 拍。**不需要初始化**。三种用途：

* task 之间的共享数据
* B core / R core 的用户数据映射表的更新与查询
* 标量数据

### 存储的整体带宽对照

| 项 | 带宽 |
| - | - |
| Matrix Memory 硬件带宽 | 8192 GB/s |
| Core Memory 硬件带宽 | 512 GB/s |
| Router 双向各 | 256 GB/s |
| DTE 数据通路带宽需求 | 190～320 GB/s |
