## 产品定位与性能目标

### 在 LLM 推理系统中的位置

Bach（对外称 LPU）是为 LLM **异步异构推理**设计的专用加速硬件，只承接 **Decoding 阶段的 FFN / MoE 计算**，用全 SRAM 架构解决这一段的访存带宽瓶颈。分工依据是两条拆分：

* **Prefill / Decoding 分离**：Prefill 可以合并多个 token 一次调模型，是算力密集型，GPU 的甜点区；Decoding 逐 token 调用模型，不组 batch 时进入访存带宽瓶颈，正是 SRAM-Base 架构的优势区。
* **Attention / FFN 分离**：Attention 要处理随上下文线性增长的 KV-cache，SRAM 架构没有优势，留给 GPU；FFN/MoE 交给 Bach。

因此系统形态是 **GPU + Bach 组合**：GPU 算 Attention 和其余层，把 token 通过 Ethernet 送进 LPU Node，Bach 算完 FFN 再送回。MoE 场景下 GPU 还负责算 top-k 并决定 EP 路由。

### FFN 算子构成

Bach 要算的是 SwiGLU 结构的 FFN。前后的 RMSNorm 与 Residual **当前不考虑支持**：

| 算子 | 输入 | 输出 | 执行单元 | 特性 | 复杂度 | 支持 |
| - | - | - | - | - | - | - |
| FC1 / FC3 | A: 1×d_model @FP8<br>B: d_model×d_inter @FP8 | 1×d_inter @FP16 | MU | GEMV，Memory bound | K×N | 支持 |
| SiLU | 1×d_inter @FP16 | 1×d_inter @FP16 | VU | Element-wise，Compute bound | N | 支持 |
| dot | 两路 1×d_inter @FP16 | 1×d_inter @FP8 | VU | Element-wise，Memory bound | N | 支持 |
| FC2 | A: 1×d_inter @FP8<br>B: d_inter×d_model @FP8 | 1×d_model @FP16 | MU | GEMV，Memory bound | K×N | 支持 |
| RMSNorm | 1×d_model | 1×d_model | VU | Element-wise + 归约 | 2K | **当前不考虑支持** |
| Residual | 1×d_model | 1×d_model | VU | Element-wise | K | **当前不考虑支持** |

> Matrix 与 Vector 的算力比例是 **1.5·K : 1**（只考虑 SwiGLU 的 FC1/2/3 与 RMSNorm/Dot 时）。硬件上给到的 M:V 算力比例是 **512:1**。这解释了为什么 MU 是 8K MAC/T 而 VU 只有 32 MAC/T 量级。

支持的工作模式随模型范围扩展分三档，越往下对硬件要求越高：

| 工作模式 | token 派遣来源 | 关键约束 |
| - | - | - |
| MoE_only | CPU 多播 / LPU 广播 | 最大化执行单元利用率；输入输出带宽要求更大 |
| MoE + Reduction | CPU 多播 / LPU 广播 | Reduction 防卡死机制（提前预留空间保序）；建立 LPU 广播缓冲 buffer |
| FC0 + MoE + Reduction (+QKV Down) | 仅 LPU 广播 | 同上 |

## 集群与 Node

Bach 的物理组成分七级：集群、LPU Node、机柜、tray、层、chip、Bach core。一个集群跑一个完整模型；一个 LPU Node 的 SRAM 装模型的一层 MoE，由一个或多个机柜组成，当前 48 chip 的部署就是一个机柜；一个机柜是 3 个 tray 纵向相接；一个 tray 是 4 层，是最小的物理部署单元；一层是排成一行的 4 颗 chip（这个“层”是 chip 阵列的一层，与模型的层无关）；一颗 chip 是 2×5 个 Bach core，Harvest 后保证 8 个可用。**tray** 在源文档里也叫 board，在编译器的硬件抽象里叫 rack，都是同一个东西。

### 集群：GPU Node 与 LPU Node 的连接

GPU Node 含 8 张 GPU 卡，GPU 与网口最多 1:1，单口 400 / 800 Gbps（50 / 100 GB/s）。GPU Node 与 LPU Node 之间经 Ethernet 交换机（RoCEv2）相连，Node 与 Node 之间也只走 Ethernet。数据流是 `GPU → PCIe Switch → SNIC → Ethernet 交换机 → SNIC（含 DPU）→ PCIe Switch → Router`；控制流用 IBRC，GPU 侧由 CPU、Bach 侧由 SNIC 中的 DPU 处理。

token 逐层在 GPU 和 Node 之间流：Only MoE 与 MoE + Reduction 模式下，每层 GPU 把 token 送进该层的 Node，Node 算完 FFN 把结果送回 GPU；FC0～MoE～QKV Down 模式下，Node 把中间结果直接送给下一层的 Node，GPU 只收最终那份。GPU Node 与 LPU Node 的配比按 GPU 替换率定：Only MoE 下一层平均配 16 张 GPU，FC0～MoE～QKV Down 下配 8 张。

### tray 组成：4 层 × 4 chip

一个 tray 有 4 层，每层是一行 4 颗 chip，合起来 16 颗 chip 排成 4×4；另有 4 个 PCIe Switch，一个 CPU 带 DDR，4 个 SmartNIC。

* **chip 的四向口**：chip 之间全部用 PCIe 相连，每颗 chip 上下左右各一个 PCIe 口，相邻 chip 之间是 x32 直连。左右口接同层相邻的 chip，每层两端的 chip 接边缘的 PCIe Switch；上下口接相邻层的同列 chip，最顶层的上口和最底层的下口接同机柜内纵向相邻的 tray。同层、同列 chip 之间直连，不经 Switch。
* **PCIe Switch**：左右各两个，每个接两层 chip 的边缘口。CPU 经左侧的两个 Switch 进出；每个 SmartNIC 同时接一个左侧和一个右侧 Switch。
* **CPU + DDR**：做多播、缓存与流控。Only MoE / MoE + Reduction 接 2 个 DDR 通道，FC0～MoE～QKV Down 接 8 个。
* **SmartNIC**：4 个，各 50 GB/s，各自对外一个 ETH 口。

### 机柜内多 tray 互联与 token 派遣

3 个 tray 纵向相接成一个机柜：上一 tray 最底层 chip 的下口接下一 tray 最顶层 chip 的上口（编译器视角是 `chip.core9 ↔ core0`），全局 chip 坐标 `global_chip_y = tray 序号 × 4 + tray 内层号`，整个机柜是 12 × 4 的 chip 网格。tray 间的纵向链路按 120 GB/s 试算。两 tray 的 PCIe Switch 之间另有一条链路，供 CPU 跨 tray 多播用。机柜之间怎么相连源文档没有给出。

外部数据从全局左上角（`global_top_left`）的西侧进入，沿第一列自上而下传递；partial result 沿最后一列自上而下；最终结果从全局右下角（`global_bottom_right`）的东侧出口经 Switch 送到 ETH。

token 进机柜有三种派遣方式，当前选定 LPU 广播：

| 派遣方式 | 做法 | MoE + Reduction 下的保序要求 |
| - | - | - |
| 跨 tray 多播 | 一个 tray 的 CPU 从 ETH 收 token，经 Switch 间链路多播到所有 tray 的每一层 | 多播时用户间保序 |
| tray 内多播 | 每个 tray 各自从自己的 ETH 收 token，本 tray 的 CPU 多播到本 tray 各层 | 各 tray 的用户流顺序相同 |
| **LPU 广播（当前选定）** | CPU 经 Switch 只把 token 送进左上角第一个 B core；B core 留一份在自己的 Matrix Mem，再沿第一列传给下一个 B core，跨 tray 经纵向链路，直到所有 B core 都拿到；每个 B core 只向本组的计算 core 广播 | 不做乱序多播，流控交给 CPU |

### 互联参数

| 链路 | 带宽 | 延迟 | 说明 |
| - | - | - | - |
| GPU ETH → LPU Node ETH | 50 GB/s / 口 | 3 μs | 外部接口传输延迟，记作 T_node_in / T_node_out |
| PCIe Switch → Chip、Chip → Chip | 64 GB/s | 300 ns | 记作 T_C2C_PCIe |
| PCIe ↔ Router（左右） | 128 B/T | 10T + 25T | 控制延迟 + 走线 |
| PCIe ↔ Router（上下） | 128 B/T | 10T + 50T | 纵向路由延迟 |
| Router ↔ Router（片内） | 256 B/T | 40T | 记作 T_R2R / B_R2R |
| Chip0_core_Router ↔ Chip1_core_Router | — | 400T | 把 PCIe 当作一种长延迟的 R2R，记作 T_C2C |

### 外部带宽需求（按工作模式）

| 工作模式 | 输入带宽 | 输出带宽 | ETH 口数 | GPU 替换率 |
| - | - | - | - | - |
| Only MoE，EP4 | 30 GB/s（1 口） | 240 GB/s（60×EP4，不做 reduction） | LPU 侧 7，GPU 侧 ≥6 | 50% |
| Only MoE，EP6 | 30 GB/s（1 口） | 360 GB/s（60×EP6） | LPU 侧 9，GPU 侧 ≥9 | 50% |
| MoE + Reduction | 30 GB/s（1 口） | 60 GB/s（2 口） | 3 | 55% |
| FC0～MoE～QKV Down | 80 GB/s（GPU，2 口）+ 60 GB/s（上层 LPU，2 口） | 30 GB/s（GPU，1 口）+ 60 GB/s（下层 LPU，2 口）；做下投影则给 GPU 变 13 GB/s | 7 | 80% |

CPU 侧 DDR 需求按工作模式分两档（单通道单向约 48 GB/s）：

* Only MoE / MoE+Reduction：读写各 30 GB/s，2 个 DDR 通道即可。
* FC0～MoE～QKV Down：读写各 150 GB/s，需要 8 个通道。

### 已知的板级问题

* **Smart NIC 是否支持 bypass CPU 做 PCIe Switch 的乱序多播**：对 reduction buffer 的资源回收无法支持，当前结论是**不做乱序多播，由 LPU 广播**，流量控制交给 CPU。
* **FC0 输入的乱序重排**要在 CPU-DDR 解决。残差输入有同样的问题，方案是让残差数据跟随 GPU 运算数据顺序传输到 LPU，但残差**当前不考虑支持**。
* **PCIe SW 只支持双路 x16，不支持 x32**；C2C 是否支持 x32 待定。

## 业务流控与退出

业务任务跨多个 tray、HBU 和 Bach core 执行。状态查看、动态专家调度、权重更新、正常退出、故障恢复这些上层操作，都要求系统能在指定范围内停止接收新任务，并把已接收的任务排空到确定的一致性边界。系统因此分层提供限流、关流、排空、状态查询、重配置、恢复、退出七种基础控制能力，上层在无任务丢失、无结果重复、无资源提前释放的前提下完成业务管理。

### 五级管理粒度

Host CPU 统一发起模型任务并编排资源，GPU 与 LPU 在它的调度下协同：GPU 完成模型的通用计算并把 MoE 输入送到 LPU，LPU 完成 MoE 专家计算后把结果返回 GPU 或送往后续计算阶段。一个 LPU 可承载多个 Node，每个 Node 对应一层完整的 MoE 计算，Node 之间通过以太网交换中间结果。一个 Node 由一个或多个 tray 组成，tray 是 Node 内承载计算资源和交换数据的基本物理单元。HBU 是 tray 内的基本计算设备，即一颗 chip：SCP 子系统、2×5 个 Bach core、上下左右四个 PCIe 接口和 cfg NoC 控制网络。

| 层级 | 类型 | 主要职责 | 本级完成语义 |
| - | - | - | - |
| Host CPU | 全局管理层 | 业务发起、资源编排、生命周期管理 | 所有 LPU 完成且业务资源已释放 |
| LPU（Node） | MoE 层计算域 | 完成一层 MoE 计算 | 所有 tray 完成且 Node 结果有效 |
| tray | 物理资源单元 | 管理 SmartNIC、PCIe 和多个 HBU | 本 tray 所有相关 HBU 完成 |
| HBU | 计算设备 | 承载多个 Bach core 和 SCP | core、DMA、PCIe 及写回全部完成 |
| Bach core | 执行单元 | 执行具体计算任务 | 当前 core 或计算链任务完成 |

管理动作落在其中三级：

* **Host CPU** 是业务生命周期的所有者，面向整个业务、一个 LPU、GPU 与 LPU 的协同任务和业务的完整生命周期，负责停止提交、跨 LPU / GPU 协调和最终的资源释放。
* **Node CPU** 是 Node 级任务的协调者，汇聚多个 tray 的完成状态。
* **Bach core** 产生最细粒度的任务完成事件，把本地状态和完成事件返回上层。

### Node CPU 的管理范围与职责

Node CPU 管理一个 Node、Node 内动态数量的 tray、各 tray 上的 HBU、Node 内所有 Expert，以及 Node 级任务完成状态。职责八项：

1. Node 创建和初始化。
2. 任务准入：按本 Node 的资源状态决定是否接收新任务，看 Node buffer 状态、SmartNIC 队列状态、tray 间网络拥塞状态三项。
3. Node 级限流。
4. Node 级停止和排空。
5. Node 内动态专家调度。
6. Node 任务完成判断。
7. Node 资源释放。
8. 向 LPU 或 Host 返回 Node 状态。

Node 包含的 tray 数量在模型初始化或 Node 创建阶段确定，之后不再修改。数量依据 Expert 权重总容量、Matrix 计算容量、目标并发度、SmartNIC 及网络带宽、HBU 可用数量。

向某个 tray 分配任务前检查四项：

* tray 内资源是否可接收。tray 的 buffer 资源指 Broadcast buffer 与 reduction buffer，既要掩盖路径延迟，也要满足并发。
* 该 tray 允许的最大在途任务数，由并发度决定。
* 该 tray 是否需要限流。
* 是否绕开拥塞或故障的 tray。

Node 内各 tray 的路径延时不同：Node 控制本地 tray 的路径较短，远端 tray 要经过 SmartNIC 和 Ethernet，各 tray 的调度负载不同，网络还可能有排队和抖动。

Node CPU 接收返回信息有两条通道：经 PCIe 返回，或走反向数据通路（会与业务数据竞争）。

### 业务正常退出

Host CPU 确认业务正常退出后停止下发新任务；已进入系统的任务继续按原有数据路径执行；各层通过正常的任务完成机制逐级返回完成信息。

* **Host CPU**：负责生命周期管理和最终的退出决策，不直接感知 LPU 内部各 tray、HBU 和 Bach core 的瞬时状态。LPU 中已下发的任务执行完成后，LPU 通过以太网向后级 GPU 输出最终计算结果及完成信息；LPU 内有多个 Node 时，由最后一个 Node 给 Host CPU 输出最终结果及完成信息。
* **tray**：已下发任务正常执行，计算结果经 PCIe 输出给下一个 tray 或 Host CPU；完成信息走“Node CPU 的管理范围与职责”里的两条返回通道之一。
* **Bach core**：HBU 内最后一个 Bach core 传出该级的任务完成信息。软件配置由哪个 Bach core 返回完成信息；Bach core 能产生本地任务完成信息；信息的格式是 message 包；Bach core 的 Router 要识别该 message 包的方向。

### 动态专家调度的一致性边界

动态专家调度指业务运行中按专家负载、HBU 利用率、tray 容量、网络拥塞或维护需求，把专家从源执行位置（tray-A / HBU-A / Context-A）迁移到目标执行位置（tray-B / HBU-B / Context-B），或增加、删除专家副本。它建立的一致性边界：

```
新任务不再进入旧专家
+ 旧专家已接受的任务全部完成
+ 新专家的资源和权重准备完成
= 可以安全切换专家路由
```

参与者：

| 参与者 | 场景职责 |
| - | - |
| Host 专家调度器 | 根据全局负载生成迁移决策 |
| Node Leader tray CPU | 协调源 tray、目标 tray 和路由切换 |
| LPU / SmartNIC 路由模块 | 执行 Expert 到 tray 的路由 |
| 源 tray CPU | 停止源专家的新任务下发 |
| 源 HBU SCP | 关闭并排空源专家 Context |
| 目标 tray CPU | 预留目标 HBU 资源 |
| 目标 HBU SCP | 创建目标专家 Context 并配置 Bach core |
| Bach core | 执行旧专家的剩余任务及新专家的任务 |

## 模型切分与映射

切分方式决定每个 core 跑什么任务链，建模时这一层要参数化。

### 四种维度

| 维度 | 含义 | 硬件映射 |
| - | - | - |
| **EP** | 专家并行，token 按 top-k 路由到不同 EP 组 | 每个 EP Group 对应 Bach 的**一行 chip**；每组需分配 1 个共享专家 |
| **TP** | 张量并行，权重矩阵按 N 或 K 维切分 | 组内 chip 间 + chip 内 core 间 |
| **PP** | 流水并行，FC1 / FC3 / FC2 分别放不同行 chip | 算力需求是 3 的倍数，对 chip 映射不友好，会有浪费 |
| **DP** | 数据并行，按用户分流 | 用于 FC0 / Router 这类小算力算子（Residual / Norm **当前不考虑支持**） |

### 切分限制

* 需要的 chip 数 = 总专家权重 / 单 chip 容量（256 MB）
* 实际部署 chip 数 = `Ceiling(需要的 chip 数 / EP 组数, 4) × EP 组数`
* 纯 MoE 下每个 EP 的 chip ≥ 8（受单 tray 的 ETH 带宽限制）
* 只有 TP ≤ 8 才能只切单一维度
* 整模型容量分析需要 37～38 chip，实际分配总数不能超过 48
* **EP 与 TP 的切分数量要限制**，否则 MU 待计算数据太少、利用率下降：
  * 专家均分时，**MU 计算时间最好不低于 100 cycle**
  * EP 组内只有一个专家激活的极端情况下，要让控制延时低于 MU 计算时间，否则影响吞吐

> 已验证结论：**在 TP ≤ 16 的情况下，可以先做 Expert 之间的加权求和，再做 TP 之间切 K 的 reduce**。反过来（各 expert 先跨 core reduce 再做 EP Reduction）会让横向 reduce 带宽翻数倍，最多 9 倍（取决于该 EP 组激活几个专家）。

| <br /> | 切 N | 切 K |
| - | - | - |
| 权重怎么分 | `[K, N/P]`，按列 | `[K/P, N]`，按行 |
| 每 core 要多少输入 | 完整的 `x`，K 个元素 | `x` 的一段，K/P 个元素 |

| 出核数据量 | 每 core N/P，合计 N | 每 core N，合计 P × N |
| 路上要不要算 | 不要，纯搬运 | 要，做加法 |

中间累加精度固定 FP32。**concat 不占计算资源**，各段落在 Core Mem 的不同偏移上，拼起来就是完整结果。

看图中间被黑框圈出的那一格：它只有一份，却同时是 FC1/FC3 的**输出**和 FC2 的**输入**。
成立的条件有两个，缺一不可：

* **FC1/FC3 的 N 与 FC2 的 K 是同一个维度**（都是 intermediate）。切 N 得到的那一段
  `[1, 512]`，长度正好等于 FC2 权重行块的高度。
* **中间夹的 SiLU·dot·量化是逐元素运算**，只碰本 chip 手里那 512 个数，不改变分布。

于是每个 chip 手里的三样东西自然对齐，谁也不用跟别人换数据，代价只剩最后一次 reduce。

**那为什么 FC2 chip 间不也切 N。** 单看数据量，切 N 反而更省，它省掉了最后那次每 chip
一份完整长度的部分和。代价在别处：

| <br /> | FC2 chip 间切 K（选定） | FC2 chip 间切 N |
| - | - | - |
| 中间要不要重分发 | 不要 | 要：各 chip 的段先汇聚成完整的 `[1, 2048]`，再广播回所有 chip |
| 这一步落在哪 | 没有这一步 | 关键路径中间，而且是**同步点**，要等最慢的那个 chip 算完 |
| 最后一步做什么 | reduce 求和 | concat 拼接 |

* reduce 在 Router 里是逐跳流水累加的，数据流过就加，不必等齐
* 中间那次汇聚加广播是一次串行往返，躲不过去也重叠不掉
* 原始文档给的依据是“尽可能减少切分造成的 concat 和 reduce 操作的**数据等待**”，省的是等待，不是带宽

#### 四种模式

chip 间与 chip 内各选一次切法，组合出 `nn` 与 `nk`；再叠加 PP 就是 `pptp_nn` 与 `pptp_nk`。
FC1/FC3 与 FC2 对 Intermediate / Embedding 的定义互为倒置，以下统一按 **FC1/FC3 的维度定义**：

| 模式 | FC1 / FC3 | FC2 | chip 内通信 | chip 间通信 |
| - | - | - | - | - |
| `tp_nn` | chip 间切 N，chip 内切 N | chip 间切 K，chip 内切 K | FC2 逐级 reduce | FC2 全局 reduce |
| `tp_nk` | chip 间切 N，chip 内切 K | chip 间切 K，chip 内切 N | FC1/3 逐级 reduce 汇聚到 1 个 core 做 dot 再广播；FC2 concat | FC2 reduce |
| `pptp_nk` | chip 间切 N，chip 内切 K（FC1、FC3 分别在不同行 chip） | chip 间切 K，chip 内切 N | FC1/3 逐级 reduce；FC2 concat | FC2 reduce |
| `pptp_nn` | chip 间切 N，chip 内切 N | chip 间切 K，chip 内切 K | FC1/3 concat；FC2 reduce | FC2 reduce |

**chip 内那一级可以切 N，`nk`** **就是这么来的。** EP6+TP8 实际落到每个 core 的分片：

| <br /> | chip 间 | core 间（chip 内） |
| - | - | - |
| FC1 / FC3 | 切 N，2048/8 = 256 | 切 K，6144/8 = 768 |
| **FC2** | 切 K，2048/8 = 256 | **切 N**，6144/8 = 768 |

两级的选择此消彼长：让 FC2 在 chip 内切 N，FC1/FC3 在 chip 内就得切 K。表里的 chip 内通信是这么来的：

* **`tp_nn`**：FC1/FC3 两级都切 N，每 core 出的就是 y 的一段，不必 concat，
  下游 FC2 切 K 正好吃这个分布。所以 chip 内只剩 FC2 的逐级 reduce。
* **`tp_nk`** **与** **`pptp_nk`**：FC1/FC3 在 chip 内切 K，每 core 出的是**部分和**，
  * 必须先 reduce 成完整的 FC1、FC3 结果才能做 dot，因此要汇聚到一个 core 上做完再广播回去
  * FC2 在 chip 内切 N，出的是 y 的一段，所以是 concat
* **两种** **`pptp`**：PP 把 FC2 放到了另一段 chip 上，dot 结果必须先 concat 成完整的再传过去，
  这是纯 TP 不需要的一步。选 PPTP 的理由正是 **concat 比 reduce 延迟低**，用它换掉跨节点的 reduce。

这四种模式会把 chip 内的 core 分化成不同角色，任务链因此不同。以 `pptp_nk` 为例：

| 算子 | core 角色 | 职责 |
| - | - | - |
| FC1 | `pptp_fc1_nk_core` | 算 FC1，结果输出做 reduce |
| FC1 | `pptp_fc1_nk_result_core` | 额外收集 reduce 结果送到 FC3 chip |
| FC3 | `pptp_fc3_nk_core` | 算 FC3，结果输出做 reduce |
| FC3 | `pptp_fc3_nk_dot_core` | 额外等 FC1 的 reduce 结果做 FC1·FC3 dot，结果作为 FC2 chip 的 token |
| FC2 | `pptp_fc2_nk_core` | 等 dot 结果算 FC2，输出做 concat |
| FC2 | `pptp_fc2_nk_concat_core` | 额外收集 chip 内所有 core 的 concat 结果送下一 chip |
| FC2 | `pptp_fc2_nk_concat_reduce_core` | 额外收跨 chip 的 reduce 数据，core 内 reduce 后送下一 chip |

### 两种专用 core

除计算 core 外，每行还要借用几个 core 做专用缓冲。这两种 core 的**任务链形态和普通 core 完全不同**，
建模时必须单独建，逐 task 的形态见《TS 任务调度器》的[“TS 的四种工作模式”](<03-ts-任务调度器.md#ts-的四种工作模式>)一节。

| 专用 core | 为什么需要 | 缓冲介质 |
| - | - | - |
| **Broadcast core（B core）** | 作广播的发起点：等这条 path 上所有目的 core 都有余量才放行，<mde-comment id="3awz3v">并在等待期间缓存 EP 组内被阻塞的 token，防止一个 EP 组的拥塞影响其他组的广播</mde-comment>。**复制由 Router 按** **`directionMask`** **逐跳完成，B core 只发一次搬运** | 一个 core 的 32MB Matrix Mem，软件维护分配 / 释放指针（顺序 FIFO） |
| **Reduction core（R core）** | EP 组间求和若放 GPU 则 ETH 带宽不足；放 Router 会卡死；放 slave CPU 则 DDR 带宽不足 | 32MB Matrix Mem，软件维护映射表（**乱序**分配和释放，因为两笔 reduce 数据来自两个方向、用户会乱序） |

**每行借用一个 Bach Core 作为 Reduction Core**，借出口处的 Core3 / Core7。此项暂定。

> **取舍**：借用现成 core 可以直接拿它的 32MB Matrix Mem 当 buffer。另外五个候选各有硬伤：
>
> | 候选 | 硬伤 |
> | - | - |
> | 经 Ethernet 送 GPU 算 | 要 7 个 ETH 通道，对客户 GPU 提出额外要求 |
> | 复用 TP 的 Router 逐级 reduce 通路 | buffer 不足以掩盖 EP 间不均衡 |
> | 外挂高性能 CPU | 受限于内存通道数与主板功耗 |
> | PCIe Switch 上挂 FPGA | 成本过高，只作备选 |
> | chip 内新增小 core | 不需要 reduction 的 chip 也要浪费 3/4 到 7/8 的新增面积 |

#### EP 组间的 reduction 通路

R core 不分配权重，不参与 TP 和 FFN 计算。各 EP 组的 R core 串成一条链，一个用户的结果沿链逐组累加。
这条通路上有两种数据，名字相近但不是一回事：

* **reduce 数据**：本组 TP 内逐级 reduce 出来的组内结果。
* **reduction 数据**：沿链在 EP 组之间流动的累加中间结果。

1. R core 的 Router 收下相邻上游 core 的 reduce 数据，存进本 core 的 Matrix Mem
2. 若当前 EP 组是该用户的第一组，累加后经 reduction 通路发往下一组 R core 的 Router
3. **reduction 数据到达 R core 后判断该用户是否落在当前组：落在本组就进 Matrix Mem，等与本组的 reduce 数据累加后再发出；不落在本组就跳过，沿通路继续向下游透传**
4. 走到链尾节点累加完成，经 result 输出通路送到 PCIe Switch

图：[`d08.png`](../../../../perfechpitch/Bach/02_二、需求分析/04_第二阶段需求分析（功能扩展）/02_EP组间Reduction讨论（过程）/d08.png)（Reduction 传输通路）、[`d09.png`](../../../../perfechpitch/Bach/02_二、需求分析/04_第二阶段需求分析（功能扩展）/02_EP组间Reduction讨论（过程）/d09.png)（core 内计算流程）

Router 侧因此多两条要求：收到 reduce / reduction 数据后通知 TS 下发 DTE 搬运任务；**搬运要原子化**，某个方向的用户数据全部搬进 Matrix Mem 后才能搬别的方向或别的用户。这与普通 reduce 要求交织（每个方向进来 128B 就往后传）正好相反。

#### EP Reduction 的死锁与解法

若每批用户都能占满 reduction core 的 reduce-buffer，逐级 reduction 会死锁。两个方案：

1. **硬同步解卡死（通信保序）**：上级 reduction core 必须等同一用户到达下级后才向下传播。优点是对顶层调度无要求，缺点是最差要首尾 reduction core 直接通信，同步机制复杂。
2. **动态调度解卡死（调度保序）** ← **选定**：调度核在派遣前检查所有 EP reduction core 余量都充足才派遣，硬件只需实现 reduce-buffer 释放反馈通路。

**LPU Dispatch 派遣机制**（选定方案的具体规则）：

1. 作为 dispatcher 的 bach core 派遣用户时，**统一分配所有 reduce core 资源，不区分 EP 组**；
2. 所有 reduce core 都有余量时才派遣；
3. 派遣时每个 reduction core 余量减 1；
4. 等最终 reduction core 返回后，所有 reduction core 余量加 1。

即使用户不需要的 EP 也要求余量充足，因此**只会顺序调度**。

### 动态专家调度

当前方案：软件在 host 侧对发出和返回的 token 计数，确认 LPU 侧已 empty 后再调整专家，
**对硬件没有额外调度要求**。

搬移 MoE 的任务需要 Fence 语义，搬移完成前阻止后续任务。写 Matrix Mem 与写 Core Mem 的延时不同，
必须保证搬 token 之前 MoE 已经搬完。

## Chip 与 Harvest

### Chip 内结构

一个 chip 是 **2×4 的 Bach Core 阵列**，Router 在物理上位于 chip 中部，各 core 通过自己的 Core Station 接入 Router。加上：

* **SCP**（System Control Processor）：通过 `ctrl_noc` 访问 chip 内全局地址空间，做初始配置与状态查询
* **PCIe / C2C**：chip 左右两侧对外，既可接 PCIe 也可接相邻 chip 的 router
* **DTM**：经 DMI 协议连到 core 内的 Debug Module，支持 JTAG 调试

### Boot 流程

#### Chip 内

1. SCP 自启动（chip 间顺序或并行由设计决定）
2. SCP 完成 PCIe 链路训练
3. SCP 顺序配置启动 chip 内的 core0～core7。core 间启动程序一致，`ctrl_noc` 可考虑实现广播：
   * 无广播：SCP 依次配 core0～core7
   * 有广播：SCP 发一次带广播的请求给 core0，由 core0 依次广播

#### Core 内

1. SCP 把启动程序搬到 DTE / MU / VU 三个控制核的 ITCM。**TS 无控制核，仅寄存器实现**，复位清 0 即可，等待外部启动
2. SCP 启动三个 RV Core，进入 wait 状态等待业务唤醒。DTE 需具备解析 MSG 并执行的能力（可选软件实现，对应解析程序通过 boot 搬到控制核）；MU / VU 不需要解析 MSG
3. SCP 确认所有 ready 信号为高，开放 Core 的业务接收权限
4. Router 开始接收业务

初始化配置按下面的顺序做完六步：

1. RV core firmware 写入 ITCM
2. DTE bootloader 写入 DTE RV core 的 ITCM
3. 配置 bach core 解复位（clk/reset 模块）
4. TS 初始化（任务链）
5. router 初始化（路由表）
6. kernel 初始化

### Harvest（良率方案）

**暂定方案 3**。三个候选的对比：

| 方案 | 做法 | 优点 | 缺点 |
| - | - | - | - |
| 1 | 保持 8 core，core 内加 SRAM 冗余备份 | core 数固定为 8，软件配路由不受坏点影响 | 对 B core / R core 支持差，会导致两侧 chip 矩阵切分不均；只有 SRAM 冗余，逻辑损坏只能当坏片 |
| 2 | 每行多加一个 chip，阵列改 4×5，保证总 core 数 ≥ 34 | 不受单 chip 坏点数影响，利用率高 | 切分最小单元只能是 core，灵活性极差；软件要按坏点位置配不同路由 |
| **3（暂定）** | chip 内 core 数从 2×4 改 **2×5**，每 chip 允许 1～2 个坏 core | 最好地支持 B core / R core 机制，保证每 chip 固定 8 个可用 core，矩阵切分更均匀 | 软件需按坏点位置初始化不同路由 |

#### 良率模型

设 full good 概率为 *f*，10 个 core 中任一个坏的概率为 *1 − f^(1/10)*，坏 n 个的概率：

```
D_n = C(10,n) × (1 − f^(1/10))^n × (f^(1/10))^(10−n)
```

取 *f* = 0.3：D_1 ≈ 0.3845，D_2 ≈ 0.2363，坏超过 2 个的概率 ≈ 0.0792。

| 芯片型号 | 坏 core 数 | 概率 | 路由影响 |
| - | - | - | - |
| A 型 | 0 | 0.30 | 不受影响 |
| B 型 | 1 | 0.3845 | 坏点 core 路由配置为“只经过，不进 core”；作为两侧 chip 时，坏点若落在 broadcast / reduction core 位置需改数据流路由策略 |
| C 型 | 2 | 0.2363 | 同上，组合更复杂 |

> 对建模的直接影响：**Router 必须支持 Skip**，某个 core 无法工作时数据直接转发给下游、不进本 core。而且“Harvest 方案中坏点位置不同会导致不同 chip 初始化配置的 router 路由不同，需要编译器感知”，所以路由表要作为建模输入参数，不能写死。

### Chip 内地址划分

Bach Core 内部各模块的地址空间视野：

| DTE DSA | DTE io reg、Matrix mem、Core mem |
| MU DSA | MU io reg、读 Matrix mem、Core mem |
| VU DSA | VU io reg、读 Matrix mem、Core mem |
