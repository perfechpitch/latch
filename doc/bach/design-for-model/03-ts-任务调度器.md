# TS 任务调度器

模式：design。层次：Core 内任务调度。本文供调度、软件和性能建模人员确定一条用户任务链如何接入、下发、完成和退休。

设计依据为原始库中的 [Task_Scheduler_详细设计文档模板](</home/colin/develop/perfechpitch/_refs/Task_Scheduler_详细设计文档模板.md>)，同步基准 revision 6452。本文描述当前采用的详设基线；现有代码的差异列在 [TS 单元设计](07-units/chip/core/ts.md) 的“当前模型与目标设计”。原文分歧集中登记在 [文档缺口与 TBD](08-文档缺口与-TBD.md) 的“TS 与 DTE 详设内部不一致”。

## TS 解决的问题

* core 里三个执行单元（DTE / MU / VU），每个单元前面挂一个顺序执行的 RV core
* 一个用户走的不是一次运算，是一串跨单元的操作：搬进来 → 算矩阵 → 算向量 → 搬出去
* 最多 16 个用户同时在 core 里，各自走到不同的位置

从各切分场景归纳出三条：

1. 每个用户的任务流由多个不同执行单元的操作顺序串联而成
2. 各场景的 core 内任务流固定，任务类型不多，变化少
3. 同一场景的 core 内，不同用户执行的任务流相同，用户间顺序执行

三条各定下一件事：

* 第 1 条 → 必须有人管住每个用户内部的先后
* 第 3 条 → 多个用户可以在三个单元上错开流水
* 第 2 条 → 这件事不必交给软件

> **取舍**：任务流固定、任务类型不多，硬化调度器足够覆盖，因此不做软件调度。代价是任务流的形状被写死在 64 项的表里，换场景要重配；2～3 拍是旧 MAS 的局部目标，实际延迟按 Lookup、许可、Fire Hold 与接受分别计算。

**TS 是一块固定的硬件逻辑，不是可编程的调度器。**

* 行为由上电时 SCP 经 `ctrl_noc` 配下来的几张表决定
* 配完写 `TS_INIT_FINISH` 就按固定逻辑跑，运行期不接受软件干预，也没有指令可执行
* 软件只能改配置：换一套 `task_chain` 换一条任务流，改 `SELF_START` 换一种工作模式
* core 里真正跑软件的是三个 RV core，TS 只负责把 task 派给它们

TS 的全部工作收在两张表和四个动作里。

* **两张表**
  * `task_chain`：静态。软件初始化时按 core 的角色配好，说清这类 core 的操作流长什么样
  * `stream_table`：运行时。硬件维护，说清每个在途用户走到了哪一步
* **四个动作**
  * 建表：新用户到了占一项
  * 判就绪：当前这一步的前置条件齐了没有
  * 选最老：同一个单元有多个候选时选谁
  * 推进度：收到完成事件把用户推到下一步，走完退休

### TS 的三种工作模式

| 模式 | 入口与启动 | 完成与退出 |
| - | - | - |
| 普通 | Trigger 查询用户并按结果创建或复用 Stream | 执行完整任务链，Head 满足条件后通知 Router |
| SELF_START | 配置保存 Task0 模板；首个已接受 Trigger 同时生成 Bypass 并激活所有启用槽 | Task0 Core ACK 绑定 UID；后续 Trigger 只生成 Bypass；用户完成后本地重生 |
| 权重加载 | 独立 DataIn PC 有效，weights_loading 标记加载阶段；PC-only DTE 请求其余身份字段为 0 | 丢弃新 ACK/RMEM 返回并暂停已有 FIFO 配对；软件用外部完成保证清 loading，再提交业务配置 |

SELF_START Bypass 使用 SID15/TID63，ACK 被过滤。它与普通计算 Stream 分别持有执行状态。权重请求的生成时点在原文中有分歧；禁止把 WEIGHTS_MODE 置位本身当成搬运完成。
加载阶段的搬入与业务流分别配置。SELF_START让MU RV Core轮询软件队列；首个Trigger之前并不创建匿名计算槽。首Trigger后全部N槽同时有效，Task0按普通仲裁连续下发；不是只启动一条链。

## 两张表

### task_chain：软件配好的操作流

最多 **64 个 task**，软件初始化时经配置口逐项写。每项PC和ATTR两个32位寄存器：`TASK_CHAIN_n_PC`（`0x000 + 8n`）与 `TASK_CHAIN_n_ATTR`（`0x004 + 8n`），先写 PC 再写 ATTR：

| 寄存器 | 位域 | 名称 | 含义 |
| - | - | - | - |
| PC | 31:0 | `TASK_PC` | 任务执行的起始 PC |
| ATTR | 1:0 | `TASK_SEND_UNIT` | 执行单元：00=DTE，01=MU，10=VU |
| ATTR | 3:2 | `TASK_RECV_UNIT` | 收哪几路完成：00=只等 RV core 的完成；01=只等 DSA 的完成；10=RV core 与 DSA 两路完成都到才算完成；11 写不进，保持旧值 |
| ATTR | 4 | `WAIT_WAKE` | 要等 Router 送来的数据唤醒，即搬入任务 |
| ATTR | 7:5 | `TASK_TYPE` | 0 普通；1 Broadcast 或 P2P 重发的搬出；2 Broadcast 重发的搬入；3 P2P 重发的搬入；4 逐级 reduce；5 完成时带回新 PID，交给紧邻的下一项 |
| ATTR | 13:8 | `TASK_P2P_REISSUE_TID` | 重发搬入配对的搬出是第几项 |
| ATTR | 14 | `TASK_CREDIT_EN` | 普通任务检查新增方向许可；Reduce独立检查RMEM，Core内搬运不申请下游方向 |
| ATTR | 22:15 | `TASK_PATH_ID` | 任务的 path_id：搬入任务按它与 Router 送来的 PID 匹配，要 credit 的任务按它问 credit |
| ATTR | 23 | `TASK_END` | 任务结束标识 |
| ATTR | 31 | `TASK_VALID` | 软件写 ATTR 后硬件自动置有效 |

这张表是一条全序链，位域里没有前驱表也没有后继表，唯一的结构信息是数组下标。软件在编译期把操作之间的依赖关系拓扑排序，拍成这条链，链上的先后就是任务之间的全部依赖信息。

`DATAIN_TASK` 是单独的两个寄存器：

* `DATAIN_TASK_PC`（`0x200`）与 `DATAIN_TASK_ATTR`（`0x204`），只能绑定 DTE
* ATTR 三个字段：`WEIGHTS_MODE`、只读的 `TASK_SEND_UNIT`（固定 DTE）、`TASK_VALID`
* `WEIGHTS_MODE` 置位表示处于 weights 加载阶段，此时不启动 task_chain
* 只在 weights 加载与自启动两种模式下用；普通模式的搬入任务就在 task_chain 里，标 `WAIT_WAKE`

其余配置寄存器：

* `STREAM_NUM`（`0x208`）：1～16，写超过 16 的值只写入 16
* `TS_INIT_FINISH`（`0x20C`）、`TS_STATE`（`0x210`，只有 `TASK_CHAIN_ERROR` 一位）
* `SELF_START`（`0x214`）：1 为自启动模式
* `ROUTER_TABLE_0～63`（`0x400～0x4FC`）：按 PID 索引，每项 `TASK_DIR`（上下、左、右、本 core 四位）与 `TASK_VCID`；VCID 随 DTE 任务下发，方向由Credit Ctrl按新增需求使用，物理位域待统一
* `B_CORE_DIRECTION`：B core 的广播方向，TS 查这些方向的 credit。这一项与 `trigger_task_chain_en` 取自《TS_通信机制》，MAS 的地址映射里没有

| 地址 | 寄存器 | 有效字段 |
| - | - | - |
| 0x000+8×TID | TASK_CHAIN_TID_PC | [31:0]PC |

| [30:24] | reserved | 读0 |
| [31] | task_valid | ATTR写入由硬件置位，软件写数据填0 |

每行独立记录PC和ATTR是否写过，两者都写过才是完整配置。成功提交生成Task0配置脉冲，装入Stream Map的模板、N和SELF_START，同时将三方向credit初始化为N。CONFIG／ERROR／ACTIVE控制配置及业务使用，运行期不热重配；ERROR下软件清INIT_FINISH回CONFIG，已写数据保留。

提交检查Task0完整、无半写行、Task0起连续、唯一末尾End、合法单元、N非0以及SELF_START独立DataIn配置。加载中提交业务配置报错。Reduce使用独立RMEM许可，credit_en可为0或1。ReissueOut的credit_en、P2P wait_wake和partner类型的检查范围存在原文分歧，软件配置仍采用一致的合法组合，硬件检查清单等待统一。

RouterTable逻辑方向bit0南北、bit1西、bit2东、bit3Local；许可只使用低三位。Task LUT可按静态PID提供方向，继承新PID时按实际PID重新取方向。VCID必须跟随实际PID，不随静态TID固定。
#### 编程顺序
1. 在CONFIG状态读回INIT_FINISH和TS_STATE；先完成权重加载，退出loading。
2. 配STREAM_NUM与SELF_START。特殊模式还配独立DATAIN PC/ATTR。
3. 每条Task先写PC再写ATTR；两半都写过才是完整行。逐项配RouterTable。
4. 写INIT_FINISH提交，检查Task0完整、连续有效、唯一末尾End和合法编码。
5. 成功后保存Task0模板与N、初始化三方向计数；失败进入ERROR，清INIT_FINISH后修正并重试。
6. 业务数据进入后，普通模式由Trigger建用户；SELF_START由首Trigger批量启动。

THROUGH_END_MASK只包含Task0至End。Reduce独立使用RMEM许可，不要求credit_en=1。Reissue配置检查范围、RouterTable物理位域与权重模式进入时是否生成请求仍在TBD逐项保留。

#### 表项里的三组字段

每槽保存用户身份、当前任务和用户级进度，三者共同决定调度。
- 用户字段：valid、UID、UID-valid、reissue、分配生命周期。
- Current字段：TID、实际PID、FSM、end、发送单元及方向需求。
- 用户级进度：64位完成位图、64位DataIn claimed位图、drct_used三位、RMEM独立许可和pending PID。
- DataIn的已接受事实先于完成；Future已接受后，后继安装为INFLY，不能再次下发。
- 硬件Stream Map不保存PC、recv和VCID；仲裁获胜后从LUT取得命令属性。模型PC缓存的寄存边界仍待统一。

普通建槽即绑定UID；SELF_START先匿名，Task0合法完成才绑定。SID重用必须清除旧生命周期的完成、claim、方向记录和UID有效状态。

#### 多源写入的原子性

Map每槽按字段计算下一值。Completion与Skip同SID不同TID可以同拍OR，不丢任一路。Current完成、合法UID/PID副作用与所属Completion一起提交。TG只在目标冲突或生命周期失效时整笔抑制，不能将同SID所有写一律排队。

Issue、raw_accept与TG同拍安装按最终Current身份处理，使已接受目标INFLY；目标同拍完成则FINISH。方向Grant只有在等待身份仍匹配时提交。RMEM返回单独恢复额度，与完成位更新独立。退休／重生保护旧用户生命周期，旧Completion、Candidate和TG不能写到复用后的SID。
### 同SID并发例子
假设Current为Task3，同拍出现Task7的DataIn接受、Task3完成和Task4的TG安装。Map先合并完成位，再按获准TG更新Current，Task7的接受记录继续保留；最终不能因TG整项覆盖而丢掉Task7的事实。若同拍安装的就是Task7，安装状态应为INFLY，若Task7也同拍完成则为FINISH。

硬件合同按字段写使能合并，不由旧稿“十四口固定优先、同SID只能写一笔”定义。模型的请求/accepted与分配代次是确定性实现方式，不能据此推导硬件握手。

### 建表

Trigger输入为UID16、PID8、reissue1和valid/ready。保留的dataout_tid6不使用。Router在未握手时保持请求全部字段；Lookup无法接入时反压。

UID查询只匹配entry_valid且uid_valid的行。响应包含hit、SID、`completion_bitmap | datain_claimed_mask`与捕获资格。hit固定当前分配，miss在提交时才获得SID；捕获资格不代表Create已成功。

Prepare使用保存的PID、SID和排除位图查LUT，选择完整有效、同PID且未被排除的最低TID，保存PC、task_type和partner_tid。用户完成或claim使排除信息变化时，先寄存新快照，再重查。Pending/Prepare正在使用的SID与UID查询结果受到退休保护；miss事务也须保留分配空间的使用资格。

Broadcast/reissue0提交搬入Candidate和配对搬出Skip；P2P/reissue0提交双Skip；reissue1提交搬入Candidate，无Skip。普通miss无论是否需要Candidate均创建用户，Current从Task0起，不能从触发的Future TID起步。

Create、Skip、Candidate和claim原子提交，SID一致。Skip送Task Done直接转发，credit_skip只取消已有行的credit wait，不能替代64位完成Skip。Candidate置claim不置completion。Skip-only无需Candidate空位，但仍受Lookup/Prepare和生命周期限制。

Candidate Hold只有1项，字段为bypass、UID、SID、TID、PID、PC。DTE Arbiter接入Fire Hold即交接所有权，允许同拍旧候选移出、新候选写入。候选valid/字段在等待中保持。

普通DataIn被Core真正接受时，Arbiter复核SID仍有效并读取最新Current TID。TID匹配Current产生INFLY Issue；Future不覆盖Current。每次普通DataIn接受都产生raw_accept SID/TID，TG搜索token、同拍安装和已提交Current共同使用该事实。

安装目标已被接受而尚未完成的DataIn时，初态为INFLY；目标已完成或Skip则取消本次安装后重搜。反压期间Future转Current也按实际接受拍判断。claimed仅用于入口排除，不能代替这些接受事实。
### 同PID连续包的例子
同一用户的LUT在Task7和Task8使用相同PID。第一包被捕获后claim Task7，第二包应选Task8，即使第一包尚未完成。用完成位单独排除会重复选择Task7。

miss事务一律从Task0建立Current。Trigger可以指向Future DataIn；它只决定该包的Candidate和Skip，不决定主线从哪个Task开始。

### 选最老发射

DTE、MU、VU各从Head起环形扫描READY且send_unit匹配的有效槽。各路每次只保持一笔命令，彼此反压独立。MU/VU按实际PID带VCID；DTE需要VCID的Stream命令按实际PID查询，DataIn、Bypass、权重VCID=0。

DTE的normal集合同时包含Stream候选和普通DataIn。SID不同按年龄选，SID相同由DataIn Bundle拥有该候选。normal/Bypass采用二源RR，装入Fire Hold后偏好切到另一源，复位优先normal。权重最高优先，不改变RR。

Fire Hold包含PC32、UID16、SID4、TID6、PID8、VCID2及valid。Core valid与ready同拍有效才接受一次；等待时保持全部字段。普通DataIn持有时持续复核Map分配，缺响应或分配失效不拉task_valid，继续持有；系统保证正常生命周期不会撤销已持有命令。

Core接受产生matching SID/TID的Issue，无内部Ready或重试队列，Map必须同拍接入。Completion/Skip命中该任务时优先处理其完成。接受后回IDLE再选下一笔，不将旧模型的Issue accepted延迟作为硬件要求。
三单元各有独立Fire Hold，同拍可接受三笔任务。同一SID的DataIn优先于普通Generated；normal与Special Bypass之间使用RR避免一方长期饿死。已进入Hold的命令保持PC、UID/SID/TID、实际PID和VCID，不能因上游表内容变化而改写。

Core接受是valid/ready同时有效；TS的Issue提交保存这次事实，不能因为Map暂未接受状态请求而重复向Core发送。Reduce许可已在REDUCE_WAIT阶段取得，不在raw_accept时再扣。

### 推进度与退休

Core ACK各有UID16、SID4、TID6、PID8和valid；DSA ACK各有UID16、SID4、TID6和valid。六路各周期独立接收，没有Ready。无效SID对应的本地ACK不生成完成。原文不要求比较ACK UID和Map UID；UID载荷的合法性由系统保证。

recv_unit的本设计基线为00只认Core、01只认DSA、10收齐同执行单元两路。双ACK分别进入该单元的Core/DSA FIFO，深度16，各保存UID/SID/TID。队头SID/TID相同才同拍弹出并生成一次配对完成，UID取Core侧。空FIFO允许输入直通，与另一侧队头同拍配对；同拍弹出后可继续收新ACK。

两侧顺序由系统保证一致，任一侧先到都合法，FIFO不溢出是系统容量合同。队头不匹配不得跳过去找任意相同SID/TID。Core-only、DSA-only、配对完成各执行单元独立输出；原文后续表给出九路有效完成加一路固定无效的Router兼容通道，旧六／七路示意已过时。

Completion提交SID/TID/UID及合法PID副作用，Map同SID按位OR累计。Current完成将状态改为FINISH；Future仅置对应位，不改Current。Task0合法Completion绑定SELF_START匿名UID，Skip不绑定UID；若Task0要求双ACK，配对完成后才绑定。

PID_UPDATE只接受Current、type5、Core-only完成的PID载荷。pid_pending置1；直接相邻后继实际安装时继承PID并清pending。TG安装被抑制则保留pending；相邻后继已完成/Skip时所选更后任务用自己的LUT PID。新PID值不由TS另作动态合法性检查，软件保证路由配置完整。

RMEM输入仅UID16/valid，无Ready。匹配entry_valid且uid_valid的用户后输出独立SID归还，恢复rmem_credit。它不读取Current TID、不比较PID/TID、不置Completion。每次Reduce应归还一次；返回同拍不直接触发重新占用。

有效槽Current为FINISH且自身不是End时，TG形成64位搜索掩码：Current之后、through-End之内且completion未置位。最低位作为target_tid/onehot，连同原Current身份保存进PE token。空掩码不查询、不安装，交退休检查处理。

下一周期16路TG分别按token查LUT。复核Current身份、kill、配置有效性、同拍Completion/Skip及DataIn接受旁带。命中目标的完成/Skip取消安装；仅完成其他TID可与安装合并。生命周期被退休或替换时取消在途token。

安装含next_tid、实际PID、send_unit、end、初态和credit_drct，SID由通道号确定。DataIn进入WAIT或已接受的INFLY；Reduce进入REDUCE_WAIT；有新增方向需求进入WAIT_CREDIT；其余READY。PC／VCID缓存边界等待原文统一，不将某一旧图的组合查询串入另一个版本的寄存时序。

Head须有效且UID有效、through-End所有位完成、RMEM空闲，无DataIn Pending/Prepare使用其查询结果。普通退休Hold保存valid/SID/UID，内部ready在顶层固定1；外部仅UID/单拍valid，Router无条件接收。退休通知不自动加回TS三方向计数，各方向仍由返回输入归还。

SELF_START首次Trigger设置core_started、Head=0、Tail=N−1，激活N槽匿名Task0 READY。其后Trigger不重复初始化。Task0完成绑定UID后参与正常退休资格检查。最后完成先写入Map，下一沿在旧Head SID重装Task0，清UID有效、pending、completion、claimed、drct_used，恢复RMEM可用并推进Head/Tail到队尾。重生不发普通用户退休通知。
### 完成、数据可用和RMEM释放分别观察
Reduce的Core/DSA双ACK完成本地Task，并允许生成后继。需要读归约结果的计算仍等待对应DataIn Task完成。RMEM输出尾拍交付后按UID归还许可；该返回不设置TID完成位。用户退休同时等待全链完成和RMEM归还。

TG对16个SID并行搜索后继：search = after_current & THROUGH_END_MASK & ~completion_bitmap。搜索先寄存，下一周期查LUT并复核；连续Skip不增加搜索次数，分配变化或位图变化会使旧token失效。

## 三处复杂性

上面四个动作假定的是一条直线：数据按任务链的顺序到、下游总能收下、用户数不超过 16。三条假定都不成立。三处应对不是三套独立机制，是四个动作在这三种约束下的变体：

* 第一处：改判就绪的依据
* 第二处：判就绪加一个条件，推进度加一个可跳过
* 第三处：改建表的触发方式，改就绪依据的存放位置

### 数据不按链序到达

DataIn由数据到达驱动，主线Current按依赖推进；两种顺序分别记录。dot Core的token、chip归约结果和七段concat可能在不同顺序到达，不能等Current走到某段才接收。

1. Trigger先Lookup用户，再按PID和完成/claim排除位图选最低匹配DataIn。
2. Candidate交给DTE Hold时转移所有权；实际Core接受记录接受事实。
3. Future完成只设置自己的完成位；主线到达时可跳过，Future已接受未完成时安装为INFLY。
4. Hold、入口资格或资源不足仍可反压，数据到达并不保证当拍执行。

### 下游收不下

#### 为什么是逐跳 credit

* 端到端 credit 要经过整条路径的往返延迟才能释放
* 路径长到一定程度，16 个 stream 的执行耗时盖不住这个延迟，就会出空泡，吞吐随路径变长而衰减
* 粗算下来端到端 credit 大概只够隐藏 C2C 两跳
* 逐跳 credit 把一段长往返切成每跳各自的短往返，稳态吞吐与跳数无关，代价是要处理中途的阻塞

#### 发送分两道门：首次查 stream credit，之后逐 flit 看 VC credit

credit 的单位是 **stream**，不是 task：Core Mem 空间按 stream 申请和释放。发送前先看这个 user 在目标方向上是否已经持有资源，两种情况走两道不同的门：

| 该方向的用户资源 | 走哪道门 | 挡住发送的是什么 |
| - | - | - |
| 尚未持有 | 用户资源门控 | 查下游 stream credit，够才占用一个表项 |
| 已经持有 | 发送就绪门控 | 不查 stream credit，只受 VC credit 与链路握手的约束 |

因此同一个 stream 的任务链里，Router **只在第一次往下游发数据时检查 stream credit**。第一次满足之后下游就有了落脚点，后续发往同一下游的 DTE 任务都走发送就绪门控。

**免检的只是 stream credit，VC credit 每个 flit 都要查。** stream credit 说的是下游 core 的 Core Mem 给这个 user 留了落地空间，不说明通路是通的。第二笔起的每个 flit 照样要查目标方向那个 VC 的 credit，下游 VC Buffer 满了就发不出去。

是否已持有按每个出方向各自独立记录。一次 fork 涉及多个方向时，先滤掉已持有的方向，**只对剩余未持有的方向查 stream credit**，全部方向都已持有则本次不查。待申请的这个子集要全部成功才发，任一方向不足则整体不发，已持有的方向也一起等，避免重复占用表项与数据重复。

检查的发起方分两种：

* **本 core Core Mem → 下游 Router**：属于任务链里的 DTE 任务，由 TS 查下游 credit
* **本 core Router → 下游 Router**：不属于任务链里的任务，即使本 core 没有任何任务它也会自动执行。数据何时到来只有本 core 的 Router 知道，因此由 Router 自己查下游 credit 并触发阻塞重发

#### 多个上游抢同一个下游的 stream

Broadcast 与 Reduce 走的路不完全一样，会出现 core1 要申请 core3 的 stream、core4 也要申请 core3 的 stream 的情况。PPTP 切中间列 chip、DP 切分的合流点、以及软件自己扩展出来的“先 DP 再合流”，都是同一件事。

核心是：**core 之间实际组成的是顺序流水线，要抢同一份资源，分流和合流就必须按同样的用户顺序**。只要多个上游按同一个用户顺序申请，下游释放时统一广播，各上游就可以各自维护自己那份 credit，不需要集中仲裁。

举个例子。两个上游按顺序向同一个下游申请同一份 stream 资源，假设广播流发得很快、reduce 流发得很慢。广播会先在下游 core 上建出 4 个用户的任务链，core 自己调度执行；但下游也要收 reduce 的数据，任务链上必然有一个 reduce 接收任务，收不到这个包任务链就不会删。等 reduce 任务做完、任务链结束、释放这个用户的 stream 资源时，这个用户在两个上游的表里一定都有记录，所以两边都能正确回收。

三个办法里选了前两个：

| 办法 | 结论 | 说明 |
| - | - | - |
| 编程模型约束：算法划分时保证不会乱序申请同一份资源 | **选中** | 数据流规划时让合流位置收到任意一种包都按同样的用户顺序；合流前是 DP 场景的，给每个上游平均分 credit，根本不抢同一份 |
| 合流位置先用 Matrix Mem 缓存 | **选中** | Matrix Mem 容量大，可以用软件流控，把“资源变少”变成“资源够多，不抢同一份” |
| 资源申请集中放到下游统一分配 | 否决 | 申请要跨 C2C，单用户在 core 上的生命期会多出约 800T，很可能压住吞吐 |

遇到坏 core（中间两列 chip 的 core2、core7，只有 Router 能用）时：

* 它的 Router 处在透传档，只按路由表转发，只查下一跳的 VC credit，**不查 stream credit、不支持阻塞重发**
* 上游要查的 stream credit 对应的是它之后那个落地的 core
* 下游返还的 release 也跨过它直接给上游

#### 用户 token 重发（Broadcast Reissue）

1. 软件把 broadcast 的搬入配成 Broadcast 重发的搬入（`TASK_TYPE = 2`），再配一项与它配对的搬出（`TASK_TYPE = 1`、`TASK_CREDIT_EN = 1`），两项都在主线任务链上
2. broadcast 数据到达 router trigger TS 时，trigger 带着下游收不收得下的判断：`reissue = 0` 表示收得下，搬出那一项在这一刻就并进 `done_bitmap` 跳过；`reissue = 1` 表示要重发
3. 要重发的用户走到搬出那一项时向Credit Ctrl申请尚未持有的方向许可，授权后下发，由 DTE 从 Core Mem 把 token 搬回 router
4. 重发标记有效但未重发成功时，该用户的原始 token 数据**不能被覆盖，也不能释放该用户**

#### P2P 重发

软件把 bypass 本 core 的一段配成两项：搬入（`TASK_TYPE = 3`、`WAIT_WAKE = 1`，`TASK_P2P_REISSUE_TID` 指向搬出）与搬出（`TASK_TYPE = 1`、`TASK_CREDIT_EN = 1`）。

* **不需要重发**（`reissue = 0`）：trigger 那一刻搬入与搬出两项都并进 `done_bitmap` 跳过，不派 DTE；这个用户是新用户时照样建表
* **需要重发**（`reissue = 1`）：
  * 搬入由 router 请求直接驱动，登记进 DataIn_task_table 做搬运
  * 搬出等前序任务做完、执行到这一项时等待Credit Ctrl满足新增方向需求，原子授权后标记READY等待下发

#### P2P 阻塞缓冲

原始通信机制提出以下需求；TS详设尚未冻结相应寄存器、接口和与现有资源计数的连接。以下作为待统一需求保留，不能作为已实现或已冻结的合同。

为防止 P2P 传输阻塞导致死锁或性能下降，设一个保底的“P2P 阻塞进 core mem”机制。该需求包含四项：

* 开关
* 分配给 P2P 缓存的 core mem 容量
* 开启的方向，最多 **3 个**
* 每方向的容量与项数

候选方案要求TS维护：

* 每个方向一张 P2P 阻塞缓冲映射表：`p2p vld | User id | Down direction | Data addr`
* 对应下游 core 的 credit 计数器

走的流程：

1. 上游某方向的 P2P 数据到达 router，下游无资源
2. 数据搬到该方向的缓冲地址并记录表项
3. 下游 credit 释放后，发起一个 TS 调度 DTE 搬数据到 router 继续传输的 task
4. 通知上游释放 credit

#### Reduce 任务的 credit

Reduce type=4只使用本SID的独立RMEM许可，credit_en取0或1都不能改变资源种类。安装REDUCE_WAIT后，取得许可时清可用位并READY。每用户同一时刻只容纳一个归约任务；前次空间返回后才能再次授权。

RMEM每用户32KiB按FP32累计，可容纳8192个元素。一笔归约超过上下文容量时，软件必须规划多个顺序任务。一个TS任务包含多个DTE搬运条目时，仅最后条目开启ack_ts_en；它不允许跨过本级RMEM任务边界。

当前模型允许已准入用户的网络分量提前到达，但只接最早未完成的Reduce；物理接收预留与TS许可位的精确寄存衔接待硬件确认。

#### 超前发送窗口：主动压住发送速度

原始通信机制提出以下需求；TS详设尚未冻结相应寄存器、接口和与现有资源计数的连接。以下作为待统一需求保留，不能作为已实现或已冻结的合同。

上面几档都是被动的：下游收不下了才想办法。还有一档是主动的：**不等下游满就先慢下来**。

要解决的问题：一条“广播 → P2P → 广播”的路径上，前半段广播跑得比后半段快时，后半段 core 的 Core Mem 收不下，数据在物理通路上排队。排队本身不致命，致命的是它把后半段 core 的输入通道占住，让本该马上开算的用户等在路上，后半段 core 出现计算空泡。

判断依据是一个 TP / PPTP 区域内每个用户在每个 core 上的**计算量与计算时间基本相同**，因此看一个 core 的进度就能推算同区域其他 core 的进度。原文举的例子是 Core2 与 Core4 同一时刻在算的 `user_id` 相距 5～6，Core2 在算 user10 时 Core4 大致在算 user4 或 user5。

利用这一点，在 Broadcast1 区域的最后一个 core 上就能推算出 Broadcast2 区域第一个 core 的进度，据此推迟发起 P2P 传输：

1. 软件为这条 path 在这个 core 上配一个“流量控制使能”，再配一个允许超前发送的用户窗口尺寸 `N`，`N` 在编译期确定
2. TS 查本 core 内正在计算的 `user_id = M`，阻塞后续 `user_id ≥ M + N` 的传输
3. `user_id = M` 的计算任务完成后，重新唤醒 `user_id = M + N` 的传输

原文举的例子：Core2 在算 user10 时最多发起到 user(10+N) 的广播，user(10+N+1) 要等 Core2 开始算 user11 才发出。

原文的≥边界与“可发送到M+N”的例子存在差异，边界条件须先统一，不能同时作为实现断言。

这一档只对 TP / PPTP 内部的传输有意义，跨 TP 组的传输不适用，因为跨组的计算时间不可推算。`N` 该取多大要靠模型量出同一 TP 组内各 core 的实际进度差。

### 用户数远超 16 项

B/R Core把“数据在Matrix Mem中的驻留”与“计算任务占用TS槽位”分开。
- B Core每份token包含6144B数据、192B scale、256B topK，逻辑6592B；软件槽跨度6656B，按256B对齐。36MiB MM可放5671槽，32KiB ShareMem的标志/用户表将当前配置限制到4085槽。
- R Core每半槽0x3080B，每用户两半；36MiB可放1520个用户槽。当前payload另保留16B归约兼容前缀，其与硬件sw_aux的关系仍TBD。
- TS只提供N≤16个并行计算槽，软件队列决定哪个已ready用户被绑定。

首Trigger批量激活N个匿名Task0，同时生成独立Bypass搬入。链一DTE接收数据、等待写响应并设置ShareMem完成flag；链二MU RV Core轮询软件表或ready用户FIFO，合法Task0完成才绑定UID，再下发后续DTE。

B Core按接收/转发序号计算环形槽位置；R Core按UID与half定位两半，只有需要的分量都已写完才入ready流程。软件用户FIFO按集齐顺序，而TS在已激活计算槽间按年龄仲裁，两者不能混为一张队列。

Head全链完成、RMEM归还且无DataIn占用后，SELF_START在下一沿原地重装匿名Task0、清生命周期状态并排到队尾；不向外发送普通用户Retire。当前模型另用内部通知清旧UID空闲RMEM上下文，该通知不构成外部新增接口。

## 异常与时延

### 异常检测

配置非法通过APB/TS_STATE报告，失败配置可修正后重新提交。运行期还需检测重复ACK、非法SID/TID、无匹配PID和用户长时间不退休。完整超时阈值、异常码与中断编码尚未冻结，应分别记录协议断言与软件可见异常。

权重加载丢弃新ACK并暂停既有配对FIFO；合法Special Bypass ACK按保留身份过滤。不能把这些正常过滤路径统计成业务Task完成。

### 参数

| 结构 | 基线 |
| - | - |
| Task LUT／RouterTable | 各64行 |
| Stream Map | 16物理槽，启用N=1～16 |
| Lookup／Prepare／Candidate | 入口各自保留事务；Candidate1项 |
| TG | 16路，各自搜索token |
| 双ACK FIFO | 三组×两侧×16条，每条26bit身份 |
| 方向计数／请求 | 三个5bit计数，16个Pending |
| RMEM许可 | 每SID一位 |
| Fire Hold | DTE/MU/VU各1项 |
| 普通退休Hold | 1项UID/SID/valid |

普通DataIn无反压最短示例为E0保存入口、E1Prepare、E2提交Candidate、E3Fire Hold、E4Core接受。Reduce许可示例为E0进入REDUCE_WAIT、E1占RMEM且READY、E2Fire Hold、E3接受。特殊Bypass最快E0Candidate、E1Fire Hold、E2接受。实际延迟还受对应Hold、执行单元和资源反压限制。
Candidate Hold、Fire Hold、TG搜索token、ACK FIFO和Retire Hold分别占有资格或状态，不能用单个“调度延迟”覆盖全部排队。通信机制中的P2P缓冲方向数≤3与发送窗口容量作为待统一参数保留。

### 三套时延数字不是一回事

| 时延 | 来源与口径 | 使用方式 |
| - | - | - |
| 2～3 cycle | 旧TS MAS的局部硬件目标 | 只作目标，不能当完整Trigger到接受延迟 |
| 16T / 21T / retire 5T | Top模拟器的旧端到端估算，含软件往返 | 与当前逐拍调度分开记录 |
| Lookup/Prepare/Candidate/Fire Hold/accept | 详设寄存路径 | 分事件统计实际排队 |
| RMEM许可 | E0安装REDUCE_WAIT，E1扣占/READY，最快E2 Hold、E3 Core接受 | 归还同拍不可复用 |
| 方向许可 | 模型采用E2提交，原文存在E3场景 | 扣账、drct_used和READY同次提交 |

无反压普通DataIn最短示例为E0入口捕获、E1 Prepare、E2 Candidate、E3 Hold、E4接受。它是路径示例，不保证所有事务固定五拍。

## 取舍

### DataIn与Current分别记录
先到包如果等待Current，会长期占住Router入口。独立Candidate、claim和接受事实允许搬入提前；代价是需要防止Future被重复选择，并在TG安装时合并已发生事实。

### 完成与资源释放分别记录
本地双ACK表示执行条件满足，RMEM返回表示物理空间可再次授权；相应DataIn表示结果已经落地。把三者合成一次完成会失去资源保护或数据依赖。

### 归约接入的两种软件/模型方案
Core Mem暂存再发两操作数可由本地链序保证归约顺序，但每token增加一笔搬入与一笔读出。直接接RMEM减少搬运，必须阻止后续归约早于前次任务，且物理预留与TS许可的衔接待统一。当前模型采用直接接入，不将旧暂存方案的图和任务号当作现行配置。

### Head退休与双链软件队列
Head-only使年龄有确定基准；代价是年轻已完成用户也可能等待。B/R Core另用大容量MM和软件ready队列缓解16槽限制。SELF_START本地重生与普通Retire有不同通知语义。

### 逐跳资源和超前窗口
逐跳credit缩短往返覆盖距离；合流必须保持用户申请顺序，坏Core只透传。发送窗口根据同TP组计算进度主动减速，能避免被动Reissue产生长队，但寄存器与授权连接尚未冻结。

### 固定Task LUT与配置变更
64项全序LUT便于优先编码和有限状态控制；代价是软件先做依赖排序、换场景重新配置，且运行期不支持热重配。
