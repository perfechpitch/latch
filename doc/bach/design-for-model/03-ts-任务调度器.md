## TS 解决的问题

* core 里三个执行单元（DTE / MU / VU），每个单元前面挂一个顺序执行的 RV core
* 一个用户走的不是一次运算，是一串跨单元的操作：搬进来 → 算矩阵 → 算向量 → 搬出去
* 最多 16 个用户同时在 core 里，各自走到不同的位置

从各切分场景归纳出三条：

1. 每个用户的任务流由多个不同执行单元的操作顺序串联而成
2. 各场景的 core 内任务流固定，任务类型不多，变化少
3. 同一场景的 core 内，不同用户执行的任务流相同，用户间顺序执行

三条各定下一件事：

* 第 1 条 → 必须有人管住每个用户内部的先后
* 第 3 条 → 多个用户可以在三个单元上错开流水
* 第 2 条 → 这件事不必交给软件

> **取舍**：任务流固定、任务类型不多，硬化调度器足够覆盖，因此不做软件调度。代价是任务流的形状被写死在 64 项的表里，换场景要重配；换来的是调度延时压到 2～3 拍。

**TS 是一块固定的硬件逻辑，不是可编程的调度器。**

* 行为由上电时 SCP 经 `ctrl_noc` 配下来的几张表决定
* 配完写 `TS_INIT_FINISH` 就按固定逻辑跑，运行期不接受软件干预，也没有指令可执行
* 软件只能改配置：换一套 `task_chain` 换一条任务流，改 `CORE_TYPE` 换一种工作模式
* core 里真正跑软件的是三个 RV core，TS 只负责把 task 派给它们

TS 的全部工作收在两张表和四个动作里。

* **两张表**
  * `task_chain`：静态。软件初始化时按 core 的角色配好，说清这类 core 的操作流长什么样
  * `stream_table`：运行时。硬件维护，说清每个在途用户走到了哪一步
* **四个动作**
  * 建表：新用户到了占一项
  * 判就绪：当前这一步的前置条件齐了没有
  * 选最老：同一个单元有多个候选时选谁
  * 推进度：收到完成事件把用户推到下一步，走完退休

### TS 的四种工作模式

由两个配置项选定，共四种，**上电配好之后运行期间不变**：

* `CORE_TYPE`：普通 core / B core / R core 三选一
* `DATAIN_TASK.WEIGHTS_MODE`：独立开关

| 模式 | 怎么进入 | TS 在这个模式下做什么 |
| - | - | - |
| **weights 加载** | `WEIGHTS_MODE = 1` | **不启动 task_chain**。只有 datain_task 工作，router 来了数据就派给 DTE 搬运，不建 stream 表项、不推进任何任务链。这是上电装权重的阶段 |
| **普通计算 core** | `CORE_TYPE` = 普通，`WEIGHTS_MODE = 0` | 完整的四个动作：router trigger 建表、按 task_chain 逐 task 推进、三条通路发射、完成后推进度并在链尾退休 |
| **B core** | `CORE_TYPE` = B core | 复位后**直接自启动 16 个表项**，不等 router trigger。datain 收到的数据不建表，完成标志由软件维护在 Share Mem 里；task_chain 上的 task 0 循环查那个标志，查到才往下走 |
| **R core** | `CORE_TYPE` = R core | 同 B core 的自启动与双链结构，区别在 task 0 查的是“两笔数据是否集齐”，因此推进顺序由软件映射表决定，不是 TS 的年龄优先 |

分成两类：

* **数据驱动**（前两种）：TS 等 router 把用户送进来
* **自驱动**（后两种）：TS 复位后把 16 个槽位全部占满，让 RV core 循环去查软件维护的标志

自驱动是被 B core 与 R core 的用户数逼出来的，细节见“用户数远超 16 项”。每种模式下 `task_chain` 与 `datain_task` 各自怎么配，见下一节的配置差异表。

## 两张表

### task_chain：软件配好的操作流

最多 **64 个 task**，软件初始化时通过 `core_noc` 配置。每个表项 64 bit：

| 位域 | 名称 | 含义 |
| - | - | - |
| 31:0 | `TASK_PC` | 任务执行的起始 PC |
| 33:32 | `TASK_SEND_UNIT` | 执行单元：00=DTE，01=MU，10=VU |
| 35:34 | `TASK_RECV_UNIT` | 完成类型：00=只调 RV core 不调 DSA；01=调 DSA；10=调 DTE DSA + Router 上的 Rmem 模块 |
| 36 | `SELF_START` | 自启动（B core、R core 的链首 task） |
| 39 | `WAIT_WAKE` | 需要外部数据唤醒 |
| 40 | `TASK_Broadcast_REISSUE` | 标识该 task 是 Broadcast Reissue 任务 |
| 41 | `TASK_P2P_REISSUE` | 标识该 task 是 P2P Reissue 任务 |
| 42 | `TASK_REDUCE` | 逐级 reduce 任务 |
| 43 | `TASK_CREDIT_EN` | 是否需要 credit 才可发射（core 内 DTE 从 MM 搬到 CM 就不需要） |
| 44 | `TASK_EXE_MASK` | 按 user 区分执行 / 不区分 |
| 50:45 | `TASK_PATH_ID` | 任务匹配的 path_id，用于 TS 判断该任务的 credit 条件 |
| 51 | `TASK_END` | 任务结束标识 |
| 63 | `TASK_VALID` | 软件写该寄存器后硬件自动置有效 |

`DATAIN_TASK` 是独立的一项寄存器：

* 只有 1 项，只能绑定 DTE
* 四个字段：`TASK_PC`、`TASK_UNIT`（固定 DTE）、`WEIGHTS_MODE`、`TASK_VALID`
* `WEIGHTS_MODE` 置位表示处于 weights 加载阶段，此时不启动 task_chain

其余配置寄存器：

* `STREAM_NUM`：1～16
* `TS_INIT_FINISH`、`TS_STATE`
* `CORE_TYPE`：B core / R core / 普通 core
* `B_CORE_DIRECTION`：B core 的广播方向，TS 查这些方向的 credit

#### 配置的下发顺序与硬件响应

软件通过 `core_noc` 按下面的顺序写，最后一步之前硬件不做任何检查：

1. 先写全局项：`CORE_TYPE`、`STREAM_NUM`、`B_CORE_DIRECTION`
2. 逐项写 `task_chain[i]`。**每写一项，硬件自动把该项的 `TASK_VALID` 置起来**，软件不必单独写这一位
3. 写 `DATAIN_TASK`（普通 core 可以跳过，见下一小节）
4. 最后写 `TS_INIT_FINISH`

硬件看到 `TS_INIT_FINISH` 后做两件事。

**一是查五项合规性**，结论写进 `TS_STATE` 供软件读回：

| 检查项 | 不合规的情形 |
| - | - |
| 是否配置 | `task_chain` 与 `datain_task` 一项都没配 |
| 多笔 END | 一条链上出现多个 `TASK_END` |
| VALID 不连续 | valid 的项中间有空洞，没有从 0 起连续排列 |
| 多笔 SELF_START | 一条链上出现多个 `SELF_START` |
| 普通 core 出现 SELF_START | `CORE_TYPE` 是普通 core 却配了自启动 |

**二是派生三张 64 位掩码**，供 `Task_ctrl` 一拍算出 SKIP_MASK：

```
DATA_IN_MASK[i] = task_chain[i] 是 datain 任务
REISSUE_MASK[i] = task_chain[i].TASK_Broadcast_REISSUE 或 TASK_P2P_REISSUE
END_MASK[i]     = task_chain[i].TASK_END
```

* 三张掩码是 `task_chain` 的纯函数，配完不再变
* 运行时的跳过判断只查掩码与 `done_bitmap`，不必逐项回读 `task_chain`

`CORE_TYPE` 是 B core 或 R core 时，硬件在复位后**直接自启动 16 个表项**：

* 每项按 task 0 的属性建立，`task_fsm` 置 `TASK_RDY`
* 此时还没有用户信息，等自启动任务（RV core）返回 `user_id` 后再补进表项

#### 每种模式下的配置差异

| | `datain_task` | `task_chain` 上的关键配置 |
| - | - | - |
| **普通计算 core** | 不用手动配，TS 自动把 chain 里的 datain 任务（Broadcast、P2P）调度过去 | chain 里的 datain 任务统一标 `WAIT_WAKE = 1`；要用 Core Mem 阻塞重传就再配一笔 `TASK_Broadcast_REISSUE = 1` 且 `TASK_CREDIT_EN = 1` 的重发 task；链尾的逐级 reduce 任务配 `TASK_RECV_UNIT = 10`（等 Router 的 Rmem 回完成）与 `TASK_END = 1` |
| **B core** | **必须手动配**，它是那条一直从 GPU 收数据进 Matrix Mem 的链 | task 0 配 `SELF_START = 1`、`TASK_RECV_UNIT = 00`（不调 DSA，RV core 循环查软件 flag）、`TASK_EXE_MASK = 1`（不区分 stream）；搬出的链尾配 `TASK_CREDIT_EN = 1`，按 `B_CORE_DIRECTION` 查下游 credit。**chain 里不能再配 DTE 的 datain 任务**，否则会影响那条收数据的 datain_task |
| **R core** | **必须手动配** | 同 B core：task 0 `SELF_START = 1`、不调 DSA、循环查映射表；chain 里同样不能再配 DTE 的 datain 任务 |
| **DP+P2P reissue core** | 不用手动配 | P2P 重发拆成 datain 与 dataout 两笔 task，都配 `TASK_P2P_REISSUE = 1` 与 `TASK_CREDIT_EN = 1`；按用户是否参与计算区分 `TASK_EXE_MASK`，计算任务配 1、纯透传的 P2P 任务配 0 |
| **weights 加载** | 只配 `datain_task`，`WEIGHTS_MODE = 1` | 此时**不启动 task_chain**，数据搬运由 DTE 直接完成 |

#### 表项里的三组字段

一项里的字段按变化的节奏分成三组。

* **用户级的标记**：建表时写入，整条任务链期间基本不动
  * `valid`：槽位有效
  * `user_id`：跟随 router 请求写入
  * `reissue`：这个用户有某笔任务要等下游 credit 才能搬
  * `compute`：DP+P2P 场景下这个用户要不要做计算
  * 老用户再次被 trigger 时只可能改 `reissue`，当前任务、状态、完成位一律不动
* **进度**：这个用户走到哪了
  * `task_id`：链上的第几步
  * `task_fsm`：这一步的状态
  * `done_bitmap`：64 位对应 64 个 task，哪一位亮就表示那一步的数据已经齐了
  * 异步 datain 提前完成，就是 `done_bitmap` 上某一位先亮、而 `task_id` 还没走到那里
  * 三个字段合起来才是完整的进度，缺一个都判断不了下一步能不能发
* **当前 task 的属性**：`task_unit`、`task_dsa_en`、`task_pc`、`is_reissue`、`end`
  * 不由软件单独配置，每次更新 `task_id` 时索引 `task_chain` 得到，随 `task_id` 一起被覆盖
  * 摊平存在表项里而不是每次现查，是为了让三条发射通路不必为每个候选都查一次表

#### 六个写口的原子性

* 这张表是被动的存储模块，写逻辑留在各模块里，只有六个写口本身在这里仲裁
* 每个写口一拍一笔，请求保持到 `accepted` 才算生效
* 写失败分两种处理：
  * `create`、`install` 这类整项写入：失败后要重读最新表内容再来
  * `issue` 这类只改一个字段：失败后只重试这一笔写，**不能重新下发已经被 RV core 接收的任务**
* 同一拍多个写口冲突时按端口的固定优先级排队，具体次序见 TS 建模单元的时序图

## 四个动作

### 建表

**数据进来这件事由 Router 直接通知 TS**，走 `router2ts_trigger_ch` 这条硬件通路：

* 不经过 RV core，也不经过任何软件环节
* Router 的 CoreStation 收满一个包，按接收包头的顺序把 trigger 发给 TS
* 请求里带 `user_id`、`path_id`，以及这一笔要不要重发的标记
* 这是 TS 被激活的唯一入口。例外只有 B core 与 R core 的自启动，它们复位后就把槽位占满

`User_Match` 拿请求里的 `user_id` 与 stream_table 里的比对：

* **没匹配上**：新用户，向 Stream Map 发起建表请求
* **匹配上**：老用户，复用原来的 stream_id，不改它当前的任务、状态、完成位
  * 只有一种情况会动表项：请求带着重发标记时，把该项的 `reissue` 置起来

四条同时满足才建表：

1. 判定是新用户
2. 当前不在 weights 加载模式
3. `trigger_task_chain_en` 允许启动任务链
4. `tail_ptr − head_ptr < stream_num`，否则并发用户已达上限，请求在入口等着

满足后：

* 在 `tail_ptr` 指向的空槽**一次性写入**用户信息、Task 0 的状态与全部属性，随后推进 `tail_ptr`
* Task 0 的初始状态按类型定：datain 或 reissue → `TASK_WAIT`；`self_start` → `TASK_RDY`

Router 的请求还统一缓存到 `DataIn_task_table`。这张表**只有 1 项**：

* 空闲时把 datain 任务信息与请求信息一起登记进去
* 被占住时反压 Router 的新请求
* 任务仲裁成功并被 DTE RV core 接收后，该项立即释放

两处细节：

* 两种 PC 的去处不同：Task 0 的 `task_pc` 进 stream_table，datain 的 `task_pc` 进 DataIn_task_table
* B core 与 R core 的 datain 任务**不建表**，见“用户数远超 16 项”

### 选最老发射

三条发射通路各自独立打拍，同一拍可以并行下发 3 个 task。

| Arbiter | 候选 | 优先级规则 |
| - | - | - |
| `MU_Arb` / `VU_Arb` | `valid=1 && task_fsm=TASK_READY && task_unit=MU/VU` | 从 head_ptr 开始环形年龄优先，选最老 Stream |
| `DTE_Arb` | Reissue 任务 | 优先级最高，从 head_ptr 选最老的 Reissue |
| `DTE_Arb` | DataIn 任务 vs 普通 Generated 任务 | 没有 Reissue 时，两者按相对 head_ptr 的 Stream 年龄比较，较老者优先；同一 Stream 时优先选 Generated |

选中后**非抢占保持**：

* 锁定任务上下文，命令与相关字段保持稳定，直到对应 RV core 返回 `raw ACCEPT`
* RV core 的 task 队列满时会反压

收到 `raw ACCEPT` 后的处理，两类任务不同：

* **Generated 任务**：向 Stream Map 提交 `TASK_READY → TASK_INFLY`。Map 返回未接受时只重试这笔状态写，不能重新下发已经被 RV core 接收的任务
* **DataIn 任务**：只通知 DataIn_task_table 出槽，不改 stream_table 里的当前任务状态

`task_dsa_en=0` 的 Generated 任务下发给 DTE Local RV core，不配 DSA。

### 推进度与退休

完成事件有**七路**：

* DTE、MU、VU 各有 RV core ack 与 DSA ack，共六路
* DTE 这条 Lane 额外接收 Router 的 Reduce Done
* 三条 Completion Lane 直接写 stream_table，不设统一的 Update 模块

判断哪一路才算数，靠当前任务的 `task_recv_type`：

| 场景 | 典型情况 | 谁上报 TS |
| - | - | - |
| RV core 收尾 | 纯 RV core task 不调 DSA，或调了 DSA 但 RV core 会等 DSA 完成后再执行一段程序 | RV core |
| DSA 收尾 | 异步配置调度 DSA 后 RV core 立刻结束 task 程序 | DSA |
| 不确定谁收尾 | RV core 异步配置 DSA 后不查询完成状态，但还要再执行一段程序 | 两者都上报，TS 等二者都完成才算 task 真的完成 |

Reduce 任务的完成要拆成两半：

* **DTE ack 只代表搬运完成**，执行 `consume_only`，不修改 stream 状态
* **只有 Router Reduce Done 才有权把 Reduce 任务置为 TASK_FINISH**
* 两个事件可以任意顺序到达。Router Done 可以被 Hold，但必须等匹配的 DTE ack 被消费后才提交任务完成
* Router 不携带 stream_id，`Task_done` 内部按 `user_id` 找对应 Stream

当前任务进入 `TASK_FINISH` 后，`Task_ctrl` 才生成后继：

* 每个 stream 独立推进，不需要全局 Task Pointer
* 从 `head_ptr` 开始环形扫描，只选 `valid=1 && task_fsm=TASK_FINISH && end=0` 的 stream
* 用一次 64 bit 优先编码**一拍**跳过所有可跳过的 task：

```
SKIP_MASK = ~END_MASK
          & ( (DATA_IN_MASK & done_bitmap)
            | (REISSUE_MASK & ~stream.reissue) )
```

连续 skip 的数量**不增加周期**。可跳过的四种场景：

* 异步 datain_task 已提前完成
* B reissue 任务不需要重发
* P2P 任务不需要重发（Router 通过匹配 `path_id` 告知哪个 P2P task 已完成）
* DP+P2P 场景：有些用户只有 P2P 无计算 task，有些是计算无 P2P。router 请求携带用户是否计算，对应匹配任务链中计算任务，其余 P2P 任务可越过

生成后继的两条硬规矩：

* **End task 即使已提前完成也不能被跳过**，并且不会再生成后继任务
* 新任务的 `task_id`、`task_fsm`、`end` 与全部下发属性必须一起原子写入才算生成成功

生成后的初始状态按类型分：

* 普通 Generated → `TASK_READY`
* DataIn → `TASK_WAIT` 等 ack
* Reissue → `TASK_WAIT` 等 credit

**退休只允许 `head_ptr` 指向的那一项**：

* 条件：`valid=1 && end=1 && task_fsm=TASK_FINISH`
* 顺序：先向 Router 持续发 credit 返还请求，Router 接收后才清除该槽位的 `valid` 并推进 `head_ptr`
* 返还的 credit 经本 core 的 Router 通知上游 core，让上游的 TS credit 加一

## 三处复杂性

上面四个动作假定的是一条直线：数据按任务链的顺序到、下游总能收下、用户数不超过 16。三条假定都不成立。三处应对不是三套独立机制，是四个动作在这三种约束下的变体：

* 第一处：改判就绪的依据
* 第二处：判就绪加一个条件，推进度加一个可跳过
* 第三处：改建表的触发方式，改就绪依据的存放位置

### 数据不按链序到达

在 `tp_nk` 这类切分下：

* 任务链里 task 0/3/7/8 都是“router trigger TS → 调度 DTE 从 router 搬数据进 core”
* 但**这些 task 不一定按任务链顺序执行**，谁先谁后取决于对应数据什么时候到 router
* 所以没法等链序执行到该 task 再去调度 DTE

解法是让 TS 支持**不受任务链约束的 datain task**：

1. 每当 router trigger TS，就激活这个 task 下发到 DTE
2. DTE core 的程序解析数据包头，判断这是任务链中哪一步的数据
3. 搬运完成后通知对应 user 的 stream 项，**只更新 `done_bitmap` 对应位，不推进 `task_id`**
4. 后续任务查询前序所有完成 flag 都有效才能下发

一个典型的 `tp_nk` 任务链（11 步）：

| task_id | unit | end | 任务描述 |
| - | - | - | - |
| 0 | DTE | 0 | Router trigger TS 后创建任务链，配置 DTE 搬 token 到 Core Mem |
| 1 | MU | 0 | 循环执行多个激活专家的 FC1 和 FC3 运算 |
| 2 | DTE | 0 | 搬多个激活专家的 FC1、FC3 数据到 router，等待逐级 reduce |
| 3 | DTE | 0 | router 逐级 reduce 完 trigger TS 后，搬回 Core Mem |
| 4 | VU | 0 | 循环执行多个激活专家的 FC1 SiLU dot FC3，生成 FC2 token |
| 5 | DTE | 0 | 搬 FC2 token 到 router 做 broadcast |
| 6 | MU | 0 | 循环执行多个激活专家的 FC2 运算和专家间 reduce |
| 7 | DTE | 0 | 本 chip 其他 core 数据到达 router 后 trigger TS，搬到 Core Mem 与本 core 数据 concat |
| 8 | DTE | 0 | 上游 chip 的 FC2 result 到达后 trigger TS，搬到 Core Mem |
| 9 | VU | 0 | 把 concat 完的数据和上游 chip 数据 reduce 后写回 Core Mem |
| 10 | DTE | 1 | 从 Core Mem 搬 result 到 router 并 P2P 传到下游 chip |

### 下游收不下

#### 为什么是逐跳 credit

* 端到端 credit 要经过整条路径的往返延迟才能释放
* 路径长到一定程度，16 个 stream 的执行耗时盖不住这个延迟，就会出空泡，吞吐随路径变长而衰减
* 粗算下来端到端 credit 大概只够隐藏 C2C 两跳
* 逐跳 credit 把一段长往返切成每跳各自的短往返，稳态吞吐与跳数无关，代价是要处理中途的阻塞

#### credit 的粒度与检查时机

* 单位是 **stream**，不是 task：Core Mem 空间按 stream 申请和释放
* 同一个 stream 的任务链里，Router **只在第一次往下游发数据时检查 credit**
* 第一次满足之后下游就有了落脚点，后续发往同一下游的 DTE 任务不再检查

检查的发起方分两种：

* **本 core Core Mem → 下游 Router**：属于任务链里的 DTE 任务，由 TS 查下游 credit
* **本 core Router → 下游 Router**：不属于任务链里的任务，即使本 core 没有任何任务它也会自动执行。数据何时到来只有本 core 的 Router 知道，因此由 Router 自己查下游 credit 并触发阻塞重发

遇到 harvest 坏核时：

* 坏核只按路由表透传，**不检查 credit、不支持阻塞重发**
* 上游要查的 credit 对应的是坏核之后那个好核
* 下游返还 credit 也跨过坏核直接给上游好核

#### 用户 token 重发（Broadcast Reissue）

1. broadcast 数据到达 router trigger TS 时，若下游无法接收则把**重发标记置为有效**
2. TS 查询下游 credit，可下发时按用户顺序选**最老的重发用户**，发起重发 task 到 DTE 去 Core Mem 搬 token 到 router
3. 重发 task **不在用户主线任务链上**，可与用户任务链并行执行，优先级高于其他主线 task
4. 重发标记有效但未重发成功时，该用户的原始 token 数据**不能被覆盖，也不能释放该用户**

#### P2P 重发

软件把 bypass 本 core 的任务配成两个 task，分别是 datain 与 dataout。

* **不需要重发**：Router 用 `path_id` 匹配告知哪个 P2P task 已完成，执行到该 task 时直接越过
* **需要重发**：
  * datain 由 router 请求直接驱动 datain_task 做搬运
  * dataout 等前序任务做完、执行到本 task 时向 Router 请求 credit，满足后标记就绪等待下发

#### P2P 阻塞缓冲

为防止 P2P 传输阻塞导致死锁或性能下降，设一个保底的“P2P 阻塞进 core mem”机制。软件可配四项：

* 开关
* 分配给 P2P 缓存的 core mem 容量
* 开启的方向，最多 **3 个**
* 每方向的容量与项数

TS 这一侧要维护：

* 每个方向一张 P2P 阻塞缓冲映射表：`p2p vld | User id | Down direction | Data addr`
* 对应下游 core 的 credit 计数器

走的流程：

1. 上游某方向的 P2P 数据到达 router，下游无资源
2. 数据搬到该方向的缓冲地址并记录表项
3. 下游 credit 释放后，发起一个 TS 调度 DTE 搬数据到 router 继续传输的 task
4. 通知上游释放 credit

#### Reduce 任务的 credit

* 软件配置任务为逐级 reduce 时，同时配置该任务会操作几次 reduce（`reduce_num = N`）
* TS 发现是 reduce task 后**顺序连续下发 N 笔 credit 请求**，credit 满足即可顺序下发
* 直到收全 N 笔 Rmem finish

### 用户数远超 16 项

两种专用 core 的需求：

* B core：EP 分配不均衡时缓存整组被阻塞的用户数据
* R core：缓存大量用户，并等两笔数据集齐

它们的用户数都远超 stream_table 的 16 项：

* 32 MB 的 Matrix Mem 按一个 token 6368 B 算，约 5200 个槽位
* 收发若绑在一条链上，能缓的用户数就被 stream_table 卡在 16
* 更根本的是，数据搬入与后续操作之间的时间窗口很大，TS 覆盖不了这么长的窗口

解法是**双任务链加软件映射表**：

1. 数据接收类 datain 任务由 datain task 支持，但**完成 flag 由软件设置维护，不在 TS 里更新**
2. 后续任务配置为任务链，调度 RV core 循环 check 软件映射表的 flag，check 通过后执行后续的计算、搬运、搬出：
   * check flag 的 RV core 需要长期工作，该 task **不调度对应的 DSA**
   * 任务链创建不受用户数据 trigger 影响，**自动在每个 stream 表项创建起点 task**（`self_start`），按 stream 顺序激活执行 check flag task
   * 前一个 stream check 通过后需清除 ready 用户的 flag，下一个 stream 才能继续 check
   * 一个 stream 的任务链完成后，会在对应 stream 项**自发创建新的任务链**

TS 侧的启动过程：

* 复位后直接自启动 16 个 stream_table 表项，同时激活 16 个用户的自启动任务参与仲裁发射，执行过程同普通计算 core
* 启动时没有用户信息，等自启动任务（RV core）返回 user_id 后更新 stream_table，再调度后续任务
* 表项从队头 retire 后再激活一个新表项，继续等待自启动任务

拆开的是本来绑在一起的两段时间：**在 TS 里占一个 stream 项**的时间，与**数据在本核停留**的时间。由此换来三件事：

* 在途用户数的上限从 stream_table 的 16 项换成 Matrix Mem 的容量
* 推进顺序从 TS 的年龄优先换成软件表说了算：链二主动去表里挑已经集齐的用户，不受到达顺序约束
* R core 必须按“谁先集齐”推进，单链下做不到

B core 的搬出 task 还要按 `B_CORE_DIRECTION` check 下游 core 的 TS credit；落 Matrix Mem 的那一侧不查 TS credit，反压由 GPU 到 Bach 的两层 credit 兜底。

## 异常与时延

### 异常检测

* 异步 task 本该执行 1 次完成，但 RV core 或 DSA 对同一 task 返回多次完成
* RV core、DSA 返回非法的 `task_id`、`stream_id`
* 超时：
  * 异步任务长时间（软件配置，例如 1 us）没有收到外部 trigger
  * 用户长时间未 retire
  * router 请求携带的 `path_id` 在 task_chain 里匹配不到

异常经 `ts2corestatus_int_ch` 上报 Core Status，再到 SCP。

| 结构 | 深度 |

### 三套时延数字不是一回事

| 数字 | 出处 | 口径 |

## 取舍

* **为什么 Reduce 的完成要拆成两个事件**
  * DTE 把数据搬到 Router 就结束了自己的活，但 reduce 是在 Router 的 Rmem 里做的，此时结果还没算出来
  * 若让 DTE ack 直接结束这个 task，后继任务会读到还没归约完的数据
  * 所以 DTE ack 只作 `consume_only`，把结束的权力交给 Router Reduce Done
* **为什么 datain 不推进 task_id**
  * 推进 task_id 意味着承认任务链走到了那一步，而异步 datain 的到达顺序与链序无关
  * 只落 `done_bitmap` 的一位，就把“这一步的数据齐了”与“任务链走到了这一步”分开记
  * 两者在 `Task_ctrl` 生成后继时才合到一起判断
* **为什么退休只允许 head**
  * stream_table 是顺序 FIFO，credit 也按 stream 记账
  * 只让队头退休，`head_ptr` 才能单调推进，年龄比较才有确定的基准
  * 代价是队头卡住时后面已经完成的 stream 也得等着
* **为什么先还 credit 再清 valid**
  * 反过来做，槽位已经放开而上游还没拿到 credit
  * 中间这段时间上游发来的数据在本 core 没有落脚点
